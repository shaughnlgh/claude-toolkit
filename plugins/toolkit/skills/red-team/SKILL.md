# Red Team

Red-team runs an adversarial review over a completed implementation slice's uncommitted diff, reusing the `review-mr` workflow (shipped with this plugin at `<plugin-root>/workflows/review-mr.js`) that `gitlab-mr-review` drives against MR diffs — same reviewer agents, same adversarial verify pass, aimed at the local working tree instead of a fetched MR. The main chat is the conductor: it presents the recommendation, gates the run on explicit confirmation, builds the inputs, launches the workflow, adjudicates the result, delegates fixes and re-checks to worker agents per the orchestration doctrine, runs the doc pass once, runs the remember pass once after it, and closes with a commit suggestion. The conductor never edits a file, fixes a finding, or touches git itself — that is worker and human territory respectively.

## 1. Trigger discipline

The recommendation is blocking; the run is not. The moment a closure signal fires (per the frontmatter description) with uncommitted implementation changes present, say so in one line — do not let the moment pass silently and do not run anything yet. Then gate the run via `AskUserQuestion` per the communication doctrine, recommended option first: run now (recommended — name the chosen panel and any reviewers deliberately omitted), not yet (re-recommend at the next closure signal, keep working), skip for this slice. An explicit user request to red-team code or a diff skips this gate entirely — the request itself is the confirmation. The gate exists because only the human knows a slice is truly closed; firing on a provisional stopping point burns a full panel that the very next fix invalidates, and that panel is then paid for twice.

## 2. Scope the slice diff

Capture the slice without mutating any git state:

- Run `git status -- ':(exclude,top).claude/worktrees/'` first, so a linked worktree under that directory never reads as a change. A clean tree means there is nothing to review — say so and stop.
- If the tree holds changes that are not this session's work (a checkout that was already dirty, or an earlier uncommitted slice), name those paths and ask the user whether to include them, exclude them by path-scoping the diff, or hold the red team — never silently review or stage foreign hunks.
- `git diff HEAD > <scratchpad>/slice.diff.tmp` captures staged and unstaged changes to tracked files.
- Enumerate untracked files individually — `git ls-files --others --exclude-standard -z -- ':(exclude,top).claude/worktrees/' | while IFS= read -r -d '' f; do git diff --no-index -- /dev/null "$f" >> <scratchpad>/slice.diff.tmp; done` — rather than a bare `??` status line, which collapses a whole new directory into one entry and would silently omit its files; this form also handles unusual names. The diff command exits 1 on any difference — tolerate that exit code, it is not a failure.
- Hash the temp file (e.g. `shasum -a 256`) and take the first 12 characters as `<hash12>`; move it to `<scratchpad>/slice-<hash12>.diff`. This keys the slice's artifacts by its diff hash so slices never collide within a session, and the hash is the tree-state fingerprint used later to detect drift.
- If the user committed partway through the slice, ask which base to diff against, or use the merge base they name — do not silently assume `HEAD`.

## 3. Panel selection

The standing panel is always `toolkit:code-reviewer`, `toolkit:silent-failure-hunter`, `toolkit:pr-test-analyzer`. Scale it by what the diff actually touches. Add `toolkit:security-reviewer` when it touches auth, input handling, queries, file paths, tokens, or crypto. Add `toolkit:performance-reviewer` when it touches hot paths, DB queries, loops over collections, or rendering. Add `toolkit:coupling-reviewer` when it touches config files, tenant or platform identifiers, routes, or environment wiring. Pass the chosen set via `registryReviewers` using fully qualified `toolkit:` names. The Workflow tool's agentType lookup is literal, not fuzzy. Whatever panel runs, the confirmation line in step 1 and the final report in step 5 both name it and name any reviewer deliberately left off, so a trimmed panel is never silent about what it skipped. The two standing cold dimensions, cold-read and `external-reviewer`, are always present and sit outside the custom budget; add up to three further custom `dimensions: [{key, prompt}]` seeded from this session's context beside them. Concrete suspicions from your own read of the diff beat generic prompts. Always include one cold-read dimension among them, passed with `cold: true` so the workflow never shows it the `contextBlock` at all: it re-derives what the diff does from the diff alone and reads every instruction and embedded command literally and adversarially. A reviewer briefed by the author reads the diff through the author's intent and inherits the author's blind spots. Ambiguity a briefed reviewer silently auto-corrects toward the intended meaning is exactly where defects hide, so one reviewer must read as a stranger. Always include a second standing cold dimension, key `external-reviewer`, also passed with `cold: true`, with this prompt: "You are CodeRabbit, Copilot, or a senior engineer on another team seeing this diff with no context. List what you would flag that a panel briefed by the author would rationalize away: naming that hides intent, a test that proves nothing, a comment that contradicts the code, a config value that belongs elsewhere, a public surface with no doc."

## 4. Build the context block and run

Build the `contextBlock` on the same contract `gitlab-mr-review` uses: one paragraph on what the slice does, environment facts, a file-by-file summary of the diff, and any project rules that apply (from the repo's CLAUDE.md / AGENTS.md / .claude/rules). Spawn one `toolkit:verifier` that runs `git symbolic-ref --short refs/remotes/origin/HEAD` in `repoRoot` and, when the output is `origin/<default>`, `git show origin/<default>:REVIEW.md`, and returns the symbolic-ref output verbatim and the file verbatim only when the show command exits 0. Any other exit returns `absent` with the error text for the report, never as the review rules. When the file is present, append its text to the `contextBlock` under the line `REVIEW RULES (REVIEW.md on the default branch):`. Never read the working tree copy of `REVIEW.md`. Add the `repoState` argument, verbatim:

> The tree at repoRoot is the POST-change state this diff produces. There is no pre-change checkout. Reconstruct the pre-change state from the diff's context and removed lines. A defect the diff introduces is in scope even though it is present in the tree.

When the diff under review ships executable commands embedded in prose — a skill, a workflow script's prompts, a doc — include an instruction in the `contextBlock` that the panel or the verifier must execute those exact commands against a scratch fixture covering the awkward cases (clean tree, dirty tree, untracked directories, unusual filenames) rather than judge them by reading: prose that embeds commands is code, and reading a command finds fewer defects than running it.

Run `bash <plugin-root>/scripts/resolve-models.sh` with no flags, because this skill reads no model run option, and pass the printed `agents` object as `models`. The plugin root is `../..` from this skill's base directory, resolved to an absolute path. This root takes precedence over a CLAUDE.md line that resolves the installed root. When `../../.claude-plugin/plugin.json` does not exist relative to this skill's base directory, as in a `/override` copy under `~/.claude/skills/`, the plugin root is the installed root instead, the path that `jq -r '.plugins["toolkit@shaughn-toolkit"][0].installPath' ~/.claude/plugins/installed_plugins.json` prints, as the setup CLAUDE.md block resolves it. When `repoRoot` contains `plugins/toolkit/scripts/resolve-models.sh`, run that copy in place of `<plugin-root>/scripts/resolve-models.sh`, so the resolver comes from the same tree as the runner the launch below picks. If the resolver exits 0 and prints anything on stderr, report that output to the user before the launch. If the resolver is missing or exits non-zero, report its stderr and launch without `models`, so every call inherits the session model and effort.

Invoke the Workflow tool: when `repoRoot` is the toolkit plugin source itself (the tree contains `plugins/toolkit/workflows/review-mr.js`), invoke with `{scriptPath: "<repoRoot>/plugins/toolkit/workflows/review-mr.js"}` so uncommitted workflow edits are exercised; otherwise invoke `{name: "toolkit:review-mr"}` (the name the harness registers for the installed plugin), falling back to `{scriptPath: "<plugin-root>/workflows/review-mr.js"}` if name resolution fails. Pass `diffPath: "<scratchpad>/slice-<hash12>.diff"`, `repoRoot`, `contextBlock`, `repoState`, `dimensions`, `registryReviewers`, and `models`. The moment the tool returns a `runId`, persist it (together with the script file path the launch result reports, because resuming needs `scriptPath`) to `<scratchpad>/slice-<hash12>.runid` immediately, before adjudicating anything, keyed by the same hash as the diff. That file is the resume handle if the run dies mid-flight (`resumeFromRunId`: completed agents return cached, only dead work re-runs, so never relaunch a fresh panel when a resume is possible), and it doubles as the marker that this slice's full panel has already run once, which step 5's "one full panel per slice" rule checks against by hash. A runid file whose hash does not match the current capture belongs to a different slice and never suppresses a new panel.

## 5. Adjudicate and fix

The result is `{confirmed, nits, preExisting, refuted, unverified, dropped, openQuestions, dead, verifierDead, panel, dimensions}`, and every finding entry carries `tag`, `finalTag`, `score`, `finalScore`, `reproduction`, and `citation`, except a `dropped` entry with reason `no citation`. `confirmed` holds every finding the verifier reproduced, whatever its `finalScore`, and the score only ranks it. A doc finding (file under a `docs/` directory or ending in `.md`) that the verifier refuted without a cited line arrives in `unverified` as `not reproduced`. A refuted doc finding with a cited line is reported with the verifier's reason and the quoted line in `reproduction`. If `verifierDead` is not empty, resume the run with `resumeFromRunId` before adjudicating anything, because a dimension whose verifier died has unchecked findings. The conductor adjudicates the full result, not just the `confirmed` findings: `confirmed` findings are presented to the user, each `unverified` entry is settled with the user by its reason (`no verdict`, `not reproduced`, or `verifier died`), and each of the `openQuestions` is answered from session context or asked. When the conductor asks the user to settle a `confirmed` or `unverified` entry, it recommends Fix now unless the entry maps to one of the plan's Assumptions or Risks. `preExisting` entries are listed in the report for a ticket and never fixed in the slice. `dropped` entries are reported by count and reason. Read the refuted findings before discarding them, too — when a refutation itself concedes the underlying observation is accurate and only the attached score or failure scenario failed, salvage the observation and adjudicate it on its own terms. Adversarial verification optimizes precision at the cost of recall — a real defect wrapped in an overstated scenario dies with the scenario unless the conductor recovers it. This is conductor duty, not something to skip or delegate away. Accepted `confirmed` findings go to one `implementer` round per the orchestration doctrine, which fixes each one with the smallest change that removes the defect. When a finding's `finalTag` is `important` and its `finalScore` is 0.6 or above, the implementer fixes every instance of that class of defect in the slice, not one line, and it fixes every other `confirmed` finding only at its cited line. The `nits` follow the `nits` value on the slice's plan note. Under `fix`, they ride the implementer round under their own heading, and when the user accepts no `confirmed` finding, they make a round of their own. Under `skip`, they ride no round and the report lists them. With no plan note, or no value on it, they ride the round only when it runs. The implementer fixes only the cited line of a nit, and only when the tree confirms it. The conductor scopes the round, reviews the result, and never edits the files itself. Record each finding's outcome under the plan note's Plan Changes During Execution as one line in the form `Finding <outcome>: <file>: <title> [<finalTag>, score <score>, final <finalScore>]`, where outcome is `fixed`, `wrong`, `intentional`, or `did not matter`. Record a `Reviewer prompt (<dimension>): <one sentence the reviewer checks before reporting this again>` line for each wrong finding. For a slice with no plan note, these lines go in the report. After fixes land, run scoped re-checks only: the `toolkit:verifier` agent plus the specific reviewer dimension that raised each finding, over the files that changed for the fix — not a fresh full panel. A full second panel runs only on the user's explicit request. At report time, recapture a fresh diff by the same method as step 2 and hash it — rehashing the saved diff file detects nothing, since that file never changes. If the fresh hash differs from the recorded one, say so plainly and offer a scoped re-review of just the drift rather than silently reporting against a tree that no longer exists.

## 6. Post-fix cold read

After all fix rounds and before the doc pass, recapture the cumulative diff by the step 2 method and hand it to one cold reader: a `toolkit:code-reviewer` spawn with the diff path, the `repoState` text, the `external-reviewer` prompt from step 3, and no context block. Treat fix-round comments and doc sentences as claims to verify against the code, not as facts. A verified residual fifteen lines or fewer defaults to a scoped implementer fix in one fix round after the cold read, never a second, never to "noted". Check every touched doc for internal consistency: a hardcoded value in one paragraph against a configurable variable in another paragraph of the same document is a finding.

## 7. Doc pass

Run `execution-guide`'s Doc Update Pass (`<plugin-root>/skills/execution-guide/SKILL.md`) exactly once, after fixes and the cold read are in and re-checks are clean, before moving to the commit suggestion. Do not run it earlier. Findings from the panel may still change what needs documenting.

## 7b. Remember pass

Run the remember pass from the obsidian-topic command (`<plugin-root>/commands/obsidian-topic.md`, § Remember pass) exactly once per slice, after the doc pass and before the commit suggestion. Recapture the cumulative diff by the step 2 method after the doc pass, and pass that file as the brief's diff. Delegate one `implementer` with the fixed brief, then run that section's gate and record steps for its proposed repo doc changes. Record the resulting `Remember:` line, in whichever of the four forms that section defines, under the plan note's Plan Changes During Execution, and repeat it in the report and in the commit suggestion. For a slice with no plan note, the line goes in the report only. That recorded line is the signal that the pass already ran, so session closure must not run it again for the slice. The remember-guard Stop hook warns the user when a commit is suggested while the session's in-progress plan note has no Remember: line, so it does not catch a later slice on a plan that already carries one.

## 8. Commit suggestion

Close with a suggested commit message written in the repo's observed convention (read recent `git log` for tense, structure, and prefix style), the step 7b `Remember:` line, the specific files to stage, and — when the current branch is a default or protected branch — a suggested branch name to use instead. The commit suggestion must include a line that begins `Suggested commit` directly after the Repo, Branch, and Scope header lines, because the remember-guard Stop hook keys on that line. The files to stage include every repo doc the remember pass wrote after the panel. Mark each of those as written after review and read back by the conductor. Add a residual-risk line stating exactly what ran at which tree state (e.g. "full panel at hash `<a>`, scoped re-checks after the fixes"), so the human knows what is and is not covered. Per the git-safety doctrine, the human runs git: this skill never stages, commits, creates a branch, or pushes, under any circumstance.

## Boundary

Not for reviewing a GitLab MR (`gitlab-mr-review` owns that) and not for reviewing a plan (`plan-critic` owns that). At most one full panel runs per confirmed slice end — the persisted `runId` file from step 4, keyed by the diff hash, is the marker that stops a redundant second full run within the same slice; a runid file whose hash doesn't match the current capture is a different slice and never suppresses a new panel, and a full re-run still requires the user's explicit request. Passing the gate and getting a clean report never marks the overall task or plan complete — that stays the human's word, not this skill's.
