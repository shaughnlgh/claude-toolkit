# Execute Flow

Execute-flow is the conductor side of the `execute-runner` workflow, shipped with this plugin at `<plugin-root>/workflows/execute-runner.js`. The script runs a baseline check, one implementer per Implementation Step in order, the plan's Validation Steps with one fix round, a diff capture, the `review-mr` child workflow as the panel, a bounded fix loop, a second capture, a cold read, and, only when nothing blocked, the Doc Update Pass, a final validation, a post-doc capture, and the remember pass. A verified cold-read finding does not block those passes. The conductor reads the run options and then asks nothing. It opens a worktree with no question when the seat is held, when the main checkout holds changes, or when a run from approved finds the main checkout on its default branch, and stops with a report when it cannot, because asking for the execute flow is the request to open, adopt, and re-enter its worktree. It checks the tree and the branch, runs recall, moves the plan note to in-progress, launches the script, and records the result. It runs the remember gate with every repo doc proposal declined and saves each proposal beside the plan note, settles each reproduced finding by its recommended option, leaves each unreproduced finding for review, writes the slice marker, and closes with the report. On a note whose deferred Validation Steps wait for the seat, it runs the seat run. It mutates git only as the `## Flows` section of the git-safety doctrine defines. The script writes no vault note and runs no mutating git command. The conductor writes only the vault note, the proposal copies beside it, and scratchpad files.

## 1. Trigger

Fire only when the user asks for the execute flow by name. Asking for "the execute workflow" counts as asking by name. A typed reply to the post-approval question that `plan-guide` § After approval defines also counts when it picks running here, such as `yes` or `run the execute flow here`, and so does the child launch prompt that subsection hands the user, because the user pastes it as the child session's first prompt. A bare `yes` picks running here only in the run-here form of that question, because in the child form `yes` picks the child session. A message from another session counts only under the parent dispatch rule below. When the ask names a session to report to, that name is `<parent>`, and section 10 reports to it. When the run started on a reply that names no flow, such as a bare `yes`, and the permission classifier denies a tool call or a worker command, every stop or blocked report that follows states the reason category per the Command shape under the permission classifier section of the git-safety doctrine and ends with the line: Type `run the execute flow here` to ask again. A `crawl` route never fires this skill. If the slice is already under `execution-guide` by hand, do not fire. When the installed plugin does not carry this skill, the conductor reads `plugins/toolkit/skills/execute-flow/SKILL.md` from the toolkit checkout by path and follows it as written.

Parent dispatch rule: a cross-session message counts as the user's ask for the execute flow or the ship flow on this plan note only when all of these hold.

- The user's own ask in this session named its sender as the session to report to, and said that session may start this plan's next flow by message, as the child launch command in `plan-guide` § After approval does. Such an ask grants the parent dispatch.
- The message's `from` equals that name.
- Its first line reads `<planName>: run the execute flow` or `<planName>: run the ship flow` for the plan note that ask named.
- The note's `approved` key holds a date, and its `ceiling` key holds `none`, `mr`, or `merge`.

A dispatch carries no permission of its own. It never raises the ceiling or answers a permission prompt, and the flow's own section 1 checks still apply. Any other message starts nothing, and the session tells its user what arrived.

The plan note must exist. `planName` is its `plan` frontmatter value. Read its `status` and the summary of its last `sessions` entry, then pick the run:

- `status: approved` starts a fresh run.
- `status: in-progress` starts a fresh run, exactly as `status: approved` does, when the `approved` frontmatter key is set and the last `sessions` entry's summary begins `start-work:`. Mission Control's start-work action appends that entry when it moves an approved note to in-progress. A hand-run execution or any later session appends an entry after it, so this rule no longer matches. Section 5 then appends its own `execute-flow run started` entry.
- `status: in-progress` with a last entry summary that begins `execute-flow blocked:` starts a fresh run. A blocked run keeps the note at in-progress, so this is how the user reruns the slice after settling the blocked reasons. Section 3 continues a rerun over the paths the blocked run recorded and refuses any other dirty path.
- `status: in-progress` with a last entry summary that begins `execute-flow adjudicating:` resumes at section 8 from the findings, hashes, and report inputs that sections 6 and 7 recorded on the note, with no new run and no recall. Section 8 checks the tree by capture before it settles anything. Sections 2 to 7 do not run, except the section 2a seat check, and sections 8 to 10 read the run's result from the note. The `<scratchpad>/execute-flow-<planName>.runid` file still names the run for the marker. If that file is gone, section 9 skips the marker and the report says so.
- `status: in-progress` with a last entry summary of `execute-flow run started` under another session id starts a fresh run, because that run died before section 6 or section 7 recorded its outcome.
- `status: in-progress` with a last entry summary of `execute-flow run started` under this session's id resumes that run with `resumeFromRunId` when `<scratchpad>/execute-flow-<planName>.runid` exists, and completed agents replay from cache. Section 5 writes that file only after the Workflow tool returned a `runId` and deletes it before each fresh launch, so it always names the latest run. Without that file, the launch never happened, so it starts a fresh run.
- `status: in-progress` routes to the seat run when Plan Changes During Execution holds a `Validation deferred:` line and the last entry summary begins `execute-flow finished:`, `ship-flow stopped:`, `ship-flow finished:`, `seat-run finished:`, or `seat-run blocked:`, or reads `seat-run started`. Such a note runs section 2 and then section 11. Sections 2a to 10 and the worktree re-entry below do not run.

If the note matches none of these, state the status and stop.

Apart from the seat route, before section 2, take the last line under Plan Changes During Execution that begins `Seat: worktree `, if the note has one. Its path is the text after that prefix, up to the first `, holder` when the line carries one. If the session already runs in that path, this section counts the worktree as entered: `repoRoot` is that path, and section 2a opens no other worktree. If the session does not already run in that path and `test -d <path>` succeeds, run the occupant check below on `<path>`, then call EnterWorktree with `path` set to it, because an earlier run of this plan ran there and left its changes there. If the directory is gone or EnterWorktree fails, stop with the plan note untouched, and report the error and the recorded path. Never resume or rerun from the main checkout, because a resumed workflow keeps the worktree as its `repoRoot`. The seat route is the one exception, and it needs a `Validation deferred:` line and one of its six summaries, so a blocked or adjudicating execute run still re-enters its worktree.

Occupant check: before an EnterWorktree `path` call on an existing worktree, here or in section 2a, rerun the section 2a seat-check command with `--worktree '<path>'` appended. If it prints an `occupant:` line, stop with the plan note untouched and no status change. The stop names each occupant by its name and session id, and says that another live session already runs in that worktree, so that session must end first. A held seat, exit 10, does not stop this check. Exit 2 means the check could not run: say so in the report and continue.

Unrecorded worktree rule: apart from the seat route, when the note has no `Seat: worktree` line and `pwd -P` sits under `<checkout>/.claude/worktrees/`, where `<checkout>` is the checkout that the note's `repo` names, the session runs in a worktree the note does not record. `<wt>` is `<checkout>/.claude/worktrees/<dir>`, where `<dir>` is the first path component after that prefix. When `<dir>` does not match `^[A-Za-z0-9._-]+$`, stop with the plan note untouched and name `<wt>`, because section 2a puts `<dir>` in the install command. Spawn one `toolkit:verifier` that runs `git branch --show-current` and `git rev-parse --path-format=absolute --git-common-dir` in `<wt>` and returns each output verbatim. When the common dir is `<checkout>/.git` and the section 2a ownership rule holds for `<wt>` and that branch, this section adopts the worktree: `repoRoot` is `<wt>`, and adoption counts as entering a worktree in every later section, except that section 2a runs the install step there and section 5 records its `Seat: worktree` line. Otherwise stop with the plan note untouched, name `<wt>` and its branch, and tell the user to ask for the execute flow from a session started in `<checkout>`.

`repoRoot` is the absolute path of the checkout that the plan note's `repo` frontmatter names, or the worktree path once this section or section 2a enters a worktree. `repoName` is the basename of the main checkout, the parent of the directory that `git rev-parse --git-common-dir` names when that directory is called `.git`, never the basename of `repoRoot`, so a run from a linked worktree recalls and reports under the main checkout's name. The `main:` line that section 2a prints names the main checkout. When the seat check could not run, take it from the `git rev-parse --path-format=absolute --git-common-dir` output that section 3 returns. If neither resolves that path, stop before any status change and report that the main checkout could not be resolved. `<plugin-root>` is `../..` from this skill's base directory, the directory that holds this SKILL.md, resolved to an absolute path, so a `--plugin-dir` session runs the loaded copy's scripts. This root takes precedence over a CLAUDE.md line that resolves the installed root. When `../../.claude-plugin/plugin.json` does not exist relative to this skill's base directory, as in a `/override` copy under `~/.claude/skills/`, the plugin root is the installed root instead, the path that `jq -r '.plugins["toolkit@shaughn-toolkit"][0].installPath' ~/.claude/plugins/installed_plugins.json` prints, as the setup CLAUDE.md block resolves it.

`<runner-plugin-root>` is `<repoRoot>/plugins/toolkit` when `repoRoot` holds `plugins/toolkit/workflows/execute-runner.js` and that file contains `planPath`, which is when section 5 launches the repo's own runner with `planPath`, and `<plugin-root>` otherwise. A repo runner without `planPath` ships with a `vault-fs.sh` that has no `index` or `sha256` subcommand, so it takes `<plugin-root>`, as it did before the read by path. The runner's `pluginRoot`, the section 5 step count, and the section 8 `vault-fs.sh index` and `sha256` calls all use it, so a repo runner that reads the plan by path never runs with the installed plugin's scripts.

Own-worktree rule: every `git status` and `git ls-files` command that this flow's verifiers run ends with the pathspec `-- ':(exclude,top).claude/worktrees/'`. Claude Code creates its linked worktrees under that directory, git lists each one as a single untracked directory even under `-uall`, and the flow reads no ignore entry for that directory.

Ref-name rule: a ref name that this flow puts in a shell command, which is the note's `branch` value, the section 3 branch output, the section 3 default branch, or a section 11 restore point, must match `^[A-Za-z0-9._/-]+$` before any command names it. The note's `branch` value and a section 11 restore point must also pass `git check-ref-format --branch`, which the next verifier runs on the single-quoted name. A sha that this flow puts in a command, which is a detached restore point, a `Seat run base:` value, a `Seat run tip:` value, or a worktree HEAD, must match `^[0-9a-f]{7,40}$`. A value that fails stops the flow before that command with the plan note untouched, and the report names it. Every command and handoff single-quotes a ref name. Git accepts `;`, `$`, a backtick, `|`, and `&` in a branch name, so `git check-ref-format` alone does not keep a name out of the shell.

## 2. Run options

Before anything else, read the run options per `plan-guide` § Run options (`<plugin-root>/skills/plan-guide/SKILL.md`): from the plan note, then from `<scratchpad>/flow-run-options` for the keys the note lacks when that file's `plan:` line names this plan, then ask only the questions for the keys still missing, and write the cache for this plan. Section 5 records every key the note lacked in its status write. After this section the flow asks no question under any ceiling. A step that needs a person is a stop with a report, and a git step under `none` is a paste-ready handoff followed by a stop. The execute flow never mutates git state under any ceiling, apart from the section 2a worktree and the section 11 seat run. Asking for the execute flow is the explicit worktree request that EnterWorktree requires, as this skill's description and the git-safety Flows section state, so EnterWorktree runs under every ceiling, `none` included, while the section 2a worktree commands run through an implementer only under `mr` or `merge` and stay paste-ready under `none`. Apart from those commands, its agents run only read-only git in the repo. Sections 5 and 11 pass `nits` and `e2e` to the runner. The `## Flows` section of the git-safety doctrine (`<plugin-root>/doctrine/git-safety.md`) defines what each ceiling permits.

## 2a. Seat

The seat is the main checkout, which a running local stack serves. Run `bash <plugin-root>/scripts/seat-check.sh <repoRoot> --self <session id>` directly, as section 4 runs recall, with the session id taken from the scratchpad path. Pass `repoRoot` as given, because the harness refuses a command whose text names `git` from a worktree session. The script reads `claude agents --json` and prints `seat: free` or `seat: held`, then the `main:`, `branch:`, and `dirty:` lines, then one tab-separated `holder: <name> <status> <kind> <sessionId> <cwd>` line per holder. Keep the output for sections 6 and 10. Exit 2 means the check could not run: say so in the report and continue as if the seat were free. On a resume, and after section 1 entered a recorded worktree, the check still runs, because the report names the holders.

`<branch>` is the plan note's `branch` frontmatter value. The worktree name `<name>` is `<planName>`, which `plan-guide` keeps lowercase kebab-case and unique across the vault, so no two plans share a `.claude/worktrees/` directory, and EnterWorktree `name` creates the branch `worktree-<planName>`. For a worktree that section 1 adopted, `<name>` is its directory name. Every EnterWorktree `name` and every `.claude/worktrees/` directory this flow names uses `<name>`. When `<branch>` is not blank, check it by the section 1 ref-name rule before any command names it.

Ownership rule: a worktree that the note does not record is this plan's when it is on `<branch>` with `<branch>` not blank, or when its directory is `.claude/worktrees/<planName>`, it is on `worktree-<planName>`, and a search of the vault finds exactly one `plan - <planName>.md`. The search runs `find '<vaultRoot>' -type f -name 'plan - <planName>.md'`, with `vaultRoot` as section 5 passes it. `<planName>` matches the `plan-guide` plan name pattern, so it is safe in the `-name` pattern. When the search finds more than one, stop with the plan note untouched and name every path it found, because `plan-guide` asks for a unique plan name and `validate-plan.py` does not check it across the vault. A worktree on any other branch, or detached, belongs to other work, and the flow never enters or adopts it.

When section 1 entered no worktree or adopted one, resolve the install step before any worktree entry, or before the install in an adopted worktree. Read `<main>/CLAUDE.md` without editing it. If a line begins `Worktree install: `, `<install>` is the rest of that line with every `<worktree>` token replaced by `.claude/worktrees/<name>`, the worktree path relative to the main checkout. That line is an override for a repo the defaults below do not fit, and it wins. Otherwise, if `<main>/.env` contains a line that begins `WARDEN_ENV_NAME=` and `<main>/composer.lock` exists, the composer part is `warden env exec -T php-fpm composer install -d /var/www/html/.claude/worktrees/<name> --no-interaction --no-scripts`. The Warden form exists because Composer runs in the `php-fpm` container, which mounts the main checkout at `/var/www/html`, and it carries `--no-scripts` because a Composer script in the container commonly reaches the running stack, which serves the main checkout. Otherwise, if `<main>/composer.lock` exists, the composer part is `composer install --no-interaction`. If `<main>/package-lock.json` exists, the npm part is `npm ci`, run on the host in both cases. `<install>` is the composer part, the npm part, or both joined with ` && `, composer first. If neither lockfile exists, the repo has no install step. The Warden command runs with the worktree as its working directory like any other, and `warden` finds the environment by walking up from there.

When section 1 entered no worktree, first run `test -d <main>/.claude/worktrees/<name>`. If it succeeds, spawn one `toolkit:verifier` that runs `git worktree list --porcelain` in `<main>` and returns the output verbatim, and read the `branch` line of the entry whose `worktree` line is that directory. When the ownership rule holds for that branch, run the section 1 occupant check on that directory, then call EnterWorktree with `path` set to that directory, and run the install step below whatever the seat state, because an earlier run of this plan opened it and stopped before section 5 recorded it, such as on a failed install. Otherwise stop with the plan note untouched, and name the directory and the branch it holds, or that it holds no branch. When `test -d` fails, decide by the table below on a fresh run. A rerun is the section 1 `execute-flow blocked:` bullet, or the `execute-flow run started` bullet under another session id. A run from approved is the section 1 `status: approved` bullet or the `start-work:` bullet. Exit 2 leaves `dirty:` unknown.

Default branch rule: the main checkout sits on a default branch when the seat check's `branch:` value is `main`, `master`, or `detached`, or equals `<default>`. On a run from approved or start-work, when the seat check exited 0 with `seat: free` and `dirty: 0` and its `branch:` value is none of `main`, `master`, and `detached`, and is not `<branch>` when `<branch>` is not blank, spawn one `toolkit:verifier` that runs `git symbolic-ref --short refs/remotes/origin/HEAD` in `<main>` and returns the output verbatim with its exit code. A blank `<branch>` never skips this read. `<default>` is the text after `origin/` when that command exits 0 and the text matches the section 1 ref-name pattern. Otherwise, and when the read did not run, `<default>` is unset. Section 3 stops a run on a default branch, so a run from approved or start-work on a free, clean main checkout that sits on one takes a worktree, which carries the plan's branch or the branch EnterWorktree creates.

| Seat check | `dirty:` | Run | Main checkout branch | Result |
|---|---|---|---|---|
| free | 0 | from approved or start-work | a default branch | worktree |
| free | 0 | from approved or start-work | `<branch>`, or any other when `<branch>` is blank | main checkout |
| free | 0 | from approved or start-work | any other when `<branch>` is not blank | worktree |
| free | 0 | rerun | any | main checkout |
| exit 2 | unknown | any | unknown | main checkout |
| free | above 0 | from approved or start-work | any | worktree |
| free | above 0 | rerun | any | main checkout, section 3 decides |
| held | 0 | any | any | worktree |
| held | above 0 | from approved or start-work | any | worktree |
| held | above 0 | rerun | any | stop, plan note untouched, holders named |

When `dirty:` is above 0 and the table gives a worktree or a stop, spawn one `toolkit:verifier` before any worktree entry. It runs `git -c core.quotePath=false status --porcelain -uall` with the section 1 own-worktree pathspec and `git rev-parse --path-format=absolute --git-common-dir` in `<main>`, and returns each output verbatim. Take each path by the section 3 rules. For each untracked path, a `??` line, build the paste-ready line `printf '%s\n' '/<path>' >> "<common dir>/info/exclude"`. A path that holds a single quote, a backslash, `*`, `?`, or `[`, or that starts with `!` or `#`, gets no line, and the report names it for the user to ignore by hand. For each tracked path, tell the user to commit or discard it on the main checkout's branch. The stop names the holders and these paths. A worktree run keeps them for section 10 under `Main checkout not clean`, with the sentence that the seat run needs an empty status in the main checkout.

Once the table gives a worktree, the conductor calls EnterWorktree or stops. When the tool is not available, a permission rule refuses it, or the call fails, stop with the plan note untouched and a report that names the cause and the setting that removes it, such as a deny rule for EnterWorktree or `permissions.blockWritesOutsideWorkingDirectories`. Never ask whether to enter the worktree, and never fall back to the main checkout.

When `<branch>` is not blank, spawn one `toolkit:verifier` that runs `git check-ref-format --branch '<branch>'` in `<main>` first. If that command exits non-zero, the verifier runs no other command, and the flow stops by the section 1 ref-name rule. Otherwise it runs `git worktree list --porcelain`, `git branch --list '<branch>'`, `git remote get-url origin`, `git ls-remote --heads origin '<branch>'`, and `git symbolic-ref --short refs/remotes/origin/HEAD` there, and returns each output verbatim with its exit code. When `git remote get-url origin` fails, the repo has no origin remote, and the failed `git ls-remote` reads as no remote branch. Only the second case below reads the symbolic-ref result, so a failed symbolic-ref stops no other case. When any other of these commands exits non-zero, stop with the plan note untouched and report its error, because a failed lookup against a configured origin cannot tell a missing branch from an unreachable remote. Then take the first case that applies:

- If either branch output is not empty, the plan's branch exists. If a `branch refs/heads/<branch>` line in the list sits under another worktree, git refuses a second checkout of the branch, so stop with the plan note untouched and report it. EnterWorktree with `name` would create a new branch instead, so obtain the worktree with the commands below, then call EnterWorktree with `path` set to `<main>/.claude/worktrees/<name>`. The fetch line applies only when `git branch --list` printed nothing, so the add creates the local branch from `origin/<branch>`. Under ceiling `none`, stop with the plan note untouched and hand the user the commands paste-ready, and the next ask enters the directory through the `test -d` check above. Under `mr` or `merge`, spawn one `toolkit:implementer` that runs only these commands in `<main>`, each as its own call, and returns each output. If a worktree command fails, stop with the plan note untouched and report its error.
- If `<branch>` is not blank and the ceiling is `mr` or `merge`, the plan's branch exists nowhere, so cut it under the name the note records. When origin exists and the symbolic-ref command failed, stop with the plan note untouched and the section 3 set-head handoff. `<default>` is the text after `origin/` in its output, and it must pass the section 1 ref-name rule. Spawn one `toolkit:implementer` that runs the second case commands below in `<main>`, each as its own call, and returns each output. With no origin remote, it runs only the add, with no start point, so the branch starts at the main checkout's HEAD. That runs only when the seat check's `branch:` value is `main` or `master`. Otherwise stop with the plan note untouched and name the branch the main checkout sits on, because the new branch would carry that branch's commits. If a worktree command fails, stop with the plan note untouched and report its error. Then call EnterWorktree with `path` set to `<main>/.claude/worktrees/<name>`. The new branch starts at the default branch, so section 3 skips the merged check.
- Otherwise call EnterWorktree with `name` set to `<name>`. EnterWorktree creates a new branch for the worktree, so section 3 skips the merged check and section 5 records the new branch as the plan's branch.

The worktree commands for the first case:

    ! cd '<main>' && git fetch origin '<branch>'
    ! cd '<main>' && git worktree add '<main>/.claude/worktrees/<name>' '<branch>'

The worktree commands for the second case:

    ! cd '<main>' && git fetch origin '<default>'
    ! cd '<main>' && git worktree add --no-track -b '<branch>' '<main>/.claude/worktrees/<name>' 'origin/<default>'

After the switch, `repoRoot` is the worktree path in every later section, and `repoName` stays the main checkout's basename as section 1 resolved it. Section 5 records the worktree path, so section 1 re-enters it in a later session. Keep the holder lines for sections 6 and 10. The holder keeps the main checkout, so Validation Steps that use the running local stack still test the main checkout's code, and section 5 passes `inWorktree` so the runner defers them.

The install step runs after any worktree entry in this section, through the `test -d` check or any case above, and after a section 1 adoption, and never after a section 1 re-entry of a recorded worktree, because the earlier run installed there. A fresh worktree holds only tracked files, so a repo whose dependencies come from Composer or npm cannot run its tests there until the install runs. When an install step exists, spawn one `toolkit:implementer` that runs `<install>` as its own call with `repoRoot` as the working directory and a ten minute timeout, and returns the exit code and the last forty lines of output. The harness blocks a worktree session's commands whose working directory is the main checkout, so the install never runs from `<main>`. The command is not git, so it runs under every ceiling. On exit 0, keep the line `Worktree install: <install> (exit 0)` for sections 6 and 10. With no install step, keep the line `Worktree install: none`. On any other exit, report those output lines, hand the user the command paste-ready as `! cd <repoRoot> && <install>`, and stop with the plan note untouched. The worktree stays without a `Seat: worktree` line on the note, because section 5 writes that line, so section 1 does not re-enter it on a later run. The next ask enters it through the `test -d` check above, or adopts it through the section 1 unrecorded worktree rule from a session still inside it, and runs the install again. Never build a worktree's environment by hand. No worker or conductor creates a symlink or a copy from the main checkout into the worktree, installs part of a tree, or edits an ignore file to hide one. A worktree whose tests cannot run after the install step is a stop, not a repair.

## 3. Tree state

Before any status change, spawn one `toolkit:verifier` that runs `git -c core.quotePath=false status --porcelain -uall` with the section 1 own-worktree pathspec, `git branch --show-current`, `git remote get-url origin`, `git symbolic-ref --short refs/remotes/origin/HEAD`, and, when the section 2a check could not run, `git rev-parse --path-format=absolute --git-common-dir` in `<repoRoot>`. When the symbolic-ref output is `origin/<default>`, the verifier checks `<default>` against the section 1 ref-name pattern and runs neither command below when it fails. When the branch output and `<default>` both match that pattern, it also runs `git merge-base --is-ancestor '<branch>' 'origin/<default>'` and returns its exit code. When `<default>` matches that pattern, it also runs `git show 'origin/<default>:REVIEW.md'` and returns the file verbatim only when that command exits 0. Any other exit returns `absent` with the error text for the report, never as the review rules. It never reads the working tree copy of `REVIEW.md`. It runs no other command and returns each output verbatim, with the error text for a command that fails. Keep the branch and the remote URL for the report. The remote URL feeds the `Repo:` header line. Before recording the remote URL on the plan note or building the `Repo:` line from it, remove any user or token segment, the text between `://` and an `@` in a URL with a scheme together with that `@`, keep the `git@` user of an ssh form, and never print the raw URL. If the repo has no `origin` remote, the `Repo:` line names `repoRoot`.

Check the branch first, as the git-safety Branch check section says. An empty branch output means a detached HEAD. A branch output that fails the section 1 ref-name pattern stops the flow before any status change, and the report names it. When `git remote get-url origin` fails, the repo has no origin remote: skip the merged check, and stop before any status change only on `main`, `master`, or a detached HEAD. When the remote exists, the default branch is the part of the symbolic-ref output after `origin/`, never a guessed name. A default branch that fails the section 1 ref-name pattern stops the flow before any status change, and the report names it. If the remote exists and the symbolic-ref command fails, stop before any status change and hand the user this command, because it writes a ref, then tell the user to ask for the execute flow again:

    ! cd '<repoRoot>' && git remote set-head origin --auto

If the branch is `main`, `master`, or the default branch, or if HEAD is detached, stop before any status change. After any worktree entry, `<repoRoot>` is the worktree, so the branch output is the worktree's branch, and section 5 records it. When section 2a called EnterWorktree with `name`, the branch is the one EnterWorktree just created, and when its second case cut the plan's branch, the branch starts at the default branch, so in both cases skip the merged check. If the merged check exits 0, the branch tip is already in the default branch, or the branch is new with no commits of its own. Stop before any status change as merged when the note's `mr` frontmatter is set, and continue as a fresh branch when it is blank. The execute flow mutates git under no condition apart from the section 2a worktree and the section 11 seat run, so on a stop at the branch check or as merged hand the user the branch command to run, with the plan note's `branch` value as the name once it passes the section 1 ref-name rule, or `feat/<planName>` when that value is blank:

    ! cd '<repoRoot>' && git switch -c '<branch>'

Then tell the user to ask for the execute flow again on the new branch.

When `<branch>` is not blank and the run stays in the main checkout, because neither section 1 nor section 2a entered, re-entered, or adopted a worktree in this run, a branch output that differs from `<branch>` stops the run before any status change. The report names both branches, hands the user this command, and tells the user to ask for the execute flow again:

    ! cd '<repoRoot>' && git switch '<branch>'

Worktree runs keep the section 5 rule that sets the `branch` key to the section 3 branch. That covers a worktree that section 1 or section 2a adopts, a section 2a `test -d` re-entry after a failed install, a section 1 re-entry of a recorded worktree, and a session started with `claude --worktree`.

Take the paths from the status output: on each line, the text after the two status characters and the one space that follows them, with the surrounding double quotes removed from a quoted name that holds no backslash, and both paths of a rename. Git quotes such a name for a space alone, and the capture lists it unquoted. A name git still quotes and escapes, one containing a backslash, a double quote, or a control character, is compared verbatim on both sides, quotes and escapes included, because the capture lists paths with the same quoting. Split a rename at the ` -> ` that sits outside double quotes. A name that contains ` -> ` holds a space, so git quotes it, and the separator is the only ` -> ` outside quotes. The `-uall` flag lists each untracked file, so an untracked directory never collapses to one `dir/` entry. The own-worktree pathspec keeps a linked worktree out of the status, so it never reaches these rules. The rerun check below, sections 2a and 6, and section 11 take paths by the same rules.

On a resume, skip the tree check, because the tree holds the run's own changes. If the status output is empty, continue. On a rerun from `status: in-progress`, which is the section 1 `execute-flow blocked:` bullet or the `execute-flow run started` bullet under another session id, read every `Changed path:` line the plan note holds under Plan Changes During Execution, from every earlier run. A path from the status output is recorded when it equals a recorded path, both sides being the same porcelain form. If every path is recorded, the tree holds the slice: continue, and carry the recorded paths and the latest `Baseline:` line that is not `none` to section 5. Otherwise stop with the plan note untouched, and tell the user to commit or discard the unrecorded paths before asking for the execute flow again. A note with no `Changed path:` line records nothing, so every dirty path is unrecorded. On a run from `status: approved` or from a `start-work:` entry, a status that holds a path stops the flow with the plan note untouched, and the report names the paths and tells the user to commit or discard them before asking for the execute flow again.

## Boundary

The conductor never edits repo files, never mutates git state apart from EnterWorktree as section 2a defines, runs the section 11 switches, fix commit, and restore only through implementers, writes only the vault note, the proposal copies, and scratchpad files, and never sets `status: completed`. The flow never builds a worktree's environment by hand, and it stops when the section 2a install step fails. Repo writes and git mutations come only from workers. Not for a plan note that section 1 does not accept (`plan-guide` owns that) and not for a standalone review of an uncommitted slice (`red-team` owns that). A clean run never marks the plan complete. The human approval rule in `plan-guide` still governs: the flow runs only on a note that section 1 accepts and on the user's ask, and completion stays the user's word.
