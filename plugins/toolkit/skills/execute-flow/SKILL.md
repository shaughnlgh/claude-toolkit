# Execute Flow

Execute-flow is the conductor side of the `execute-runner` workflow, shipped with this plugin at `../../workflows/execute-runner.js` relative to this skill's base directory. The script runs a baseline check, one implementer per Implementation Step in order, the plan's Validation Steps with one fix round, a diff capture, the `review-mr` child workflow as the panel, a bounded fix loop, a second capture, a cold read, and, only when nothing blocked, the Doc Update Pass, a final validation, a post-doc capture, and the remember pass. A verified cold-read finding does not block those passes. The conductor asks the git-permission question, checks the tree and the branch, runs recall, moves the plan note to in-progress, launches the script, records the result, runs the consent gate, adjudicates the unreproduced panel findings, the reproduced panel findings the fix rounds left open, and the verified cold-read findings with the user, writes the slice marker, and closes with the report. The script writes no vault note and runs no mutating git command. The conductor writes only the vault note and scratchpad files.

## 1. Trigger

Fire only when the user asks for the execute flow by name. Asking for "the execute workflow" counts as asking by name. A `crawl` route never fires this skill. If the slice is already under `execution-guide` by hand, do not fire. When the installed plugin does not carry this skill, the conductor reads `plugins/toolkit/skills/execute-flow/SKILL.md` from the toolkit checkout by path and follows it as written.

The plan note must exist. `planName` is its `plan` frontmatter value. Read its `status` and the summary of its last `sessions` entry, then pick the run:

- `status: approved` starts a fresh run.
- `status: in-progress` starts a fresh run, exactly as `status: approved` does, when the `approved` frontmatter key is set and the last `sessions` entry's summary begins `start-work:`. Mission Control's start-work action appends that entry when it moves an approved note to in-progress. A hand-run execution or any later session appends an entry after it, so this rule no longer matches. Section 5 then appends its own `execute-flow run started` entry.
- `status: in-progress` with a last entry summary that begins `execute-flow blocked:` starts a fresh run. A blocked run keeps the note at in-progress, so this is how the user reruns the slice after settling the blocked reasons. Section 3 continues a rerun over the paths the blocked run recorded and refuses any other dirty path.
- `status: in-progress` with a last entry summary that begins `execute-flow adjudicating:` resumes at section 8 from the findings, hashes, and report inputs that sections 6 and 7 recorded on the note, with no new run and no recall. Section 8 checks the tree by capture before it asks. Sections 2 to 7 do not run, except the section 2a check, which asks no question, and sections 8 to 10 read the run's result from the note. The `<scratchpad>/execute-flow-<planName>.runid` file still names the run for the marker. If that file is gone, section 9 skips the marker and the report says so.
- `status: in-progress` with a last entry summary of `execute-flow run started` under another session id starts a fresh run, because that run died before section 6 or section 7 recorded its outcome.
- `status: in-progress` with a last entry summary of `execute-flow run started` under this session's id resumes that run with `resumeFromRunId` when `<scratchpad>/execute-flow-<planName>.runid` exists, and completed agents replay from cache. Section 5 writes that file only after the Workflow tool returned a `runId` and deletes it before each fresh launch, so it always names the latest run. Without that file, the launch never happened, so it starts a fresh run.

If the note matches none of these, state the status and stop.

Before section 2, take the last line under Plan Changes During Execution that begins `Seat: worktree `, if the note has one. Its path is the text after that prefix, up to the first `, holder` when the line carries one. If the session already runs in that path, this section counts the worktree as entered: `repoRoot` is that path, and section 2a asks no seat question. If the session does not already run in that path and `test -d <path>` succeeds, call EnterWorktree with `path` set to it, because an earlier run of this plan ran there and left its changes there. If the directory is gone or EnterWorktree fails, stop with the plan note untouched, and report the error and the recorded path. Never resume or rerun from the main checkout, because a resumed workflow keeps the worktree as its `repoRoot`.

`repoRoot` is the absolute path of the checkout that the plan note's `repo` frontmatter names, or the worktree path once this section or section 2a enters a worktree. `repoName` is the basename of the main checkout, the parent of the directory that `git rev-parse --git-common-dir` names when that directory is called `.git`, never the basename of `repoRoot`, so a run from a linked worktree recalls and reports under the main checkout's name. The `main:` line that section 2a prints names the main checkout. When the seat check could not run, take it from the `git rev-parse --path-format=absolute --git-common-dir` output that section 3 returns. If the session does not know that path, ask the user for it. `<plugin-root>` is the installed plugin root, resolved with `jq -r '.plugins["toolkit@shaughn-toolkit"][0].installPath' ~/.claude/plugins/installed_plugins.json`.

## 2. Git permission

Before anything else, check `<scratchpad>/flow-git-permission`. If the file exists, an earlier flow in this session recorded the answer, so read it and do not ask. If the file does not exist, this flow is the first in the session, so ask once through AskUserQuestion: "Do I have permission to run git commands on your behalf for every flow in this session?" with the options in this order:

1. "No, suggest only (Recommended for a work repo)", with the description "Every flow in this session suggests git commands and runs none.", writes `none`.
2. "Yes, commit, branch, push and open the MR or PR, never merge", with the description "Covers every flow in this session, including a later flow in this session that runs git, without asking again.", writes `push`.
3. "Yes, through merge and tag", with the description "Covers every flow in this session, including a later flow in this session that runs git, without asking again.", writes `release`.

Write the answer to `<scratchpad>/flow-git-permission` as `none`, `push`, or `release`. A missing, empty, or unrecognised file reads as `none`, so until the question is answered no flow has git permission. The answer holds for every flow run in this session, so a later flow in the same session reads the file and never re-asks. The execute flow never mutates git state under any answer, apart from the section 2a worktree. The user's Open a worktree answer is explicit consent, so EnterWorktree runs under every answer, `none` included, while the section 2a worktree commands run only under `push` or `release`. Apart from those commands, its agents run only read-only git in the repo. The `## Flows` section of the git-safety doctrine (`../../doctrine/git-safety.md` from this skill's base directory) defines what each answer unlocks.

## 2a. Seat

The seat is the main checkout, which a running local stack serves. Run `bash <plugin-root>/scripts/seat-check.sh <repoRoot> --self <session id>` directly, as section 4 runs recall, with the session id taken from the scratchpad path. Pass `repoRoot` as given, because the harness refuses a command whose text names `git` from a worktree session. The script reads `claude agents --json` and prints `seat: free` or `seat: held`, then the `main:`, `branch:`, and `dirty:` lines, then one tab-separated `holder: <name> <status> <kind> <sessionId> <cwd>` line per holder. Keep the output for sections 6 and 10. Exit 2 means the check could not run: say so in the report and continue as if the seat were free. On a resume, and after section 1 entered a recorded worktree, the check still runs, because the report names the holders, and no question is asked.

When the check printed `seat: held` on a fresh run, a rerun included, and section 1 entered no worktree, ask once through AskUserQuestion: "Session <name> (<status>) also sits in <main>, on <branch> with <N> dirty paths. Open a worktree, take the seat, or hold?" With more than one holder, the question carries one such holder sentence per holder before "Open a worktree, take the seat, or hold?". The options are:

- "Open a worktree", with the description "Creates a worktree under .claude/worktrees/ on the plan's branch, or on a new branch when the plan's branch does not exist yet, switches this session into it, and runs the flow there. The holder keeps the main checkout. Validation steps that use the running local stack still test the main checkout's code."
- "Take the seat", with the description "The run proceeds and the report names the holder. A holder that wakes and switches the branch stops the run."
- "Hold", with the description "Stops with the plan note untouched. Finish or pause that session, then ask for the execute flow again."

Open a worktree comes first with " (Recommended)" appended. If any holder's status is `busy`, Hold comes second and Take the seat comes third. Otherwise Take the seat comes second and Hold comes third. On Hold, stop with the plan note untouched. On Take the seat, continue and keep the holder lines.

On Open a worktree, the user's answer is the explicit worktree request that Claude Code's EnterWorktree tool requires, so EnterWorktree runs under every git permission, `none` included. `<branch>` is the plan note's `branch` frontmatter value, and the worktree name `<name>` is `<branch>`, or `<planName>` when that value is blank. Spawn one `toolkit:verifier` that runs `git worktree list --porcelain` in `<main>` and, when `<branch>` is not blank, `git branch --list <branch>` and `git ls-remote --heads origin <branch>` there, and returns each output verbatim. Then take the first case that applies:

- If a `worktree` line in the list names `<main>/.claude/worktrees/<name>`, call EnterWorktree with `path` set to that directory.
- If either branch output is not empty, the plan's branch exists. If a `branch refs/heads/<branch>` line in the list sits under another worktree, git refuses a second checkout of the branch, so go straight to the fallback question below. EnterWorktree with `name` would create a new branch instead, so obtain the worktree with the commands below, then call EnterWorktree with `path` set to `<main>/.claude/worktrees/<name>`. The fetch line applies only when `git branch --list` printed nothing, so the add creates the local branch from `origin/<branch>`. Under git permission `none`, hand the user the commands paste-ready and wait until the user says they ran. Under `push` or `release`, spawn one `toolkit:implementer` that runs only these commands in `<main>`, each as its own call, and returns each output.
- Otherwise call EnterWorktree with `name` set to `<name>`. EnterWorktree creates a new branch for the worktree, so section 3 skips the merged check and section 5 records the new branch as the plan's branch.

The worktree commands for the second case:

    ! cd <main> && git fetch origin <branch>
    ! cd <main> && git worktree add <main>/.claude/worktrees/<name> <branch>

After the switch, `repoRoot` is the worktree path in every later section, and `repoName` stays the main checkout's basename as section 1 resolved it. Section 5 records the worktree path, so section 1 re-enters it in a later session. Keep the holder lines for sections 6 and 10. If EnterWorktree or a worktree command fails, report its error and ask the seat question once more with only Take the seat and Hold, ordered by the busy rule above, with " (Recommended)" appended to the first of the two.

## 3. Tree state

Before any status change, spawn one `toolkit:verifier` that runs `git -c core.quotePath=false status --porcelain -uall`, `git branch --show-current`, `git remote get-url origin`, `git symbolic-ref --short refs/remotes/origin/HEAD`, and, when the section 2a check could not run, `git rev-parse --path-format=absolute --git-common-dir` in `<repoRoot>`. When the branch output is not empty and the symbolic-ref output is `origin/<default>`, it also runs `git merge-base --is-ancestor <branch> origin/<default>` and returns its exit code. When the symbolic-ref output is `origin/<default>`, it also runs `git show origin/<default>:REVIEW.md` and returns the file verbatim only when that command exits 0. Any other exit returns `absent` with the error text for the report, never as the review rules. It never reads the working tree copy of `REVIEW.md`. It runs no other command and returns each output verbatim, with the error text for a command that fails. Keep the branch and the remote URL for the report. The remote URL feeds the `Repo:` header line. Before recording the remote URL on the plan note or building the `Repo:` line from it, remove any user or token segment, the text between `://` and an `@` in a URL with a scheme together with that `@`, keep the `git@` user of an ssh form, and never print the raw URL. If the repo has no `origin` remote, the `Repo:` line names `repoRoot`.

Check the branch first, as the git-safety Branch check section says. The default branch is the part of the symbolic-ref output after `origin/`, never a guessed name. If the symbolic-ref command fails, ask the user for the default branch name and skip the merged check. An empty branch output means a detached HEAD. If the branch is `main`, `master`, or the default branch, or if HEAD is detached, stop before any status change. After any worktree entry, `<repoRoot>` is the worktree, so the branch output is the worktree's branch, and section 5 records it. When section 2a called EnterWorktree with `name`, the branch is the one EnterWorktree just created, so skip the merged check. If the merged check exits 0, the branch tip is already in the default branch. A branch the user has just cut and not yet committed on gives the same exit code, so ask once through AskUserQuestion: "Branch <branch> has no commits beyond origin/<default>. Is it merged work, or a fresh branch for this slice?" with the options "Merged, stop (Recommended)" and "Fresh branch for this slice, continue". On Merged, stop before any status change. The execute flow mutates git under no answer apart from the section 2a worktree, so on every stop hand the user the branch command to run, with the plan note's `branch` value as the name, or `feat/<planName>` when that value is blank:

    ! cd <repoRoot> && git switch -c <branch>

Then tell the user to ask for the execute flow again on the new branch.

On a resume, skip the dirty-tree question, because the tree holds the run's own changes. If the status output is empty, continue. If it is not empty, take the foreign paths from it: on each line, the text after the two status characters and the one space that follows them, with the surrounding double quotes removed from a quoted name that holds no backslash, and both paths of a rename. Git quotes such a name for a space alone, and the capture lists it unquoted. A name git still quotes and escapes, one containing a backslash, a double quote, or a control character, is compared verbatim on both sides, quotes and escapes included, because the capture lists paths with the same quoting. Split a rename at the ` -> ` that sits outside double quotes. A name that contains ` -> ` holds a space, so git quotes it, and the separator is the only ` -> ` outside quotes. The `-uall` flag lists each untracked file, so an untracked directory never collapses to one `dir/` entry. On a rerun from `status: in-progress`, which is the section 1 `execute-flow blocked:` bullet or the `execute-flow run started` bullet under another session id, read every `Changed path:` line the plan note holds under Plan Changes During Execution, from every earlier run. A path from the status output, after the rules above, is recorded when it equals a recorded path, both sides being the same porcelain form. If every path is recorded, the tree holds the slice: continue with no question, treat no path as foreign, and carry the recorded paths and the latest `Baseline:` line that is not `none` to section 5. Otherwise offer no Proceed: stop with the plan note untouched, and tell the user to commit or discard the unrecorded paths before asking for the execute flow again. A note with no `Changed path:` line records nothing, so every dirty path is unrecorded. The section 1 bullet for a last entry that begins `start-work:` is no rerun, so it takes the question below as a run from `status: approved` does. Otherwise ask once through AskUserQuestion: "The tree holds changes that are not this slice: <paths>. Hold the run, or proceed and leave them out of the staging list?" with the options in this order:

1. "Hold (Recommended)", with the description "Workers are guarded by prompt text only, so the run would expose these changes to them. Settle the changes yourself, then ask for the execute flow again."
2. "Proceed, the foreign paths are named in the report and left out of the staging list", with the description "The diff captures the whole tree, so the panel and the cold read review these paths with the slice. The report names them and never stages them."

If the answer is Hold, stop with the plan note untouched. If the answer is Proceed, keep the foreign paths for section 10.

## 4. Recall

Before any status change, run recall as `plan-flow` section 3 describes (`../plan-flow/SKILL.md` from this skill's base directory), with each key term from the plan name and the Objective passed as its own quoted argument: `python3 <plugin-root>/scripts/topic-recall.py --repo <repoName> --repo-root <repoRoot> "<term one>" "<term two>"`. Read the exit code as that section says. On `0`, pass the output as `recallHits`, or `none` when the output is empty. On `2` or `3`, stop with the plan note untouched and report the exit code and stderr.

## 5. Status and launch

Before launch, count the steps the way the script parses them. The Implementation Steps section runs from its section heading to the next section heading outside a fence. A section heading is a line outside a fence that starts with `##` followed by a space or tab, and it names a section when the text after `##`, trimmed, equals the section name. A `###` line is not a section heading. A fence opens on a line of 3 or more backticks or tildes with an optional info string, and it closes only on a line of the same character at least as long with nothing else on it. A numbered line is a line outside a fence that opens with a number followed by `.` or `)` and a space. A subheading is a line outside a fence that starts with `###` followed by a space or tab. The numbered lines form a single list when their numbers, in order, run 1, 2, 3 with no restart and no gap. Inside Implementation Steps, the first of three rules that applies splits the steps. First, if at least one subheading starts with a number followed by `.` or `)` after `###`, those numbered subheadings split the steps and every other line stays inside its step. Second, every subheading starts a step, and its heading is the text after `###`, when all of these hold: the section has at least two subheadings and none of them is numbered, no numbered line comes before the first subheading, and the numbered lines do not form a single list that runs across a subheading. A single list that sits entirely under one subheading, a section with no numbered lines, and numbered lines that restart or skip a number all meet the last condition. Third, otherwise a numbered line starts a step when its number is greater than every number before it, so a list that restarts at 1, such as a Tripwires list under its own subheading, stays inside the step before it. Text before the first step joins step 1. A section with no step marker is one step for one implementer. Tell the user the step count, the first line of each step, and that a permission prompt pauses the run until the user answers it.

On a fresh run, first delete any `<scratchpad>/execute-flow-<planName>.runid` left by an earlier run, so a later resume can only pick up the latest run. Move the status only when the launch is about to happen. Load `plan-guide`. On a fresh run, set `status: in-progress` if the note is not already there, and record this session's entry per its session rules with the summary `execute-flow run started`, with the id taken from the scratchpad path. If section 2a opened a worktree, add the line `Seat: worktree <path>` under Plan Changes During Execution in the same write, so section 1 re-enters the worktree in a later session. If section 1 or section 2a entered a worktree and the section 3 branch differs from the `branch` frontmatter, also set that key to the section 3 branch in the same write, so the commit handoff, the ship flow, and the key name the branch the worktree carries. On a resume, leave the status and the entry as they are. Write the change atomically: Write the note to a `.tmp.md` file beside it, then move it into place with `vault-fs.sh mv`. Then run `python3 <plugin-root>/scripts/validate-plan.py "<plan note path>"` and require exit 0. If the validator fails, report its output and stop. Never patch a failure silently.

Build the args:

- `planName`: from section 1.
- `repoRoot` and `repoName`: from section 1.
- `planContent`: the full text of the plan note as the status change wrote it.
- `recallHits`: from section 4.
- `scratchDir`: the absolute scratchpad path.
- `pluginRoot`: `<plugin-root>` from section 1.
- `vaultRoot`: `<vault_path>/<root_folder>`, both read from `~/.claude/obsidian-sync.json`.
- `knownEvidence` (optional): facts this session already verified, each with its file:line. On a rerun that section 3 continued over recorded paths, add one line: "An earlier blocked run of this plan left its changes in the tree at the paths under ALREADY CHANGED. These paths are part of this slice, for every step and for the doc pass. Read them before redoing a step."
- `verifyCommand` (optional): the repo's verify or test command, when the session knows it. Without it, the baseline verifier finds the command itself.
- `priorChangedPaths` (optional): on a rerun that section 3 continued, the recorded paths it carried, as a list. The runner seeds its changed list with them, so every implementer prompt lists them under `ALREADY CHANGED`, the doc pass sees them under `CHANGED PATHS`, and `changedPaths` returns them. Omit it on any other run.
- `baselineFailing` (optional): on a rerun that section 3 continued, the failing names from the latest `Baseline:` line that is not `none`, as a list, or an empty list when that line says `failing none`. When no earlier run recorded a `Baseline:` line other than `none`, pass an empty list, so every failing check blocks, and say in the section 10 report that no clean baseline was recorded. The runner shows this list to the validation verifier as the baseline failing list, so a check the blocked run broke is not marked pre-existing. Omit it on any other run.
- `maxFixRounds` (optional): the fix rounds after the panel, a non-negative integer, default 1.
- `reviewRules` (optional): the `REVIEW.md` text that section 3 returned, verbatim. Omit it when section 3 returned `absent`.
- `reviewMr` (optional): `{scriptPath: "<repoRoot>/plugins/toolkit/workflows/review-mr.js"}` when `repoRoot` contains that file, the rule `red-team` step 4 uses, so the toolkit repo's own flow runs its working-tree review-mr. Omit it otherwise. If the result's `blocked` carries `The review-mr child workflow failed:` naming that ref, report it and tell the user to rerun without `reviewMr`.

When `repoRoot` contains `plugins/toolkit/workflows/execute-runner.js`, launch `{scriptPath: "<repoRoot>/plugins/toolkit/workflows/execute-runner.js"}`, otherwise `{name: "toolkit:execute-runner"}` with the `scriptPath` fallback `red-team` uses. That fallback is `{scriptPath: "<this skill's base directory>/../../workflows/execute-runner.js"}` resolved to an absolute path, used if name resolution fails. The script is named `execute-runner` because a workflow and a skill cannot share a name in the plugin registry. If the Workflow tool refuses the `scriptPath` as outside the working directory, copy the script byte-identical to `<scratchpad>/execute-runner.js`, take the first 12 characters of `shasum -a 256` for the source and for the copy, require the two to match, and launch `{scriptPath: "<scratchpad>/execute-runner.js"}`.

Write `<scratchpad>/execute-flow-<planName>.runid` only after the Workflow tool has returned a `runId`, and at once, before reading the result. It holds the `runId`, the script path, and the two sha256 prefixes when the copy rule applied. A dead run resumes with `resumeFromRunId` and the script path from that file. Completed agents return cached, so never relaunch a fresh run when a resume is possible.

The result is `{baseline, steps, validation, review, coldResidual, coldUnverified, docPass, remember, changedPaths, planChanges, diffHashes, diffPaths, diffFiles, blocked, incomplete}`:

- `steps` holds one entry per Implementation Step implementer that returned, each with `changedPaths`, `deviations`, `checksRun`, `result`, `blockers`, and `topicMaterial`.
- `validation` is `{results, runs, allPass, manualChecks, preExisting}`. It is null when the build stopped before `verify:validation` returned, including when that verifier died. When the run stopped after it returned, it holds the latest results. For a plan with no Validation Steps, it is `{results: [], runs: 0, allPass: false, manualChecks: [], preExisting: []}`, and `blocked` carries the no-Validation-Steps sentence.
- `review` is `{panel, panelRule, dimensions, dead, verifierDead, confirmed, nits, preExisting, fixed, open, refuted, unverified, dropped, openQuestions, rounds}`, or null when the child workflow did not run or did not return. Every finding carries `tag`, `finalTag`, `score`, `finalScore`, `reproduction`, and `citation`, except a `dropped` entry with reason `no citation`, which never reached the verifier. `open` holds the findings the fix round left unresolved, each with its `bucket`, `confirmed` or `nit`. `panelRule` names the rule that chose the panel: `docs only`, `high-risk path`, or `standing`. `dead` lists the reviewer names and dimension keys that died, `verifierDead` lists the dimensions whose verifier died by the same names, and the script blocks when either is not empty. Each `unverified` entry carries a `reason` of `no verdict`, `not reproduced`, or `verifier died`. `nits` holds the nits whether or not a fix round ran.
- `coldResidual` lists the cold read's verified findings that carry a citation, each with `title`, `tag`, `score`, and `citation`, and `coldUnverified` lists the rest of the cold read's findings. Both are null when the cold read did not run or returned nothing.
- `docPass` is the Doc Update Pass return, or null when it did not run, including when the slice was already blocked.
- `remember` is `{ran, material, proposals, topicsUpdated, rememberLine}`.
- `diffHashes` and `diffPaths` are `{redTeam, final, postDoc}`, with null for a capture that failed or did not run. `diffFiles` has the same keys, each the repo-relative paths that capture holds, or null.
- `blocked` lists one plain sentence per reason the slice is not done, and is empty when nothing blocks.
- `incomplete` lists the labels of the stages that died.

A run is blocked when `blocked` or `incomplete` is not empty.

The adjudication list is every `review.unverified` entry, then every `review.open` entry with bucket `confirmed`, then every `coldResidual` entry, in that order. A null `review` or `coldResidual` adds no entry. An entry on the adjudication list is settled when the plan note records it as fixed, wrong, intentional, or did not matter. An adjudication list entry is never a blocked reason.

## 6. Record

Record the result under the plan note's Plan Changes During Execution, one line each:

- every `planChanges` line, including the fix-round lines.
- every `blocked` reason, every `incomplete` label, and every step blocker from `steps`. A validation result count that differs from the plan's Validation Steps count arrives as a `blocked` reason, so it is recorded here.
- on a blocked run, the run's own paths: spawn one `toolkit:verifier` that runs `git -c core.quotePath=false status --porcelain -uall` in `<repoRoot>` and returns the output verbatim, take each path with the section 3 rules, remove every path that equals a section 3 foreign path or starts with one that ends in `/`, and write each remaining path as its own line in the form `Changed path: <path>`. The record comes from the tree, not from `changedPaths`, so it holds a dead implementer's partial edits and never a foreign path. If that verifier returns nothing, write no `Changed path:` line and say in the section 10 report that the next rerun will refuse the dirty tree.
- on a blocked run, one line in the form `Baseline: <baseline.verify.command> exit <baseline.verify.exitCode>, failing <names separated by commas, or none>`, or `Baseline: none` when `baseline` is null, so section 5 can pass the failing names to a rerun as `baselineFailing`.
- every `validation.manualChecks` entry, under a line that reads "Manual checks for you".
- every `validation.preExisting` entry.
- the `review.panel` and the `review.panelRule` that chose it.

## Boundary

The conductor never edits repo files, never mutates git state apart from the section 2a EnterWorktree call that the user's Open a worktree answer consents to, and never sets `status: completed`. Repo writes come only from the script's workers, from the implementer that the consent gate delegates, and from the section 8 fix implementer. Not for a plan note that section 1 does not accept (`plan-guide` owns that) and not for a standalone review of an uncommitted slice (`red-team` owns that). A clean run never marks the plan complete. The human approval rule in `plan-guide` still governs: the flow runs only on a note that section 1 accepts and on the user's ask, and completion stays the user's word.
