# Ship Flow

Ship-flow is the conductor side of the `ship-runner` workflow, shipped with this plugin at `<plugin-root>/workflows/ship-runner.js`. The script runs Prep, then Commit, Push, MR, the pipeline watch with its fix loop, the bot review threads, Merge, Release, and Cleanup, each up to the ceiling, and every git and host mutation runs inside its agents under a per-stage rule. The conductor reads the run options, reads the host and the tree through one verifier, plus a capture verifier before a commit, reads the staging list, prints the preview, launches the script, records the result on the plan note, starts the background watcher and relaunches the script when a run stopped only to wait, and closes with the report. The conductor writes only the vault note and scratchpad files.

## 1. Trigger

Fire only when the user asks for the ship flow by name, when a worker session's first prompt names the ship flow on this plan note, or on a continue message that the worker grant rule in execute-flow section 1 accepts with the first line `<planName>: run the ship flow`. When the first prompt names a lead, that name is `<lead>`, and section 9 reports to it. In a worker session, an auto mode refusal of a commit, push, MR or merge that the ceiling allows asks nobody to approve it. The run stops at that stage, and the report carries a blocked reason that names the denied command and its reason category, so the lead runs the ship flow itself. A `crawl` route never fires this skill. When the installed plugin does not carry this skill, the conductor reads `plugins/toolkit/skills/ship-flow/SKILL.md` from the toolkit checkout by path and follows it as written. When the conductor follows a ship-flow skill file read by path from inside the plan's worktree, it copies that file byte-identical to `<scratchpad>/ship-flow-SKILL.md` before section 7 launches, takes the first 12 characters of `shasum -a 256` for the source and the copy, requires the two to match, and follows the copy from then on, because the runner's cleanup removes the worktree before sections 8 and 9 run.

The plan note must exist. `planName` is its `plan` frontmatter value. `repoRoot` and `repoName` come from the note's `repo` frontmatter as execute-flow section 1 derives them (`<plugin-root>/skills/execute-flow/SKILL.md`). `<plugin-root>` is `../..` from this skill's base directory, the directory that holds this SKILL.md, resolved to an absolute path, so a `--plugin-dir` session runs the loaded copy's scripts. This root takes precedence over a CLAUDE.md line that resolves the installed root. When `../../.claude-plugin/plugin.json` does not exist relative to this skill's base directory, as in a `/toolkit:override` copy under `~/.claude/skills/`, the plugin root is the installed root instead, the path that `jq -r '.plugins["toolkit@shaughn-toolkit"][0].installPath' ~/.claude/plugins/installed_plugins.json` prints, as the setup CLAUDE.md block resolves it. When Plan Changes During Execution holds a `Seat: worktree` line, take the path from the last such line as execute-flow section 1 reads it. Before any command names that path, check it by the execute-flow section 1 seat path rule, and stop with a report that names it when it fails. When `test -d` on that path succeeds, `repoRoot` is that path, because the plan branch is checked out there, and the ship flow calls no EnterWorktree. Stop unless all three hold:

- the note is `status: in-progress`, or `status: completed` for the release-only run below.
- its `branch` value is not blank and that branch exists in the repo, which section 3 confirms, except on the release-only run below, which tags the merge commit alone and so runs after the cleanup deleted the branch.
- the summary of its last `sessions` entry begins `execute-flow finished:`, `seat-run finished:`, `ship-flow stopped:`, or `ship-flow finished:`.

`execute-flow finished:` marks a slice that has not shipped yet. `seat-run finished:` marks a seat run that finished the deferred Validation Steps. `ship-flow stopped:` marks a run that ended below its ceiling or in a handoff. `ship-flow finished:` marks a run that reached its ceiling, which a `ceiling: mr` note sets at mr, so after the user raises the note's ceiling to `merge` a later run ships the same note on to merge. A `status: completed` note goes on only for the release-only run: its PR or MR is merged, its merge commit carries no tag, and the note carries `ceiling: merge` and `tag_merge: true`, which section 3 checks. Section 3 refuses any note whose PR or MR is merged unless the run only tags the merge commit. Any other summary means the slice is not ready to ship. A summary that begins `execute-flow blocked:`, `execute-flow adjudicating:` or `seat-run blocked:`, or reads `execute-flow run started` or `seat-run started`, belongs to the execute flow, so stop and tell the user to finish it there. Any other status or summary: state it and stop. Where a run resumes is derived from observed state in section 3, never typed by the user.

A note whose repo set (`plan-guide` § Repos and modules) holds two or more repos ships by section 3b, which takes the repo set, the projects root check, the roots and `repoRoot` from execute-flow section 2b and the ship order from `plan-guide` § Repos and modules.

## 2. Run options

Before anything else, read the run options per `plan-guide` § Run options (`<plugin-root>/skills/plan-guide/SKILL.md`): from the plan note, which an execute-flow run has already written, then from `<scratchpad>/flow-run-options` for the keys the note lacks when that file's `plan:` line names this plan, then ask only the questions for the keys still missing, and write the cache for this plan. Section 8 records every key the note lacked. The ship flow is the only flow that mutates git, and it does so only under `mr` or `merge`, through the runner's agents. Under `none` it runs Prep only and hands over the commit block. The `## Flows` section of the git-safety doctrine (`<plugin-root>/doctrine/git-safety.md`) defines what each ceiling permits.

## 3. Host, tree and observed state

Before any command names the note's `branch` value, check it by the execute-flow section 1 ref-name rule, and stop with a report that names it when it fails. `<main>` is the checkout that the note's `repo` names. Spawn one `toolkit:verifier` that runs these commands in `<repoRoot>` and nothing else: `git remote get-url origin`, `git symbolic-ref --short refs/remotes/origin/HEAD`, `git branch --show-current`, `git rev-parse HEAD`, `git ls-remote origin 'refs/heads/<branch>'`, `git ls-remote --tags origin`, `git -c core.quotePath=false status --porcelain -uall`, `test -f`, `test -e`, and `git ls-tree`. On GitHub it also runs `gh pr view '<branch>' --json number,url,state,mergeCommit`, and on GitLab `glab mr list --source-branch '<branch>' --all -F json` and `glab api 'projects/:id'`. When the note's `ceiling` is `merge` and section 1 read a `Seat: worktree` path, it also runs `test -d '<worktree>'` and returns its exit code. Section 3 reads no occupants, because the runner's `cleanup:state` reads them at cleanup time. It lists the `.yml` and `.yaml` files under `.github/workflows/` with `find .github/workflows -maxdepth 1 -name '*.yml' -o -name '*.yaml'` and never a shell glob, because zsh aborts a command whose glob matches nothing. It greps only the listed files, plus `.gitlab-ci.yml` when that file exists, for `tags` and `CI_COMMIT_TAG`. A missing directory, no listed file, or no match reads as no tag trigger. The CI paths are `.gitlab-ci.yml`, `.gitlab`, `.circleci`, `Jenkinsfile`, `.travis.yml`, `azure-pipelines.yml`, `appveyor.yml`, `.appveyor.yml`, `.buildkite`, `.drone.yml` and `bitbucket-pipelines.yml`. It runs `test -e` on each CI path and returns each exit code. It runs `git ls-tree --name-only refs/remotes/origin/HEAD -- .github/workflows` followed by every CI path, which reads the default branch, because the slice can delete a CI file. On GitLab it returns the `ci_config_path` value from the `glab api 'projects/:id'` output, because a project can name a CI file at another path or in another project. It also reads the step commands in the same files: each `run:` value in the GitHub workflow files, including every indented line of a `run: |` or `run: >` block, and each line of the `script:`, `before_script:` and `after_script:` entries in `.gitlab-ci.yml`, including the list items on the lines below the key. It runs `test -f` on each repo-relative path a step command runs as a file, with any leading `./` removed, and returns `ciScripts` as the paths where `test -f` succeeds, such as `verify.sh` from `run: bash ./verify.sh`. It returns each output verbatim, with the error text for a command that fails. A PR or MR lookup that finds nothing is not a failure. `<branch>` is the plan note's `branch` value.

Read the outputs:

- Host is `github` for a `github.com` remote URL, else `gitlab`.
- `noCiConfig` is true only when the `.github/workflows/` listing holds no file, each `test -e` exited non-zero, the `git ls-tree` read exited 0 and printed nothing, and on GitLab the `ci_config_path` value is empty or null, because neither the slice nor the default branch then carries CI configuration. A missing `.github/workflows` directory, which makes the `find` fail, counts as a listing with no file, as it does for the tag trigger above. Any other read, such as another `find` error, gives false.
- Before building `remotePath` or the `Repo:` header line, strip any user or token segment from the remote URL: in a URL with a scheme, the text between `://` and an `@`, with that `@`. In an ssh form such as `git@host:owner/repo.git`, the text before the `@`, with that `@`. Never print the raw remote URL.
- The `Repo:` header line is the stripped URL with the scheme and `.git` removed, and the scp `:` turned into `/`. `remotePath` is that line without its leading host segment, such as `owner/repo` or `group/sub/repo`, because the runner builds the API paths from it.
- The default branch is the symbolic-ref output after `origin/`. If the command fails, stop before any stage runs, hand the user `! cd '<repoRoot>' && git remote set-head origin --auto`, because it writes a ref, and tell the user to ask for the ship flow again. A default branch that fails the `^[A-Za-z0-9._/-]+$` pattern of the execute-flow section 1 ref-name rule stops the run with a report that names it, before any stage receives it.
- If the current branch differs from the note's `branch`, HEAD is detached, or the branch is `main`, `master`, or the default branch, stop and hand the user the switch command: `! cd '<repoRoot>' && git switch '<branch>'`. Skip this check when rule 5 below sets `startAt` to `release`, because the tag stage needs only the merge commit.

Derive `startAt` once section 4 has the staging list, for every summary prefix section 1 accepts. The rules are exclusive and ordered, and the first match wins:

1. When a staging-list path is dirty in the status output, `startAt` is `commit`.
2. Else, when the `ls-remote` sha for `origin/<branch>` differs from HEAD or is absent, `startAt` is `push`. When the remote branch is gone (`ls-remote` prints nothing for it) and a merged PR or MR exists, rule 5 applies before this rule, so a merged slice whose branch the host deleted does not start at push.
3. Else, when no PR or MR for the branch is open or merged, `startAt` is `mr`.
4. Else, when a PR or MR for the branch is open, `startAt` is `merge`.
5. Else the PR or MR is merged. `mergedSha` is its merge commit: `mergeCommit.oid` from `gh pr view` on GitHub, and on GitLab `merge_commit_sha`, else `squash_commit_sha`, else `sha`. When the note carries `ceiling: merge` and `tag_merge: true` and no `git ls-remote --tags origin` line carries `mergedSha`, `startAt` is `release`. Otherwise stop and say that the slice is already merged, with the merge commit.

A `status: completed` note goes on only when rule 5 sets `startAt` to `release`. Any other rule stops it, and the conductor states the status.

For `merge` and `release`, keep the PR or MR `url` and `number` (the iid on GitLab) as `mr`.

`recordedSha` is the commit sha the plan note records under Plan Changes During Execution from an earlier ship-flow run, or an empty string.

The latest remote `vX.Y.Z` tag from `git ls-remote --tags origin` feeds the release suggestion: `tagName` is that tag with its patch number raised by one, or `v0.1.0` when no such tag exists, and `tagMessage` is the first line of the commit message. When the grep finds a tag trigger, keep the file and line for the preview with the sentence "A tag push starts the job at <file>:<line>."

## 3b. Several repos

A note whose repo set holds two or more repos ships by these rules. Each repo's name, branch, root and main checkout come from execute-flow section 2b, and each repo's branch stands in for the note's `branch` in sections 1 and 3. Ship order is the `plan-guide` § Repos and modules order.

- The session runs from the projects root and calls no ExitWorktree.
- Section 3 runs once per repo in ship order on that repo's root, so each repo has its own host, `remotePath`, default branch, `noCiConfig`, `ciScripts`, PR or MR and `startAt`. A module's root is its checkout from the `Module checkout:` line. A repo whose PR or MR is already merged takes no run in either pass and counts as merged, in place of the rule 5 stop.
- Section 4 reads the one shipping record, whose hash on such a note is one `<name>=<hash12>` pair per repo. When any repo's `startAt` is `commit`, one verifier runs the capture brief with one ` --repo '<root>'` per root in ship order for `${REPO_FLAGS}`, whatever each repo's `startAt`, ` and parts` for the `parts` clause, and the sentence the `${MULTI ? ...}` clause of `GIT_RULE` holds for that clause, so every part keeps the prefix and the nested excludes it had at review. Each repo whose `startAt` is `commit` compares the `hash12` of the `parts` entry whose `root` is its root with its own pair, and a mismatch stops that ask with the repo named and says that the tree changed since review. A repo past `commit` holds no slice diff and compares nothing, so a re-ask after an ask that died between two repos' commits goes on. A root's prefix is its path relative to `repoRoot` followed by `/`. Each staging path belongs to the root whose prefix is the longest one it starts with, and that repo's `paths` are its paths less the prefix. A repo with no path ships nothing, and under `ceiling: merge` the report hands the removal of its worktree.
- Section 5 runs per repo. The project repo of a note with modules stops at `mr`, because its composer constraint must move to a module release first. The seat cap on such a note lifts only when every `Validation deferred:` step has a later `Validation step accepted:` line.
- Pass 1 opens every PR or MR. Section 7 launches one ship-runner run per repo in ship order at ceiling `mr`, or `none` under a `none` note, with that repo's args: `paths` less the prefix, `knownShas`, `priorFixShas`, `priorCarried` and `recordedSha` read only from lines that carry that repo's `<name>: ` prefix, `carriedFindings` from each `Finding for the PR:` line whose `<file>` belongs to that repo's root by the section 4 longest-prefix rule, with that prefix removed from `file` before the `Carried fix:` match and the runner's `paths` check, `carriedVerify` for that repo's files, and `mergeCheck: true` when the note's ceiling is `merge`. `mrBody` gains the line `Repos in ship order: <name>, <name>`. A repo whose run blocks or hands off does not stop pass 1, because a later repo's PR or MR merges nothing, but it stops pass 2.
- Gate. Pass 2 runs only when the note's ceiling is `merge`, the seat cap and the carried cap do not apply, and every repo either counts as merged or has a last pass-1 result with `mergeReady` true, `blocked` and `incomplete` empty and `handoff` null. Otherwise section 9 reports each repo's `mergeRefusal` or blocked sentences, and nothing merges in this ask.
- Pass 2 merges in ship order. For each repo that merges under this ask, which is every repo apart from a project with modules, run section 3 again, which derives `startAt` `merge`, and launch at ceiling `merge` with that repo's `mr`, no `mergeCheck`, and the budgets pass 1 left. The runner reads the pipeline and the threads again on the head before it merges. `mainRoot` and `worktree` are the repo's main checkout and `<wt>` for a top-level repo, and `<c>` and `<mw>` for a module with an external checkout. For a nested module, `mainRoot` is the module checkout with no `worktree`, so the cleanup deletes a merged module branch there. The next repo launches only after this repo's `merged` is set. When a pass-2 run does not merge, the ask stops. Section 9 then names each repo this ask merged with its merge sha and its PR or MR url, says that each later repo did not merge, and says that when a later repo cannot follow, the user reverts an earlier merge through the Revert action on its PR or MR.
- Section 7b starts each watcher as `cd '<root>' && bash <pluginRoot>/scripts/watch-mr.sh ...`, so `glab` reads that repo's host, and runs one watcher at a time across the repos. A relaunch keeps its pass's ceiling and `mergeCheck`. The fix and thread budgets count per repo across both passes, and the three-watcher cap counts across every repo of the ask.
- Section 8 starts every line it writes with `<name>: `, writes each repo's `mr.url` into its `repos:` or `modules:` entry's `mr` field, and leaves the top-level `mr` blank. The summary is `ship-flow finished: <ceiling>` only when every repo reached its ceiling, else `ship-flow stopped: at <stage> (<name>)` for the first repo below it.
- Section 9 gives one Repo, Branch and Scope header and one result block per repo in ship order. After a project stop at `mr` on a note with modules, it names the next steps: release each merged module, move the project's constraint to that release, push it to the project branch, then merge the project MR by hand.

## 4. Staging list and message

Take the staging list and the commit message from the execute-flow report in this session when one exists. Otherwise read the staging list and the commit message from the shipping record on the plan note, which execute-flow section 7 records on every unblocked run whose capture succeeds and an execute-flow section 8 fix replaces. If neither source has them, stop and say that the slice needs an execute-flow run first.

When `startAt` is `commit` and the note records a shipping record, spawn one `toolkit:verifier` briefed with the `CAPTURE_PROMPT` text from `execute-runner.js` (beside `ship-runner.js`), with `<repoRoot>` for `${a.repoRoot}`, the scratchpad path for `${S}`, `HEAD` for `${DIFF_BASE}`, the plugin root that holds that `execute-runner.js` for `${a.pluginRoot}`, the `GIT_RULE` text from the same file for `${GIT_RULE}`, and nothing for `${REPO_FLAGS}`, for the `parts` clause and for the `${MULTI ? ...}` clause of `GIT_RULE` on a single-repo note, and compare its `hash12` with the shipping record hash. If they differ, stop and say that the tree changed since review and that the slice needs an execute-flow run. After a commit the tree holds no slice diff, so no later `startAt` runs the capture.

`paths` is the staging list. `mrTitle` is the first line of the message. `mrBody` is the rest of the message after its first blank line, followed by a line `Plan: <planName>`.

## 5. Ceiling

The ladder is suggest, commit, push, mr, merge, release. The note's `ceiling` sets where the run stops: `none` stops at suggest, `mr` at mr, `merge` at merge, and `merge` with `tag_merge: true` at release. Say "The ceiling is <ceiling>, so the run stops at <stage>." No question is asked here. The user changes the ceiling by editing the note.

The seat cap applies when the note's `ceiling` is `merge`, Plan Changes During Execution holds a `Validation deferred:` line, and no `Seat run passed:` line after the last such line names the HEAD sha from section 3. Under the cap, the run stops at mr. A `none` or `mr` ceiling already stops at or below mr, so the cap never applies to it. Say "The ceiling is <ceiling>, and the deferred Validation Steps cap the run at mr until the execute flow's seat run passes on <short HEAD>." in place of the sentence above. A ship fix commit after a passed seat run moves HEAD, so the cap returns until a seat run passes on the new tip. When a `Seat run passed:` line lifts the cap, pass that line's sha as `seatSha`, so the runner refuses a merge of any head the seat run did not pass on, such as a fix this run pushes.

The carried cap applies when `noCiConfig` is true and the note holds a `Carried fix: <sha>` line with no later `Carried verify: <sha> passed` line. Under the cap, the run stops at mr, as under the seat cap, so a later ask never merges a carried fix that ran no test. Say "The ceiling is <ceiling>, and the carried fix <short sha> ran no passing test in a repo with no CI configuration, so the run stops at mr." in place of the ceiling sentence.

## 6. Preview

Print the preview in chat and ask nothing, because the note's recorded `ceiling` is the answer:

- the commit message, the MR title, and the MR body.
- each path in `paths` on its own line.
- the ceiling and `startAt`.
- the `botAuthors` list, empty unless the user names bot logins, the `botLogins` list from section 7, and each login section 7 dropped. GitHub app authors count as bots without either list. On GitLab only a listed login counts as a bot, because the note author carries no bot flag.
- the `nits` value. Under `skip`, say that a bot thread that asks only for a cosmetic change stays open and that an open thread refuses the merge.
- when the ceiling is `mr` or higher, the fix templates:
  - the pipeline fix message template `fix(ci): <failing check> (ship-flow)`, bounded at `maxFixRounds` commits, default 1.
  - the review fix message template `fix(review): <thread summary> (ship-flow)`, bounded at one commit per fixable bot thread.
  - the reply template `Fixed in <short sha>: <what changed>`, one reply and one resolve per fixed bot thread.
  - when `carriedFindings` is not empty, each carried finding as `<file>: <title>`, the carried fix message template `fix(review): <count> findings the execute flow carried (ship-flow)`, one commit after the MR stage, and each `testDirs` entry the fix may add tests under.
  - when `noCiConfig` is true, the sentence "The repo carries no CI configuration, so the pipeline watch waits 2 minutes for a host check to appear, a check that appears is watched to the usual bound, and a pushed commit with no check does not stop the run."
- when the ceiling is `mr` or higher, the protected paths: CI configuration (`.github/`, `.gitlab-ci.yml`, `.gitlab/`, `.circleci/`, `Jenkinsfile`), every `ciScripts` path from section 3, and every path on the note's `Protected paths:` line, with the sentence "A fix commit that changes one of these, or a file outside the paths above, hands the merge to the user."
- that no commit carries a Co-Authored-By trailer and that human threads are never touched.
- the tag name and message when the stage is release, and every CI tag trigger sentence from section 3.
- when `startAt` is `merge` and Plan Changes During Execution records fix shas from earlier ship-flow runs, or for any `startAt` when it holds a `Seat run reviewed:` line, the heading `Commits this run may merge without a panel review` with each of those shas and each sha on every `Seat run reviewed:` line on its own line, because the run merges over every fix sha the note records and every commit a seat run reviewed.

Under `none`, the preview holds only the commit message, the MR title and body, each path in `paths`, the ceiling, and `startAt`, and it still prints before the handoff.

This preview is the execution-guardrails preview for the whole run.

## 7. Launch

Run `scripts/resolve-models.sh` as `plan-guide` § Run options defines, from the `worker_model`, `verifier_model` and `verifier_effort` values this flow read or asked there, and pass the printed `agents` object as `models`.

When the `ceiling` arg below is `merge` and `pwd -P` sits under `<main>/.claude/worktrees/`, call ExitWorktree with `action` set to `keep`, never `remove`, because the runner's cleanup removes the worktree from the main checkout, and run `pwd -P` again. Asking for the ship flow at merge is the request to leave the worktree. If the call fails, or the session still sits there, pass no `mainRoot`.

Build the args:

- `planName`, `repoRoot`, `repoName`: from section 1.
- `host`, `remotePath`, `defaultBranch`, `branch`, `startAt`, `recordedSha`, `mr`, `mergedSha`: from section 3. Pass `mr` only when `startAt` is `merge` or `release`, and `mergedSha` only when `startAt` is `release`.
- `commitMessage`, `mrTitle`, `mrBody`, `paths`: from section 4.
- `ceiling`: the note's value from section 2, or `mr` when the section 5 seat cap or carried cap applies. `tag`: the note's `tag_merge` value from section 2 as a boolean, `false` when the key is absent.
- `nits`: the note's value from section 2.
- `botAuthors`: the logins the user's ask names, else `[]`.
- `botLogins`: on GitLab, the logins listed under the remote's host name, the leading segment of the section 3 `Repo:` line with any `:<port>` suffix removed, in `~/.claude/toolkit-review-bots.json`, read with the Read tool. A missing file, a file that does not parse, or no entry for the host gives `[]`. Drop each login that does not match `^[A-Za-z0-9][A-Za-z0-9._-]*(\[bot\])?$`. On GitHub pass none, because GitHub marks app authors itself.
- `maxFixRounds`: 1 unless the ask names another bound. `maxThreadRounds`: 3.
- `noCiConfig`: the section 3 value as a boolean.
- `seatSha`: from section 5, only when a `Seat run passed:` line lifted the cap.
- `tagName`, `tagMessage`: from section 3, only when `ceiling` is `merge` and `tag` is true.
- `knownShas`: the shipping record's commit sha (`recordedSha`) plus every fix sha that Plan Changes During Execution records from an earlier ship-flow run and every sha on a `Seat run reviewed:` line, or an empty list.
- `priorFixShas`: every fix sha that Plan Changes During Execution records from an earlier ship-flow run, or an empty list. Those shas stay in `knownShas` as well.
- `priorCarried`: one `{sha, testDirs}` per `Carried test dirs: <sha>: <dirs>` line under Plan Changes During Execution, with `testDirs` as the comma-separated `<dirs>`, or an empty list for `none`, so the merge gate lets an earlier carried fix commit keep the test files it added. Pass none when the note holds no such line.
- `protectedPaths`: every `ciScripts` path from section 3 plus each path on the plan note's `Protected paths:` line, a comma-separated list of repo-relative paths under Affected Files. A note with no such line adds none, and no other path the note names counts.
- `mainRoot`: `<main>`, only when `ceiling` is `merge` and the session is not inside a worktree. `sessionId`: the session id taken from the scratchpad path, as execute-flow section 2a takes it, passed only with `mainRoot`.
- `worktree`: the `Seat: worktree` path when the section 3 `test -d` succeeds, else empty, passed only with `mainRoot`, because the runner refuses a `worktree` that does not sit under `<mainRoot>/.claude/worktrees/`. The runner reads the worktree's occupants at cleanup time, so no launch-time occupant read gates this arg.
- `carriedFindings`: one `{file, title, detail}` per `Finding for the PR: <file>: <title> [<tag>, score <score>, final <finalScore>]: <detail>` line under Plan Changes During Execution with no later `Carried fix:` line for the same `<file>: <title>`, or none. `<file>` is the text before the first `: `, `<title>` the text after it up to the last ` [` before `]: `, and `<detail>` the text after that `]: `.
- `carriedVerify`: only when `carriedFindings` is not empty, `{dir, command, failing, testDirs}` from the latest `Baseline:` line that is not `none`. `<cmd>` is the text after `Baseline: ` and before the last ` exit `, and the failing names are the comma-separated text after `failing `, or none for `failing none`. On a single-repo note, `dir` is `repoRoot`, `command` is `<cmd>`, and `failing` is those names. On a several-repos note, `<cmd>` holds `cd '<root>' && <command>` parts joined by ` ; `, so `dir` and `command` come from the part whose `<root>` is the repo's root, or the project root's part for a nested module with no part of its own, and `failing` holds the names that begin `<name>: `, with that prefix removed. No such line or no matching part passes no `carriedVerify`, and the runner then refuses an unattended merge under `noCiConfig`. `testDirs` comes from one `toolkit:verifier` that reads the verify command, and the script it runs when the command runs a repo script, and returns the directories, relative to `repoRoot` and each ending with `/`, that hold the test files that suite runs, because the runner matches them against fix paths relative to `repoRoot`. Each must exist under `repoRoot` and sit on no hands-off path from section 6, so a nested module that takes the project root's part keeps only the directories inside the module. A read that finds none passes no `testDirs`, so the carried fix stays inside the listed files.
- `mergeCheck`: only on a section 3b pass-1 launch, as section 3b says.
- `scratchDir`: the absolute scratchpad path. `pluginRoot`: `<repoRoot>/plugins/toolkit` when the launched script comes from `<repoRoot>`, directly or through the scratchpad copy below, else `<plugin-root>`, so the runner calls the `watch-mr.sh` and `seat-check.sh` beside it.
- `models`: the `agents` object the resolver printed.

When `repoRoot` contains `plugins/toolkit/workflows/ship-runner.js`, launch `{scriptPath: "<repoRoot>/plugins/toolkit/workflows/ship-runner.js"}`, otherwise `{name: "toolkit:ship-runner"}`. If name resolution fails, launch `{scriptPath: "<plugin-root>/workflows/ship-runner.js"}`. The script is named `ship-runner` because a workflow and a skill cannot share a name in the plugin registry. If the Workflow tool refuses a `scriptPath` as outside the working directory, copy the script byte-identical to `<scratchpad>/ship-runner.js`, take the first 12 characters of `shasum -a 256` for the source and for the copy, require the two to match, and launch `{scriptPath: "<scratchpad>/ship-runner.js"}`. A run that dies is not resumed: every stage is idempotent, so asking for the ship flow again derives `startAt` from the tree and the host. The section 7b relaunch is that same mechanism, driven by the watcher's exit instead of the user's ask.

The result is `{stoppedAt, stopStage, commitSha, headSha, pushed, mr, pipeline, threads, fixShas, carried, merged, mergeReady, mergeRefusal, tag, cleanup, handoff, blocked, incomplete}`:

- `pipeline` is `{state, sha, rounds, failingLines}` or null, where `state` is `green`, `red`, `pending`, or `none` and `sha` is the commit the state belongs to.
- `threads` is `{fixed, pushedBackNeeded, human, open, review, rounds}` or null, where `review` is `{outcome, login, sha}` from the last review wait or null, with `outcome` `landed`, `quiet`, `busy`, or `unreviewed`. Once either review wait reads a bot review that says it did not review, `review` is `{outcome, login, sha, reason}` with `outcome` `unreviewed`, kept over a later `quiet` wait until a `landed` or `busy` wait replaces it, where `login` is the refusing bot, `sha` the head it refused on, and `reason` the first line of its sentence. `rounds` is the thread fix rounds this run used.
- `carried` is `{sha, resolved, unresolved, verify}` once the carried fix commit pushed, else null, where `resolved` and `unresolved` list `<file>: <title>` per carried finding and `verify` is `{exitCode, failing}` from the `carriedVerify` command, or null when no command ran.
- `mergeReady` is true under `mergeCheck` when the Merge stage's refusal reasons are empty and nothing blocked the run, false otherwise, and null when no check ran. `mergeRefusal` is the sentence that names those reasons, or null.
- `fixShas` lists every fix commit this run pushed, the carried fix commit included. `merged` is `{sha, kind}` or null, where `kind` is `merge`, `squash`, `fast-forward`, or `unknown`.
- `cleanup` is `{ran, skipped, failed, notRun, holders, remote}` or null when the cleanup stage did not read the state. `ran`, `failed` and `notRun` list commands, `skipped` lists one sentence per step the cleanup left in place, `holders` lists each live seat holder as `<name> (<sessionId>)`, and `remote` is `cleanup` when the cleanup's push removed the remote branch, `host` when origin no longer held it, and `kept` otherwise. A cleanup command failure lands in `failed`, never in `blocked`.
- `handoff` is `{stage, command}` when the permission system denied a command, else null.
- `blocked` lists one sentence per reason the run stopped, and `incomplete` lists the labels of the stages that died.

## 7b. Wait

The runner ends its run at its nine-minute watch bound, because a blocking call inside an agent is capped at ten minutes, so the conductor owns any longer wait. Wait only when the result has `handoff` null, `incomplete` empty, and `blocked` holding exactly one sentence, which is the pending sentence `The pipeline for <sha> was still pending at the watch bound.`, the no-review sentence `No review from <bots> has landed on <url> for <sha> at the watch bound.`, or the in-progress sentence `A bot review of <url> was still in progress for <sha> at the watch bound.` Every other result goes to sections 8 and 9.

Run section 8 for the returned result before starting the watcher, so the plan note is right if the session ends during the wait.

Start the watcher with the Bash tool and `run_in_background: true`. For the pending sentence, run `bash <pluginRoot>/scripts/watch-mr.sh <host> <remotePath> <number> pipeline --sha <sha> --bound 180`, followed by ` --none 2`, the runner's `NONE_MINUTES`, when the launch passed `noCiConfig` true. For the no-review sentence, run `bash <pluginRoot>/scripts/watch-mr.sh <host> <remotePath> <number> threads --sha <sha> --bound 180` with one `--bot "<login>"` per `botAuthors` entry. For the in-progress sentence, run `bash <pluginRoot>/scripts/watch-mr.sh <host> <remotePath> <number> review --sha <sha> --bound 180` with one `--bot "<login>"` per login in `botAuthors` and `botLogins`, each login once. The threads-mode watcher takes `botAuthors` only. `<pluginRoot>` is the `pluginRoot` arg section 7 passed, so the watcher runs the same `watch-mr.sh` as the runner. `<number>` is `mr.number` and `<sha>` is the sha in the sentence. The watcher runs from the repo's working directory, which a ship-flow session already uses, and `glab` reads the GitLab host from the git remote there. Say in one chat line what the watcher waits for and that the run resumes on its own when the watcher exits, then end the turn. The harness wakes the conductor when the command exits. Never poll, never spawn an agent to wait, and never run the watcher in the foreground. Run one watcher at a time.

On the completion notification, read the exit code and the status line that `watch-mr.sh` prints:

- `GREEN` or `LANDED` (exit 0), `QUIET` (exit 15), `UNREVIEWED` (exit 16), `RED` (exit 10), or `NONE` (exit 13) when the launch passed `noCiConfig` true, because the runner accepts a pushed commit with no check there: spawn the section 3 verifier again and derive `startAt` again. If `startAt` is `merge` and the branch, the MR url and number, and the launch's ceiling are unchanged, rebuild the args per section 7 with the same `ceiling`, `paths`, `botAuthors`, `botLogins`, `nits`, `seatSha`, `protectedPaths`, and `noCiConfig`, and with no refusal arg, with `maxFixRounds` and `maxThreadRounds` set by the two budget rules below, and with `knownShas`, `priorFixShas`, `priorCarried`, `carriedFindings` and `carriedVerify` rebuilt from the note. Then relaunch per section 7, because the recorded ceiling covers this run and nothing the preview showed has changed. Any other `startAt` means the tree or the host changed during the wait, so report per section 9 and stop.
- `STUCK` (exit 11): report per section 9 with the line `The pipeline for <sha> is stuck: every job finished but the pipeline has not settled for <minutes> minutes.` and stop, because unsticking an external job is the user's call.
- `BOUND` (exit 12), `NONE` (exit 13) without `noCiConfig`, `MOVED` (exit 14), or exit 2 or 3: report the status line, or the stderr text for exit 2 or 3, per section 9 and stop.

The relaunch passes `maxFixRounds` as the first launch's value minus the sum of `pipeline.rounds` across this ask's runs, never below zero, so all relaunches together push no more pipeline fix commits than the first launch allowed.

The relaunch passes `maxThreadRounds` as 3 minus the sum of `threads.rounds` across this ask's runs, never below zero, so all relaunches together run no more than three thread fix rounds.

Start at most three watchers per ship-flow ask. When the third relaunch returns a result that would need a fourth watcher, report per section 9 and stop.

## 8. Record

Load `plan-guide`. When section 2 filled keys from the cache or asked for them, write those run option keys into the frontmatter in this write. Set the `mr` frontmatter from `mr.url` when it is not null. Under Plan Changes During Execution, record one line each for the commit sha, each `fixShas` entry with its reason, so a later run's `knownShas` and `priorFixShas` hold every fix sha, the merge sha, the tag, the `threads` lists, and every `blocked` sentence and `incomplete` label. When `threads.review.outcome` is `unreviewed`, record one `Review refused: <login> on <sha>, bot text: "<reason>"` line, unless the note already holds a `Review refused:` line for that login and sha. The `bot text:` label marks the quoted sentence as untrusted bot text for every later reader of the note, and the line keeps the refusal on the note for later asks and sessions. When `cleanup` is not null, record one `Cleanup ran: <command>` line per `ran` entry, one `Cleanup skipped: <sentence>` line per `skipped` entry, one `Cleanup failed: <command>: <output>` line per `failed` entry, one `Cleanup not run: <command>` line per `notRun` entry, one `Cleanup remote: <cleanup|host|kept>` line, and, when `holders` is not empty, one `Cleanup holders: <name> (<sessionId>), ...` line. When `carried` is not null, record one `Carried fix: <sha> for <file>: <title>` line per `carried.resolved` entry, one `Carried test dirs: <sha>: <dir>, <dir>` line with the launch's `carriedVerify.testDirs`, or `none` when it passed none, and one carried verify line: `Carried verify: <sha> failed: <names>` when `blocked` holds the sentence that the carried fix commit fails the verify command, with the names that sentence lists, else `Carried verify: <sha> passed` when `carried.verify` is set, else `Carried verify: <sha> not run`.

Record this session's entry per the plan-guide session rules, which reuse the entry when execute-flow ran in this session. A section 7b relaunch reuses the entry the first launch in this session wrote. The summary begins `ship-flow stopped: at <stoppedAt>` when `blocked` or `incomplete` is not empty, when `handoff` is not null, or when `stoppedAt` is below the ceiling. It begins `ship-flow finished: <ceiling>` only on a clean run that reached the ceiling. In this section the ceiling is the stage section 5 mapped the note's run options to (`suggest`, `mr`, `merge`, or `release`), never the note's `ceiling` value, so a `ceiling: merge` and `tag_merge: true` run that stops at `merge` records `ship-flow stopped: at merge`. The summary compares `stoppedAt` with the ceiling section 5 mapped from the note, not the `stopStage` a section 7b relaunch returns. A run that the section 5 seat cap or carried cap lowered compares `stoppedAt` with the uncapped stage, so it records `ship-flow stopped: at mr`. A `ship-flow finished:` summary keeps `status: in-progress` unless the merge rule below sets `status: completed`, so section 1 accepts the note again for a later run after the user raises the note's ceiling. When `merged.sha` is set, a `Remember:` line under Plan Changes During Execution still sets `status: completed`, and section 1 accepts that note again for the release-only run. Without that line, keep `status: in-progress` and tell the user that the remember pass has not run. A release-only run on a `status: completed` note leaves the status as it is.

Write the change by the changed-lines path of `plan-guide`'s atomic write rule, `vault-fs.sh cp` to the `.tmp.md` copy, an Edit on the copy, then `vault-fs.sh mv`. Every later plan note write in this skill takes the same path. If the Edit tool or the Write tool refuses the copy, remove the copy with `vault-fs.sh rm`, Write the whole note to the same `.tmp.md` path as a new file, then `vault-fs.sh mv` it over the note. Then run `python3 <plugin-root>/scripts/validate-plan.py "<plan note path>"` and require exit 0. If the validator fails, report its output and stop. Never patch a failure silently.

## 9. Report

Open with the Repo, Branch, and Scope header lines from the git-safety Commit handoff section. After the header, write `MR: <url>`, followed by `merged <sha>` when `merged` is set, or `MR: none`.

Then write `Fixed beyond the plan:` with one line per fix sha from every run of this ask and every fix sha the note records. Each line carries its reason: the thread summary for a sha in `threads.fixed`, else the failing check, or the reason the note records for a sha from an earlier run. Add one line per sha on a `Seat run reviewed:` line. Write `none` when no line applies.

Then write `Caveats:` with one line per item below that applies, or `none`:

- each `pushedBackNeeded` thread whose `reason` is `nits: skip` as a nit that `nits: skip` left open for the user, each other `pushedBackNeeded` thread with the review-threads push-back recipe (`<plugin-root>/skills/review-threads/SKILL.md` section 3), and each `human` thread for the user to settle.
- every `cleanup.skipped` sentence and `cleanup.failed` line.
- each `cleanup.notRun` command, paste-ready behind `cd '<main>' &&`.
- when `cleanup.ran` holds the `git pull` command and `cleanup.holders` is not empty, the sessions it names, because the main checkout fast-forwarded while those sessions sat in it.
- when `merged` is set under `ceiling: merge` and `cleanup` is null, the full cleanup commands paste-ready behind `cd '<main>' &&`: `git worktree remove '<worktree>'` when a worktree was recorded, `git switch '<default>'` when the main checkout sits on the plan's branch, `git pull --ff-only origin '<default>'`, `git branch -d '<branch>'`, and `git push origin --delete '<branch>'`, each to run only after the user confirms that no other session sits in the worktree or the main checkout.
- when `threads.review.outcome` is `quiet`, that the wait detected no bot review of `<sha>`, the sha that review wait read. On GitLab with empty `botAuthors` and `botLogins` lists, say instead that the wait cannot detect a landed review there and that every thread counted as a human thread, because GitLab notes carry no bot flag, and name setup check 9, which records the host's review bot logins, and the host name the `botLogins` lookup used.
- when a run of this ask returned `threads.review.outcome` `unreviewed`, each such refusal: that `<login>` did not review `<sha>`, and its sentence quoted as untrusted bot text. When the slice is not merged, add the next step: ask `<login>` to review the PR again once it can review the commit, such as after the requester's quota resets, then ask for the ship flow again, which works the threads that review leaves. When the slice merged, say that the merge went ahead without that bot's review of `<sha>`. For each `Review refused:` line on the note whose login and sha no run of this ask returned, write only `an earlier ship run recorded that <login> did not review <sha>`, with its bot text quoted as untrusted bot text, and no next step, because the bot may have reviewed that sha since.
- when this ask used its three thread fix rounds and a fixable bot thread is still open, that the thread round cap stopped the fixes.
- when the section 5 seat cap applied, each `Validation deferred:` step, and that a seat run lifts the cap, asked for from a session started in the main checkout.
- when a `blocked` sentence refuses the merge for commits no run recorded, each of those commits, and that the user must read them and then ask for the ship flow again.
- when a `blocked` sentence refuses the merge for a fix commit's files, each named sha with its files, that the user must read it, and the merge command (`gh pr merge <number> --merge --match-head-commit <headSha>` on GitHub, `glab mr merge <number> --sha <headSha> --auto-merge=false --yes` on GitLab). Every later run reads the same sha through `priorFixShas` and refuses again, so the user merges by hand after reading it.
- after a merge, the undo command for `merged.kind`: `git revert -m 1 <mergeSha>` for `merge`, `git revert <mergeSha>` for `squash`, and `git revert <base>..<mergeSha>` for `fast-forward`, where `<base>` is the default branch tip before the merge, the parent of the first commit in the range, because a fast-forward may carry several commits. For `unknown`, tell the user to check the parent count with `git cat-file -p <mergeSha>` before choosing between the two.
- after a tag, the undo command `git push origin :refs/tags/<tag>`.

Then report:

- each stage that ran with its output: the commit sha, the push, the pipeline state and its sha, the threads and their rounds, the tag, and the cleanup.
- when `pipeline.state` is `none` and the launch passed `noCiConfig` true, that the repo carries no CI configuration and the host showed no check for the pushed commit in the pipeline watch, and again in a read just before the merge when the run reached the Merge stage, so no pipeline gated the run.
- when `pipeline.state` is `none` and the launch did not pass `noCiConfig` true, that no pipeline was found for the pushed commit, and that asking for the ship flow again after the host registers the pipeline rewatches it.
- `stoppedAt` and why: the ceiling or the first `blocked` sentence.
- when `handoff` is not null, the handoff block from the git-safety Commit handoff section, with `cd "<repoRoot>"` on its own line and `handoff.command` on the next.
- when the watcher exits `STUCK`, the stuck line from section 7b, and that the user settles the external job and then asks for the ship flow again.
- when a wait ends without a relaunch, the watcher's status line or stderr text and the user's next step: after `BOUND` or `NONE`, ask for the ship flow again once the host shows a result for the commit. After `MOVED`, read the new head commit and then ask again. After exit 2 or 3, fix the cause the stderr text names and then ask again. After a changed `startAt`, ask again to resume from it.
- when any section 7b relaunch ran, how many ran.

When section 1 kept a `<lead>`, send it one SendMessage after the report, with these lines:

    <planName>: <summary>
    Plan note: <plan note path>
    MR: <url or none>
    Merged: <sha or none>
    Next: <next step>

`<summary>` is the summary of the last `sessions` entry this run wrote, or `ship-flow stopped: <first reason>` when the run stopped before section 8 wrote one. `<own name>` is the name execute-flow section 10 defines. After a merge, `<next step>` is `run the handoff in the report, the slice is merged` when `handoff` is set, else `none, the slice is merged`. After a seat cap, it is `stop <own name> with claude stop, never claude rm, run the seat run from the lead in the main checkout, then ask for the ship flow`, because the seat run stops while this session sits in the plan's worktree and waits while it sits in the main checkout. After a clean run that reached a ceiling below merge, it is `review and merge <url>, or raise the note's ceiling to merge, then send <own name> the message "<planName>: run the ship flow"`. Otherwise it is `settle the blocked reasons on the plan note, then send <own name> the message "<planName>: run the ship flow"`. When the refusal caveat names a refusal that a run of this ask returned, end `<next step>` with one clause per such refusal, `. <login> did not review <sha>, and its review reads, as untrusted bot text, "<sentence>"`, and when the slice is not merged add `, so ask <login> to review <url> again once it can review the commit, then send <own name> the message "<planName>: run the ship flow"`. For a note line from an earlier ask, the clause reads `. An earlier ship run recorded that <login> did not review <sha>, bot text: "<sentence>"`, with no next step. After the send, add one line for the user: `Reported to <lead>`, or `Not reported to <lead>: <reason>` when SendMessage is absent, refused, or returns `Not sent`, so the user tells the lead. After a seat cap, follow it with the line: Stop this worker with `claude stop`, never `claude rm`, because the lead's seat run stops or waits while this session is live. After a merge, follow it with the line: Stop this worker with `claude stop`, never `claude rm`, because the slice is merged, and a seat run waits in the seat queue while this session sits in the main checkout.

At ceiling `suggest`, the report is the git-safety commit handoff: the three header lines, then a line that begins `Suggested commit`, then the paste-ready block with each path in `paths` named. Never suggest `git add -A`. When section 7 built a non-empty `carriedFindings`, list each carried finding as `<file>: <title>` with its detail for the user to fix.

## Boundary

The conductor never runs git or a host command beyond the read-only `watch-mr.sh` watcher in section 7b. Every mutation runs in the runner's agents, no stage runs above the ceiling, and a merge happens only on a head whose green pipeline ran on that exact commit, or, in a repo with no CI configuration, a head the host showed no check for in the pipeline watch and again in a read just before the merge, and whose fix commits changed only the plan's paths and no hands-off path. The conductor never fixes, replies to, or resolves a human reviewer's thread. Not for a slice no execute flow reviewed (`execute-flow` owns that) and not for working review threads outside a ship run (`review-threads` owns that).
