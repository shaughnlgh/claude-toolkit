# Prose style (all prose: responses, docs, plans, commits)

- Prefer the plain word: use, before, if, because, many. Never leverage, utilize, prior to, in the event that, delve, crucial, robust, seamlessly.
- Say the mechanism or the number, not the feeling. If a sentence could appear unchanged in another project's docs, it says nothing about this one. Cut it.
- Active voice with a named actor: "the loader parses the file", not "the file is parsed". Passive stays when the actor is unknown or genuinely does not matter.
- Delete filler and hype: "in order to", "it is worth noting", "simply", puffery ("pivotal", "testament to"), vague attributions ("experts believe"). State the fact or delete the sentence.
- One word, one meaning per document. Pick config or settings, check or verify, and keep it.
- In instructions: imperative mood, one instruction per sentence, condition before command ("If the build fails, read the log"). Write "must" or delete. Never write `should`, readers and models treat it as optional.
- Short sentences with complete grammar: one idea each, keep articles and "that", no contractions in docs.
- No em dashes in new prose. End the sentence or use a comma. Do not substitute parentheses or semicolons.
- Sentence-case headings. No decorative emojis, no bold-restating list labels ("**Performance:** performance improved"), no chatbot phrases ("Hope this helps!").
- Rewrite style, never facts: no invented specifics. Code, identifiers, and quoted errors stay exact.
- Voice and opinions belong in conversation and narrative, not repo docs. Marketing and brand copy are exempt from the style rules, never from factual fidelity.
- Full catalogs: rules/prose/unslop.md (AI-tell patterns, for rewriting existing text) and rules/prose/simple-english.md (instructional-text discipline, for runbooks, error messages, procedures, agent instructions). Open the one the task touches.
