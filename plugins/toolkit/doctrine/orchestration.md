# Agent Orchestration

Use a supervised multi-agent workflow for any task that changes files, regardless of size. The main conversation is the conductor: it owns scoping, planning, acceptance criteria, sequencing, integration, and final review. Worker agents handle bounded subtasks (exploration, narrow edits, test runs, docs drafting, verification, evidence gathering).

The worker agents ship with this toolkit: `explorer` (read-only search and discovery), `planner` (plan drafting from gathered evidence), `implementer` (bounded execution), `browser-driver` (browser automation loops via claude-in-chrome), `verifier` (independent validation), plus the reviewer set (`code-reviewer`, `security-reviewer`, `silent-failure-hunter`, `pr-test-analyzer`, `performance-reviewer`, `doc-reviewer`, `coupling-reviewer`), `plan-critic` (adversarial plan review), and `frontend-designer`. Their models and effort live in the template the Model policy names. Projects may override with local agents at `<repo>/.claude/agents/`; prefer project-local agents when they exist.

## Hard rules

- These orchestration rules bind the conductor (main chat) only, and a worker session is a main chat for these rules. Worker subagents are leaf nodes: they do their assigned work themselves and must never spawn subagents. A worker that hits a blocker, question, or ambiguity reports it back to the conductor, which decides how to proceed. It does not delegate its way out.
- The main chat is supervisor-only, regardless of task size and including after a compaction. It must not edit files or run implementation commands directly; every change, however small, goes to a worker agent that reports back. Convenience, obviousness, or "tiny and faster done directly" never justify a direct edit. The conductor-guard hook enforces this mechanically: it refuses a direct conductor edit to a project file, and the only override is the human setting `TOOLKIT_CONDUCTOR_EDITS=1` for a session, or for a project through `/toolkit:setup` check 10 in its `.claude/settings.local.json` (see docs/hooks.md).
- Planning always stops for user review. Do not execute until the user explicitly approves the plan and instructs execution. The plan flow's `approveIf` gate is the one exception, because it may set a plan to approved without a user review, and the human approval rule still governs execution.
- Do not ask about model preferences if the prompt or project workflow already defines them; record the routing in the plan and follow it during execution.
- Every delegation goes to the toolkit worker (or a project-local agent shadowing it) whose charter fits the task: docs to `doc-reviewer`, research including web lookups to `explorer`, plan drafting to `planner`, plan review to `plan-critic`, execution to `implementer`, completion checks to `verifier`, code review to the reviewer set. The harness's generic agents (general-purpose, Explore, Plan) are a last resort for work no toolkit charter covers, and reaching for one requires stating why in the delegation.
- An agent the user has stopped is cancelled work. Never resume, re-message, or relaunch it on your own initiative; it comes back only on the user's explicit instruction.
- A review-stage content change to a plan note is plan drafting, not transcription. Route it to `planner` with the amendment and the affected sections. The conductor keeps assembly, the atomic write, and `validate-plan.py`. After three or more amendments to one plan in a review round, run a scoped `plan-critic` re-pass over the amended sections.

## Model policy

Routing preferences, not hard guarantees. Goal: best possible plan and acceptance, lowest possible cost for mechanical implementation.

- **No Haiku.** All worker subagents use Sonnet or stronger. `scripts/resolve-models.sh` refuses Haiku at every layer. A workflow call with a blank resolved model runs on the session model, and an Agent-tool spawn with no model uses the agent definition's model, then a configured default subagent model, then the parent session's model, so neither the conductor session nor a configured default subagent model may run on Haiku.
- Conductor: strongest reasoning model (the user's choice; do not override). Keeps planning, scoping, architecture, code review, and final sign-off.
- Workers: models and effort live in `scripts/toolkit-models.json.template` (Opus at high effort for every agent that writes or judges code, the verifier at xhigh, Sonnet at medium for the read-only `explorer` and `browser-driver`, and `planner` blank, so a workflow `planner` call inherits the session model and an Agent-tool `planner` spawn uses a configured default subagent model, then the parent session's model, because the agent file sets none). `~/.claude/toolkit-models.json` overrides per machine. The plan note's `worker_model`, `verifier_model` and `verifier_effort` apply per session: each flow passes the plan's values when it launches a workflow, and the `agent-model.sh` hook applies the session's newest run options cache to Agent-tool spawns, whichever plan wrote it. A per-invocation `model` or `effort` wins for that field, and `scripts/resolve-models.sh` refuses Haiku at every layer on both spawn paths, the `agent-model.sh` hook and the runner scripts' `models` arg. Session start lists each toolkit agent's model and effort as the hook would add them. On every Agent-tool spawn of a `toolkit:<name>` agent, pass `model` and `effort` from that list, so the auto mode classifier reviews the final call, because a hook that changes a call after that review gets the call refused once. Omit a field the list says to omit. A model or effort the user asks for wins. The `agent-model.sh` hook stays the backstop for a call that lacks either field.
- Escalate to the strongest model when the task touches project-defined high-risk areas.
- If the actual model used is visible and differs from the requested routing, report it.

## Spawning

Spawn workers proactively when the task splits into independent subtasks, evidence can be gathered in parallel with other work, a subtask is mechanical/search-oriented, or a long-running command can run alongside another step. During planning for any non-trivial task, spawn at least one worker for repo/doc scan (`explorer` — discovery is its job, not the planner's) unless the task is obviously too small — if no worker is used, say why. Use a single worker rather than a fan-out when multiple workers would touch the same file or decision surface, or when the main challenge is choosing architecture — but the edit itself still goes to that worker, never the conductor.

Never brief an agent to poll. A wait on external state, such as a pipeline, a bot review, or a deploy, is one background shell command that exits on a terminal condition and wakes the conductor, so the wait costs no tokens while it runs. Acting on the result is an agent's job. A workflow script has no shell, so a wait inside one is one bounded blocking call in a verifier, and at the bound the script ends the run with a named `blocked` sentence for the conductor skill to wait on in the background. `scripts/watch-mr.sh` is the watcher for a pipeline or a bot review on an MR or PR. `scripts/seat-queue.sh wait` is the watcher for a turn at the seat. `scripts/worker-watch.sh` is the lead's watcher for its worker sessions.

Two writers on one file lose work: `vault-fs.sh mv` and the Edit tool both replace whole-file content, so the last writer wins and the earlier write vanishes without an error. After any round in which more than one worker wrote, grep the load-bearing markers (headings, frontmatter keys, anchor lines) in every touched file before accepting the round.

Browser automation is worker work. Reproduction runs, multi-step UI journeys, and dashboard or log-viewer trawls through claude-in-chrome go to `browser-driver`, not the conductor: hundreds of computer-use steps carried at full conductor context are the single most expensive known usage pattern (a worker starts near-empty; the conductor does not). The conductor coordinates — what to drive, what evidence to collect, when the human logs in — and reads the distilled run report. In any browser context, prefer text extraction (`get_page_text`, `read_page`, `find`) over screenshots and batch mechanical sequences with `browser_batch`; screenshots are image tokens that sit in context for the rest of the session. The conductor drives the browser itself only for a genuinely short interaction (a handful of steps) or when the human is interleaved in every step.

When spawning multiple independent workers, launch them in a single message (multiple Agent tool calls in one response) so they run concurrently.

For repeatable multi-stage fan-out patterns (multi-dimension review, per-task execute-verify loops over a known work list), prefer a Workflow script over improvised conductor-driven spawning: deterministic sequencing, compact structured-JSON returns via schemas, low reasoning effort on mechanical stages, resumable if a run dies. The bundled review-mr workflow is the house example. Keep conductor acceptance between phases; do not script away the green light.

## Lead and worker sessions

- Roles. Any session the user starts is the lead. Its name may carry the optional `lead-<key>` prefix that crawl suggests, and any name that does not start `worker-` marks a lead. A worker session is a background session the lead starts with `claude --bg`, named `worker-<type>-<key>`. Types are `investigate`, `plan`, `execute` and `ship`. The key is the ticket in lowercase, else the plan name, plus a wayfinder child's `-t<n>` suffix after a ticket key. `worker-spawn.sh` appends `-2` and up only on a name collision, and a stopped worker session keeps its name. A worker session is a conductor for its own subagents and follows every conductor rule, and it never starts a worker session.
- Worker session or subagent. A worker session is for a phase the user may talk to or resume, or that runs long unattended: execute, ship, investigate, one ticket among several. Discovery, review and judging stay in subagents in the lead and in its worker sessions, and plan-flow discovery stays in subagents. The lead runs the crawl itself.
- Spawn. The lead proposes in one plain-text line that names the worker session and every flow it will run, and starts it only on the user's typed yes, with `scripts/worker-spawn.sh`. The script reads the mode that the `worker-spawn-mode.sh` hook records, so the worker session runs in the lead's permission mode, because a session in another mode holds the lead's messages for approval. It passes `--plugin-dir` with the lead's own plugin root when that root sits outside the plugin cache, so a lead loaded by path gets a worker session on the same copy. The lead passes the `session_model` and `session_effort` that the plan note or the session cache records, or the model and effort the user names for that one worker session, and never its own model or effort or the machine default, because either would put every worker session on whatever model the lead runs. When no answer is recorded, the lead asks the worker session question of `plan-guide` § Run options before it proposes the worker session, and never answers that question itself. An execute worker session on a single-repo note starts with `--cwd <main> --worktree <planName>`. Claude Code then creates `.claude/worktrees/<planName>` on `worktree-<planName>`, cut from origin's default branch under its default `worktree.baseRef`, or opens that worktree when it exists, as on a rerun. A ship worker session starts the same way when the note records `<main>/.claude/worktrees/<planName>`, and with `--cwd <worktree>` for a worktree the note records at another path. A several-repos note starts the worker session in the projects root with no `--worktree`. A plan or investigate worker session starts in the main checkout with no `--worktree`, because it writes only the vault and its scratchpad, which sit outside its working directory. `claude --bg` refuses a repo the user has not trusted, and the script then exits 3 with Claude Code's line. On `NOBG` the lead says in one line that this Claude Code has no `claude --bg` and offers to run the flow in its own session, with no paste fallback. On exit 2 or 3 it quotes the `error:` line and makes the same offer. On `UNRECORDED <name>` the worker session runs but is not recorded, so the lead quotes the `error:` line, tells the user in one line that the worker session started and that the watch does not cover it, so the user follows it in agent view, and offers no run here.
- First prompt. The first prompt is the plugin's `templates/worker-<type>.md`, which `worker-spawn.sh` fills, and the lead never writes a first prompt by hand. The lead writes only the task text to `<scratchpad>/worker-task.md` with the Write tool before each spawn, and passes its read-at-dispatch ListAgents name as `--lead-name` and the plan note path as `--note`. Each template carries the task and plan note path, the flows granted, the recorded run options with the ceiling stated as the user's permission given in advance, the question routing, vault access, the report shape and the stop point. The script refuses the spawn when the lead name holds a double quote, a backslash or a control character, or when a placeholder stays unfilled, and the lead then offers to run the flow here.
- Grant. The ceiling the user picks in the run options is the user's permission, given in advance. The user's typed yes covers every flow the proposal names, up to that ceiling, and the first prompt names those flows. A worker session runs execute, ship and merge up to the recorded ceiling and never asks the user again. A later lead message only continues inside that grant, under the worker grant rule of execute-flow section 1. A flow the first prompt does not name needs a new worker session. When a worker session reports that auto mode refused a commit, push, MR or merge inside the grant, or when a continue message cannot be sent, the lead runs the ship flow itself on that plan note up to the recorded ceiling, says so in its final summary, and names the refusal as a template defect to fix. It never asks the user to approve again or to type a flow command in a worker session.
- Ownership and watch. `worker-spawn.sh` records each worker session in `<scratchpad>/workers`, and the lead reads only its own record. After a spawn, unless a watcher runs, the lead starts `bash <plugin-root>/scripts/worker-watch.sh wait --scratchpad '<scratchpad>'` with `run_in_background: true` and no `--hold`, because the watch treats a new worker session as pending until it first reads busy or waiting, and a running watcher picks up the new `workers` line on its next round. On each exit the lead tells the user one line per event: needs you (permission prompts first, answered in agent view with `←`, then `Space` to peek), finished (an `IDLE` or `NOSTART` line with a report message from that worker session since its last event), asked the lead (an `IDLE` line with a question message, which the lead answers), stopped without reporting (an `IDLE` line with no message), did not start (a `NOSTART` line with no message), gone (a worker session that disappeared mid-task), and one line for unowned background sessions. On `PUSH` it loads PushNotification through ToolSearch with `select:PushNotification` and sends one push naming the worker session, or says in the line that push is not available. It re-arms after every exit except `NONE`, `RUNNING` and 2. After an exit 3 it re-arms once, and after a second exit 3 in a row it quotes the `error:` line and tells the user in one line that the worker watch is off until they ask for it again. A worker session that sits idle after its event is settled, so the watch exits `NONE` once every owned worker session is settled or gone. A continue message goes out through SendMessage with `notify_when_idle: true`, and the lead then starts the watch with `--hold <id>` for that worker session unless a watcher runs. When a continue message cannot be sent, the lead follows the Grant rule above.
- Stop. The lead ends a worker session with `claude stop <id>` as its own call, never `claude rm`, because rm and agent view's delete remove a worker session's worktree and branch, while stop ends only its process. The lead stops a worker session on its own once its work is pushed or merged: after a ship report whose `MR:` line holds a URL or whose `Merged:` line holds a sha and that holds no blocked reason, or after its own ship run on that worker session's plan note pushed or merged. It lists each stop in its decisions-made list and never asks the user whether to stop a worker session. After any other report the lead leaves the worker session idle. A worker session left idle uses no tokens, and Claude Code's supervisor ends its process after about an hour unattached and keeps its conversation and its worktree.
- Questions. A planning grill question, like every grill question, goes from the worker session straight to the user through AskUserQuestion, answered in agent view, as the Loaded grills paragraph of the grill skill defines, and so does the ticket create confirmation. Every other worker session question goes to the lead by message. The lead answers what evidence, doctrine or earlier answers settle, lists each such answer in its decisions-made list for veto, and asks the user only what it cannot settle. Worker sessions ask only through AskUserQuestion, never in plain text. Plan approval happens in the lead, which records it on the plan note. Permission prompts stay in the worker session, because a message never grants consent.
- Reports. A worker session reports by SendMessage in its flow's shape (execute-flow section 10, ship-flow section 9), else in the three lines its template gives: `<key>: <summary>`, `Plan note: <path or none>`, `Next: <next step>`. When a send fails, it runs `bash <plugin-root>/scripts/worker-watch.sh name <lead session id>` and sends again to the name it prints, so a lead rename never breaks a report. When a worker session reports `Operation not permitted` on a vault path, the lead tells the user that macOS needs Claude Code's background host granted access to that folder in System Settings, Privacy & Security, as `docs/prerequisites.md` describes.
- Gate. The lead is the gate between phases, and no worker session waits on another worker session. The lead judges each report against the plan note and may message an idle worker session to continue in its own context. The lead may do work itself, as on the no-plan route, and edits nothing in a checkout a worker session is writing.
- How many. A task normally has one or two worker sessions, and the count across tasks is the user's choice, so `worker-spawn.sh` sets no cap and the lead queues nothing. The execute flow's own implementers are subagents, not worker sessions.
- Seat. An execute worker session's run opens or adopts the plan's worktree through the execute flow, which opens one with no question because the lead holds the main checkout, and runs the repo's install step there as execute-flow section 2a defines. No worker session builds its environment by hand. The seat run needs the main checkout to itself. It stops while a live session sits in the plan's worktree, waits in the seat queue while any live session other than the one that runs it sits in the main checkout, and returns to the worktree it left once it has restored the main checkout. A session in the main checkout with no queue entry, such as a worker session that is still planning, holds that wait until it ends or moves into a linked worktree. The waiting run names each such session to the user and, by message, to its lead, and the lead tells the user. When that session is the run's own lead, which the run knows by the lead session id its first prompt carries and never by name, the run starts no watcher and stops with `LEAD`, because a lead stays until its user ends it. A run with no valid lead session id waits for it as for any other holder, up to the wait bound that docs/scripts.md states. The lead then runs the seat run itself once the worker session is stopped with `claude stop`, or moves into a linked worktree and dispatches the seat run again. A session that only coordinates several leads, and runs no flow, starts outside the main checkout so that it never holds the seat.
- Older sessions. A plan note session entry named `parent-` reads as a lead and one named `child-` as a worker session.

## Context budget

Conversation context is re-sent on every request, so a long main chat pays for its own history on every tool step: past ~200k tokens each step costs several times a fresh session's, and near the window limit roughly thirty times. The context-sentinel hook injects a nudge at each threshold; treat it as binding, not as noise.

- Past ~200k tokens: stop taking on new mechanical work in the main chat. Delegate searches, browser loops, log trawls, and test runs to workers — they start near-empty — and plan a wrap-up point.
- Past ~400k tokens: bring the current task to a stable point, update the plan or work note, and recommend the user continue in a fresh session. The note is the continuity mechanism, not the conversation.
- Riding auto-compaction is not a strategy: a session that compacts repeatedly re-pays its context indefinitely. From the second compaction in one session, wrap up and hand off instead of continuing.

## Worker handoff contract

Every worker task includes:

- **Objective.** The exact outcome the worker must produce.
- **Scope.** The repo and the specific files or directories in bounds.
- **Task-specific constraints.** The generic write-time rules already arrive at spawn via the subagent-rules hook, so enumerate only the extras: applicable doctrine sections, project conventions, and plan decisions.
- **Required checks.** The checks the worker must run before reporting done.
- **Expected return format.** The fields and level of detail the report must use.
- **Known evidence.** File paths, line numbers, and findings the conductor already has, from planning, explorer output, or prior workers, so the worker does not re-explore for them.

Every worker result returns: `Objective`, `Files inspected`, `Files changed`, `Checks run`, `Result`, `Assumptions`, `Blockers`, `Residual risks`, `Rules applied` (only for a free-form report, not schema-constrained structured output), and `Topic note material` (facts about stable recurring concepts with source refs, or "none"). `Rules applied` is a self-report aid for conductor acceptance, not proof.

The conductor keeps every worker's Topic note material for the slice's remember pass (topic command, § Remember pass), the one consumer of that field.

Worker returns are distilled, not dumped: file paths with line references and one-line findings, never pasted file contents or multi-line code blocks. A short snippet (under 10 lines) is allowed only when the finding is unintelligible without it. Returns land in the conductor's context and stay there for the whole session, so a bloated return is paid for repeatedly.

## Acceptance and re-delegation

The conductor is the only role that decides "done". Before accepting worker output: compare it against the plan, inspect the changed files or reported evidence, verify or rerun key checks, and reject work that is incomplete, off-scope, or low-confidence. Do not let the implementer self-mark complete or the verifier mark complete on its own claim. The conductor remains accountable for the final answer.

When the verifier reports gaps or the conductor's acceptance check finds a problem: identify the specific gap, re-delegate with a narrow corrective scope (not the entire task), re-run the relevant verifier checks, and loop until the work matches the plan — or escalate to the user if a gap requires plan revision.

A worker that stops at its turn budget (frontmatter `maxTurns`) is unfinished work, not a result: resume it via SendMessage, or re-delegate the remaining tail with narrowed scope. The conductor does not finish implementation tails itself — that breaks the supervisor-only rule and skips acceptance.

For corrective follow-ups on work an agent just did, continue that same agent via SendMessage (by its agent ID or name) instead of spawning a fresh one — the continued agent keeps its context, so it skips re-reading the plan and files it already knows. But resuming replays the worker's entire accumulated transcript on every message that follows, so weigh that cost first: the deciding variable is whether the retained context is still load-bearing. Resume for corrective rounds on work the agent just did — same files, same effort, context still warm (minutes, not hours) — where skipping re-reading pays for itself. Spawn fresh for genuinely new scope, a suspect or polluted context (the agent misunderstood the task, or its context carries a wrong approach), or once the accumulated context no longer earns its keep — a small fix sent to a long-lived worker pays for that worker's whole history just to answer it. Rule of thumb: if the delegation prompt has to restate the context anyway, spawn fresh rather than resume.

## Reporting agent usage

When agents were used, the plan note and end-of-session report include each agent's name and intended model, and whether the actual model matched, if visible.
