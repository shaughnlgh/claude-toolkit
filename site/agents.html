Worker agents

The toolkit ships 14 worker agents. The main conversation is the conductor: it plans, delegates and accepts, and it hands every change to an agent, however small. You meet the agents when a flow or a guide spawns them at the right step, or when you call one by name.

How they work

Leaf workers

Each agent carries an explicit tool allowlist, and none of them gets the Agent tool, so no agent can spawn another. A worker that hits a blocker, a question or an ambiguity reports it back to the conductor, which decides how to go on and is the only role that decides when work is done. Returns are file paths and one-line findings, never pasted file contents.

The subagent-rules.sh hook injects the write-time rules into every worker at spawn, so it writes against them without the conductor pasting them in.

Tools are set in each agent's own frontmatter. Model and effort come from the shipped scripts/toolkit-models.json.template, which a per-machine ~/.claude/toolkit-models.json overrides per agent. Overrides shows how.

5 agents

Workflow agents

The plan-then-build pipeline: explore, plan, red-team the plan, implement, verify.

toolkit:explorer

Read-only exploration: code search, file discovery, pattern analysis, investigation questions and evidence gathering, including discovery during planning. It never edits.

WhenFor any search, investigation or evidence gathering that must not touch files.

toolkit:planner

Drafts a reviewable implementation plan from the evidence it is given, such as recall facts and explorer findings, and reads further only to close gaps. It never edits or implements.

WhenOn a non-trivial task once discovery evidence is in hand, before any code changes. Discovery alone is the explorer's job.

toolkit:implementer

Makes bounded file changes and runs focused commands from an approved plan.

WhenAfter plan approval, for minimal-scope execution.

toolkit:verifier

Checks claimed work against real checks and real data, not fixtures alone, and reports gaps. It never edits.

WhenAfter implementation, before a task is marked complete.

toolkit:plan-critic

Red-teams the plan itself: flawed assumptions, missing risks, scope creep, alternatives nobody weighed, and validation that cannot be tested. It runs the inversion pre-mortem and returns a verdict, objections, a tripwires block and a walk-away checks block in under 60 lines. It reviews the plan, not code.

WhenAfter the planner drafts a non-trivial plan and before you approve it.

7 agents

Review agents

Each reviews a diff it finds with git diff --name-only, has a terse and a verbose output mode, and keeps only findings it rates at 80 confidence or above.

toolkit:code-reviewer

Catches real bugs: off-by-one errors, null dereferences, inverted logic, race conditions, swallowed errors and needless complexity. It skips style nitpicks.

WhenAfter any code change, before a commit, or when a pull request or diff needs review.

toolkit:security-reviewer

Static security analysis: injection, authorization flaws, data exposure and weak crypto, ranked by severity with the attack vector and the fix.

WhenAfter changes to auth, input handling, queries, file paths, tokens or crypto, before any of them deploy.

toolkit:performance-reviewer

Finds measurable bottlenecks, such as N+1 queries, memory leaks, blocking I/O and re-renders, not theoretical micro-optimizations.

WhenAfter changes to hot paths, API endpoints, database queries, loops over collections or rendering code.

toolkit:doc-reviewer

Checks docs against the source: stale references, wrong signatures, missing parameters and broken examples.

WhenAfter changes to .md files, docstrings, JSDoc or API docs, or when a code change may have made existing docs wrong.

toolkit:silent-failure-hunter

Finds code that fails silently: swallowed errors, failures reported as success, and fallbacks that hide breakage.

WhenAfter any change to error handling, catch blocks, fallbacks, retries or async flows, and on every pull request review.

toolkit:pr-test-analyzer

Judges whether tests verify the change: tests with no assertions, tests that only exercise mocks, tests that cannot fail, and weakened or deleted tests.

WhenWhen a diff adds or changes tests, or changes behavior without touching tests.

toolkit:coupling-reviewer

Finds hardcoded account, tenant or platform identifiers and missing extension seams, but only where a second value is already committed in the roadmap, the plan or an existing config surface, never for a speculative one.

WhenAfter changes to config files, tenant or platform wiring, routes or environment plumbing, and whenever a diff hardcodes such an identifier.

1 agent

Browser

toolkit:browser-driver

Drives the browser through claude-in-chrome for multi-step journeys: reproduction runs, checkout and login-gated flows, UI checks, and dashboard or log-viewer trawls. It prefers text extraction over screenshots, reports a login wall as a blocker and never enters credentials, and returns a short run report.

WhenAny browser loop longer than a handful of steps, so the steps and screenshots stay out of the conductor's context.

1 agent

Design

toolkit:frontend-designer

Designs tokens-first UI with one deliberate design principle, avoids generic AI aesthetics, enforces accessibility, states its plan before writing files, and checks its own output with the design detector before delivering.

WhenBuilding or restyling any web UI: pages, dashboards, components.

Usage

Calling an agent

Most agents you never call by hand. The workflow agents run through plan-guide and execution-guide when a session follows the steps itself, or through plan-flow and execute-flow when a flow runs them. The review agents run when there is a diff to check. You can also call any agent directly:

Example prompts
Use the frontend-designer agent to build a pricing card component.
Use the toolkit:code-reviewer on my staged diff.
Use the toolkit:security-reviewer on the auth changes.
Use the toolkit:explorer to find every place we resolve the vault path.

Call an agent by its scoped name, toolkit:<name>, so the plugin copy resolves rather than a project agent of the same name. A project can supply its own agents at <repo>/.claude/agents/, and a project agent wins when it exists. To replace an agent for yourself, see Overrides.
