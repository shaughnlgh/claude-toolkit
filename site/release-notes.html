Release notes

What shipped, by month, newest first. Each merged change is one line, and a release is the line that names its version. An install receives changes only when a new version is released.

November 2026

  • v1.1.0 19 November 2026. The session you start is the lead. Crawl and the post-approval question offer to start a worker session in the background on your yes, instead of handing you a command to paste. The ceiling you pick in the run options is your permission, so a worker does not ask again. A new run options question picks the model and effort of the worker sessions. The lead tells you when a worker needs you, finishes, or stops. It stops a worker once its work is pushed or merged, and otherwise leaves it idle. /toolkit:setup offers the new script rules.
  • v1.0.2 17 November 2026. In auto mode a toolkit agent spawn is no longer refused once before it runs. Session start lists each toolkit agent's model and effort, and the session passes them on the call, so the hook that adds them has nothing to change after the auto mode check.
  • v1.0.1 15 November 2026. The docs, the site, the bug report template and the plugin's own messages name each command and skill with the plugin's toolkit: prefix, as in /toolkit:setup, which is the name a user types. /toolkit:setup offers to add topic-index to an older Toolkit Scripts block in the global CLAUDE.md.
  • v1.0.0 14 November 2026. The first numbered release. The plugin now carries a version number, and an install receives changes when a new version is released.
  • The /toolkit:obsidian-topic command is now /toolkit:topic, and the old name still works as a pointer. The vault config file is now ~/.claude/toolkit-vault.json, and an existing obsidian-sync.json keeps working. vault-fs.sh topic-index writes the vault's topic index, and the repository has a project site, CONTRIBUTING.md and SECURITY.md.
  • The planning grill is a fixed step of every first-draft plan flow, run between a discovery launch and a draft launch, and it states the outcome of the work before its first question.
  • /toolkit:setup asks its questions with a recommended answer first, and the crawl runs the grill on the route that splits work into several plans.
  • One plan can span several sibling repos and nested module repos, and the ship flow merges no repo until every repo has a green pipeline and no open thread.
  • A seat run that finds the main checkout taken joins a queue and waits its turn instead of stopping.
  • Every execute run and seat run writes an evidence note beside the plan note, and plan note changes send only the changed lines.
  • The crawl session is the parent of the work it routes, and it ends the plan route with a plain-text offer to run the plan flow.
  • Planning asks one ticket question before any branch or plan name is derived: use a ticket, create one, or go without.
  • The execute runner indexes the plan note once, and each worker reads only the lines of the plan its job needs.
  • /toolkit:setup offers the auto mode allow rules for each source control host and a per-project override for the conductor guard, each only on a typed reply that names it.
  • In a repo with no CI configuration, the ship flow stops waiting for a pipeline after two minutes, and a review bot that says it did not review is reported as such.
  • The nits run option decides whether the review loops fix small findings, and /toolkit:setup records the review bot logins for each host.
  • The ship flow asks nothing after the run options, works bot review threads in up to three rounds, and cleans up the branch and the worktree after a merge.
  • After plan approval the session asks in plain text whether to run the execute flow here, open a child session, or stop, and a child reports to its parent by message.
  • The execute flow asks nothing after the run options, and a seat run finishes the end-to-end steps that a worktree run deferred.
  • One resolver sets each agent's model and effort on both spawn paths, and the agent files no longer pin either.
  • The plan note records the run options, the crawl asks them once, and a ceiling replaces the git permission question.
  • The execute flow runs the repo's install step in a worktree it opens and defers the Validation Steps that need the running local stack to the seat.
  • The main conversation keeps its rules across a compaction, direct edits by the main conversation are refused, and a run opens a worktree when another session holds the main checkout.

October 2026

  • The verifier's verdict, not the score, decides which review findings get fixed.
  • Session start and the execute flow report which session holds a repo's main checkout.
  • /toolkit:setup detects and offers the git allow rules that auto mode needs.
  • The skills for hand-run planning and execution are renamed plan-guide and execution-guide.
  • The ship flow waits on a pipeline or a bot review in the background and relaunches itself.
  • Each execute runner worker receives only the plan sections its job acts on.
  • Worker agents send an ambiguity to Assumptions and keep Blockers for work they could not do.
  • A rerun of a blocked execute flow continues over the changes the earlier run left in the tree.
  • Review findings carry a score, verification runs in batches, and the review panel is picked by the paths a change touches.
  • The ship flow carries a reviewed slice through commit, push, pull request, merge and tag.
  • The execute flow finishes by settling the findings of its cold read.
  • Topic recall has a --version flag that prints the toolkit content version.
  • The execute flow builds an approved plan and stops with a commit suggestion.
  • The plan flow's workflow is renamed plan-builder so that it no longer shadows the skill.
  • The plan flow turns a brief into a validated plan note.
  • A hook warns when a reply suggests a commit before the remember pass has run.
  • Sessions recall vault topic notes and repo docs, and each slice runs one remember pass.

September 2026

  • The hook tests create their dangling-symlink fixture at test time.
  • Each agent's model is set per agent from a models file, with the code-writing and review workers on the strongest tier.
  • The review-threads skill resolves the threads it fixed on every supported host.
  • The functional test probes for skills give the same result on every run.
  • Corrections that hold across projects can be promoted into the doctrine and the rules.

August 2026

  • Every worker agent receives the write-time rules at spawn.
  • The prose rules join the injected rules, with a catalog of patterns to avoid.
  • A plan note requires a Plain Language Summary section.
  • The merge request review skill reads its access token through the host CLI and refuses a malformed token.
  • The design rules catalog adds form controls, loading feedback and color.
  • The review workflow resolves from the working tree when it runs in this repo.
  • The red team reads the change cold, independent of the session that wrote it.
  • The red team gates each implementation slice before it is handed off.
  • The doctrine explains when to resume a worker and when to start a fresh one, and a writing rule joins the rules.
  • A design rules catalog adds one file per design concern behind an index.
  • The notification hook posts a fixed message instead of untrusted hook input, and session start announces only the rules it injected.
  • Skills write durable knowledge into fixed locations in the repo, always behind a consent question.

July 2026

  • The setup command is renamed /toolkit:setup, and it offers auto-update.
  • A context sentinel and the conductor guard keep the main conversation delegating its work.
  • A read-only ticket skill turns a tracker ticket into a brief.
  • The crawl skill reads new work first and routes it, and the doctrine is injected again after a compaction.
  • The review workflow's agents are namespaced, and discovery goes to the explorer agent.
