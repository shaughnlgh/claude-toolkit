Walkthroughs / Ship flow

Ship flow walkthrough

The ship flow carries a reviewed slice up the ladder suggest, commit, push, mr, merge, release, and stops at the ceiling the plan note records. It prints every external side effect before it starts and asks nothing.

  2. Execute flow

Context

The setup

The project is still todo-api. The execute flow finished on the plan note in ~/notes, and the note records ceiling: merge. The ceiling is the limit on what any flow may do in git:

none
Stops at suggest: the flow hands you the commit commands and runs none.
mr
Commits, pushes, opens the pull request, watches the pipeline and handles the bot review threads.
merge
Adds the merge, and with tag_merge: true it also tags the merge commit.

Step by step

The steps

  1. You type: run the ship flow.

    The flow: The flow reads the run options from the plan note. One verifier reads the host, the remote, the branch, the tree and any open pull request, and the flow derives where the run starts from that observed state, never from your input. It takes the staging list and the commit message from the execute flow's report or from the shipping record on the plan note.

  2. You type: nothing. Read the preview.

    The flow: The flow states the ceiling, in the form "The ceiling is <ceiling>, so the run stops at <stage>." It prints the commit message, the pull request title and body, each path to stage, the fix message templates fix(ci): <failing check> (ship-flow) and fix(review): <thread summary> (ship-flow), the reply template Fixed in <short sha>: <what changed>, the protected paths, and that no commit carries a Co-Authored-By trailer and that human threads are never touched.

  3. You type: nothing.

    The flow: The flow launches the ship-runner workflow. Its agents stage each listed path by name and commit, push the branch, and open the pull request with gh pr create, or the merge request with glab mr create. A verifier watches the pipeline of the pushed commit, and a failing check gets a bounded fix loop. The runner waits for a bot review. Under the default thread_mode: manual it reports a verdict and a recommendation per bot thread and posts nothing. Under thread_mode: automatic it fixes, replies to and resolves each fixable bot thread, and pushes back on and resolves a false one, in up to three rounds. It merges only that exact commit, on a green pipeline with no open thread, and then removes the branch and the worktree when no other session sits in them. When a pipeline or a bot review is slow, the flow waits in the background with watch-mr.sh and relaunches itself.

  4. You type: nothing yet. Read the report.

    The flow: The report opens with the Repo, Branch and Scope lines, then MR: <url> followed by merged <sha>. Under Fixed beyond the plan: it lists each fix commit with its reason, and under Caveats: it lists what is left for you, such as a human review thread. After a merge it gives the undo command, git revert -m 1 <mergeSha> for a merge commit. The plan note records the session as ship-flow finished: merge.

Variations

Other ceilings

Under ceiling: none the report is a commit handoff: the three header lines, a line that begins Suggested commit, and a paste-ready block that names each path. Under ceiling: mr the run stops once the pull request is open, its pipeline watched and its bot threads handled. Raise the note's ceiling to merge and ask again to merge it.

Under thread_mode: manual an open bot thread stops a merge run at mr, so you settle the thread and ask again.

When the execute flow deferred a Validation Step to the seat, the run stops at mr until the seat run passes on the commit it would merge.
