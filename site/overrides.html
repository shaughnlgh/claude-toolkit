Your config wins

The toolkit ships opinionated doctrine, rules, agents and skills. They are defaults, not law. When your own config disagrees, yours wins, so you bend the toolkit to how you and your team work instead of forking it. You meet this the first time a default does not fit.

Precedence

The rule

Most specific wins.

  1. Project config Wins over your global config. Project rules override the doctrine for project-specific matters, and a project agent at <repo>/.claude/agents/ wins when it exists.

  2. Your global config, under ~/.claude/ Your personal scope overrides any doctrine section and the plugin's defaults.

  3. The plugin's defaults What the toolkit ships. It applies wherever you have not said otherwise.

One limit holds at every level: the safety sections, git-safety and security, may be tightened, never loosened. Safety sections explains.

Four types

What you can override

You override a component by placing a copy with the same name under your global ~/.claude/. Each type takes effect in its own way.

  • Doctrine 13 files

    ~/.claude/doctrine/<name>.md

    The session-start hook detects your copy and announces it, and the model reads your copy for that concern instead of the plugin's.

  • Rules 8 files

    ~/.claude/rules/<name>.md

    The session-start hook injects your body in place of the plugin's rule, and subagent-rules.sh does the same for every worker. Keep the file's frontmatter.

  • Agents 14 agents

    ~/.claude/agents/<name>.md

    Claude Code resolves your agent over the plugin's for the bare name, matched by its frontmatter name. Call it as <name>, because toolkit:<name> pins the plugin copy.

  • Skills 20 skills

    ~/.claude/skills/<name>/

    Copied as a whole directory and resolved for the bare name, matched by the directory name or the frontmatter name.

The frontend and design rules are reference-only and never injected, so a rule override has nothing to replace. The content of frontend lives in the frontend-designer agent, so override that instead. design is an index over the rules/design/ catalog. /toolkit:override tells you this if you try.

Agents and skills

Every one of the 14 worker agents and the 20 skills.

Two ways

Say it, or replace the file

  • State it inline

    Write the override as a line in your global ~/.claude/CLAUDE.md. Your personal scope overrides any doctrine section.

  • Replace a whole file

    Put a same-named copy under ~/.claude/ and edit it. /toolkit:override makes the copy for you, or you can drop the file in by hand. There is no pointer to write or maintain.

Doctrine and rules take effect because the session-start hook loads them fresh each session. Agents and skills are resolved by Claude Code itself, with no hook involved, but only when called by their bare name. A copied agent or skill sits outside the plugin, so it still runs the scripts of the installed plugin, and a copied skill reads the doctrine, commands, workflows and other skills it names from there too.

Step by step

The /toolkit:override command

Usage: /toolkit:override [type] [name]

  1. Pick the component. With no argument, /toolkit:override lists everything you can override, grouped by type, and asks which one. With a name, such as /toolkit:override conventions, it detects the type. A name that exists under two types needs the type first: security is both a doctrine file and a rule, so you run /toolkit:override rules security.

  2. It checks the name. It refuses an unknown or ambiguous name, never overwrites an override you already created, and refuses when one of your agents or skills under another file or directory name already carries that frontmatter name.

  3. It copies the plugin's version. It runs scripts/override.sh, which copies the file into ~/.claude/<type>/, or a skill's whole directory. The script finds the plugin root itself and needs no config.

  4. It reports. It names the created path and how that type takes effect, and offers to open the new file for editing.

  5. You edit your copy. Doctrine and rules apply from the next session. Agents and skills apply when you call them by the bare name.

It writes into ~/.claude/ only. Nothing in the plugin changes, and nothing in git.

Worked example

Your own conventions

The conventions doctrine file says to match the codebase's patterns, write docs first, keep comments sparse and single-line, and flag and ask before deviating. To make it yours:

Claude Code
/toolkit:override conventions
  1. The command finds one component with that name, a doctrine file, and copies it to ~/.claude/doctrine/conventions.md.
  2. You edit that file to say how you work.
  3. From the next session on, the session-start hook announces the doctrine override for conventions, and the model reads your copy for that concern instead of the plugin's.

The same steps work for a rule, an agent or a skill. For /toolkit:override code-reviewer, the copy lands at ~/.claude/agents/code-reviewer.md, and you call it as code-reviewer, not toolkit:code-reviewer.

Never silent

What you see each session

When an override is active, the session-start hook announces it.

Doctrine overrides active

Followed by the names, such as conventions. Your global copy is read for that concern.

Rule overrides active

Your rule body was injected instead of the plugin's.

Rule override(s) empty or unreadable, plugin default used instead

Your override file exists but has no usable body, so the hook used the plugin's copy. Fix or remove the override.

Rule file(s) unreadable, no override and no usable plugin default

Neither your override nor the plugin's copy could supply a body for that rule, and the rule is named.

Agent/skill overrides active

Your version resolves for the bare name.

The limit

Safety sections tighten, never loosen

The safety sections are the git-safety and security doctrine files and the security rule. Your override may make them stricter, never looser.

This is stated discipline, not something a hook enforces, because a hook cannot tell a tighter rule from a looser one. It rests on you keeping to it, the same as the rest of the doctrine.

No copy needed

Settings you change without an override

For these, a copied file is the wrong tool.

~/.claude/toolkit-models.json

Changes an agent's model or effort as a {"model": ..., "effort": ...} object per agent, without copying the agent file. /toolkit:setup offers it, and both the agent-model.sh hook and the workflow runners apply it. A plan note's run options override the implementer and verifier entries for that plan.

A copied agent freezes that agent's future updates, and it runs on the default subagent model or the session model until you add model: and effort: lines to its frontmatter.

TOOLKIT_CONDUCTOR_EDITS=1

Lets the main conversation edit project files itself. Set it in the shell for one session, or for one project through /toolkit:setup check 10, which writes it to that project's .claude/settings.local.json.

CLAUDE_PROTECTED_BRANCHES

A comma-separated branch list that replaces the default protected branches for block-dangerous-commands.sh.

TOOLKIT_CTX_SENTINEL=0

Turns off context-sentinel.sh.

TOOLKIT_REMEMBER_GUARD=0

Turns off remember-guard.sh.

TOOLKIT_SESSION_VERBOSE=1

Extends the git briefing that session-start.sh injects.
