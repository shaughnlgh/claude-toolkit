Parent and child sessions

One session plans the work and another builds it. The parent holds the plan and the main checkout. The child runs one plan's flows in that plan's worktree and reports back by message.

How it runs

  • The user describes the work in the parent session. The crawl skill routes it, and on the plan route the parent runs the plan flow. The crawl session is the parent of the work it routes. Its name starts parent- only when a launcher starts it with such a name, such as claude -n 'parent-<slug>', or when the user runs crawl's /rename parent-<planName> line.
  • After approval the parent hands the user one launch command for a new terminal. It starts the child in the main checkout under the name child-<planName>, and its prompt asks for the execute flow and names the parent to report to.
  • The child's execute flow opens the plan's worktree with no question, because the parent holds the main checkout, and runs the repo's install step there.
  • When its flow finishes or stops, the child reports to the parent by message. The parent checks the report against the plan note and tells the user the next step the report names.
  • When the report's Next: line names it, the parent sends the child <planName>: run the ship flow, and the child runs the ship flow within the ceiling the plan note records. A dispatch never raises the ceiling or answers a permission prompt.
  • A child leaves its worktree with keep only after a report whose Next: line tells the user to end the child session, and then ends. After any other report it waits in its worktree for the parent's dispatch.
  • The seat run, which runs the Validation Steps that need the running local stack, needs the main checkout to itself. It runs after the child has ended.
  • Children stay short. A child that would compact is a signal to finish and hand back.
