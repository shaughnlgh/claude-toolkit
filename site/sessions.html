Walkthroughs / Sessions

Lead and worker sessions

The session you start is the lead. On your yes it starts a worker session in the background for a phase such as the execute flow, watches it, and tells you when it needs you or finishes. The worker session runs its flows up to the ceiling you picked and reports back by message.

Sequence

How it runs

  • You describe the work in a session you start, and that session is the lead. The crawl skill routes the work, and once you confirm the route it suggests an optional /rename lead-<name> line. The prefix is optional: any session whose name does not start worker- is a lead.
  • With the run options you pick the model and effort of the worker sessions, once per task. The answer is recorded on the plan note as session_model and session_effort, and every worker session of the task runs on it, never on the lead's model or the machine default.
  • The ceiling you pick in the run options is your permission, given in advance. A worker session runs the execute flow, the ship flow and the merge up to that ceiling and never asks you again.
  • When the lead offers a worker session, it proposes it in one plain-text line that names the session and every flow it will run, such as worker-execute-<key> for the execute flow and then the ship flow. Your typed yes starts it in the background with claude --bg. Types are investigate, plan, execute and ship.
  • An execute worker session opens the plan's worktree, .claude/worktrees/<planName>, and runs the repo's install step there.
  • The lead watches its worker sessions and tells you in its own terminal when one needs you, finishes, stops without reporting, or does not start. A planning grill question and a ticket create confirmation come to you as a question form, which you answer in agent view. Every other question goes to the lead.
  • When its flow finishes or stops, the worker session reports to the lead by message. The lead checks the report against the plan note. To continue inside the grant it sends <planName>: run the ship flow, which never adds a flow and never raises the ceiling.
  • When auto mode refuses a worker session's commit, push, MR or merge inside the grant, the lead runs the ship flow itself up to the ceiling and says so in its final summary.
  • The lead stops a worker session with claude stop once its work is pushed or merged, and otherwise leaves it idle. Stop ends only the process and keeps its worktree and branch.
  • The seat run, which runs the Validation Steps that need the running local stack, needs the main checkout to itself.

Source: doctrine/orchestration.md, section Lead and worker sessions.
