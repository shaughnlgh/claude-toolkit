Slash commands

The toolkit ships 8 slash commands in two groups: setup and vault helpers, and thinking tools you run on demand. You type a command in a Claude Code session, with or without arguments. Each command carries the plugin's toolkit: prefix, as in /toolkit:setup.

  • Setup and vault 4
  • Thinking tools 4

4 commands

Setup and vault

Machine setup, topic notes in the vault, and your own copies of toolkit components.

/toolkit:setup

Checks this machine's toolkit setup in order and guides you through anything missing: plugin state, the vault config, the CLI tools, optional permission and environment offers, leftover local copies that conflict with the plugin, worker models and effort, review bot logins, the per-project conductor-guard override, and the ticket tracker. It ends with a readiness report and a one-line verdict.

RunOn first setup on a new machine, after a plugin update, or when something in the toolkit seems misconfigured. It is safe to re-run.

ChangesNothing without your answer to the question that names the entry or block.

/toolkit:setup

/toolkit:topic

Creates or updates one topic note in the vault, the distilled knowledge layer for stable concepts such as a subsystem or a recurring pattern. A topic note is a claim as of its verified timestamp, so at least one source reference is spot-checked against current code before the note is relied on, and the code wins when they disagree.

Run/toolkit:topic <Topic Name> [repo], any time a topic note needs creating or refreshing outside the normal flow. Inside the flow, plan-guide runs the same process.

ChangesFiles under the vault's root folder, then it rewrites the topic index with vault-fs.sh topic-index. Never project source code or git state. In repo mode, and only after you confirm, it also writes one context doc under docs/context/ in the project repo.

/toolkit:topic "Payment Gateway" my-repo

/toolkit:topic "Caching Strategy"

/toolkit:obsidian-topic

The old name of /toolkit:topic. It forwards its arguments to /toolkit:topic.

/toolkit:override

Copies a toolkit doctrine file, rule, agent or skill into your global ~/.claude/ so your version wins for that concern, without editing the plugin. It refuses unknown or ambiguous names and never overwrites an override you already have.

Run/toolkit:override [type] [name]. With no argument it lists everything overridable. With a name it detects the type. Give the type too only for an ambiguous name.

ChangesWrites into ~/.claude/ only. Nothing in the plugin, nothing in git.

/toolkit:override

/toolkit:override conventions

/toolkit:override rules security

/toolkit:override code-reviewer

Thinking tools

Reflection and red-team commands. None of them changes files or git state. /toolkit:mentor is a mode that lasts for the session, and the rest are one-shot.

/toolkit:glass-box

Audits the provenance of the last answer, or the one about to be given, and surfaces exactly three things: the load-bearing fact, tagged verified or derived; the unchecked assumption, naming the place not looked; and an offer to verify the derived fact now, or the answer restated with the assumption inline.

Run/toolkit:glass-box [what to audit], when an answer feels too confident, an action is hard to undo, or you want the load-bearing assumption surfaced before you act.

/toolkit:glass-box the migration estimate you just gave

/toolkit:mentor

Switches on a learning mode for the rest of the session. It explains plainly first, then asks one deeper question after each step, and moves on only when you explain the idea back in your own words. It runs until you say stop.

Run/toolkit:mentor [topic], when you want to learn a concept rather than only get the answer.

/toolkit:mentor how database indexes actually work

/toolkit:cold-read

Reads back the unstated assumptions behind how you have been talking in the conversation: the premise you treat as fact, the frame that hides options, and the tell you would not endorse out loud. It works only from what you said.

Run/toolkit:cold-read [decision or thread], when a direction feels obvious, or before you commit to one.

/toolkit:cold-read the way I've scoped this migration

/toolkit:mirror-test

Reads your last message back the way a stranger would hear it, with no benefit of the doubt: how it lands, where intent and wording come apart, and the one change that closes the gap.

Run/toolkit:mirror-test [message or text], before you send something that matters, such as a review comment, a message to a colleague or a ticket.

/toolkit:mirror-test the PR review I just drafted
