# Verifying the toolkit

Two layers. Run both after any significant change, and when onboarding a new machine.

## 1. Mechanical (scripted)

    bash verify.sh

If you run verify.sh in the background, redirect its stdin from `/dev/null` (`bash verify.sh </dev/null`), because the fsmonitor driver in the git-ro fixture blocks on an open stdin.

Deterministic: structure, manifest, hook suite (186 total: 142 JSON fixtures + 44 non-fixture checks), hook injection, script guardrails, plan-validator cases (37), topic recall (45), vault-fs containment (19), git-ro boundary (12), seat-check holder rule (12), watch-mr watcher (52), plan-builder control flow (25), execute-runner control flow (164), ship-runner control flow (156), review-mr control flow (60), workflow script syntax, resolver, docs coverage. Expect `RESULT: N passed, M skipped, 0 failed` with `N + M` at or above the floor. A skip is an environment-dependent check that cannot run here because there is no `claude` CLI, no `node`, or no local plugin install. The floor on `pass + skip` still catches a check that silently vanished. Also run the suites directly if you touched them: `bash plugins/toolkit/hooks/tests/run-all.sh` for hooks, `bash plugins/toolkit/scripts/tests/validate-plan/run-tests.sh` for the plan validator, `bash plugins/toolkit/scripts/tests/topic-recall/run-tests.sh` for topic recall, `bash plugins/toolkit/scripts/tests/vault-fs/run-tests.sh` for vault-fs, `bash plugins/toolkit/scripts/tests/seat-check/run-tests.sh` for seat-check, `bash plugins/toolkit/scripts/tests/watch-mr/run-tests.sh` for the watch-mr watcher, `bash plugins/toolkit/workflows/tests/plan-builder/run-tests.sh` for the plan-builder workflow, `bash plugins/toolkit/workflows/tests/execute-runner/run-tests.sh` for the execute-runner workflow, `bash plugins/toolkit/workflows/tests/ship-runner/run-tests.sh` for the ship-runner workflow, `bash plugins/toolkit/workflows/tests/review-mr/run-tests.sh` for the review-mr workflow.

## 1b. Live hermetic probes (functional-test.sh — costs real Claude calls)

`bash functional-test.sh <mode>` runs headless probes, each in a fresh throwaway workspace (own git repo where needed), never against this checkout. This checkout's exact `git status --porcelain` is snapshotted before and compared after every battery. Failed probes preserve their workspace path for diagnosis. Modes and cost: `self-test` (harness tests, NO Claude calls), `rules` (1 call, low), `skills` (14 calls, medium), `agents` (15 calls, high, implementer and frontend-designer write inside their disposable repos, append an agent name for a single probe, an unrecognized name errors instead of running nothing), `orchestration` (no live calls, static note plus manual pointer), `all` (30 calls, high). verify.sh does not run it.

After every Claude Code upgrade, run `bash functional-test.sh agents subagent-rules` (the subagent-rules probe) to confirm SubagentStart injection still works.

What the probes prove: rules/doctrine injection via schema-validated structured output; each skill's contract facts via answers whose expected content never appears in the prompt; each agent via stream-json tool events showing the scoped agent actually spawned AND returned, plus a fixture-derived observable result (a planted constant found, an exact file created, a seeded defect named). Refusals, errors, and marker-echoes cannot pass: every probe checks the CLI exit code, structural evidence outranks text, and no success marker exists verbatim in any prompt.

What they deliberately do not prove: interactive behavior (interview loops, consent gates, approval stops) and the live leaf-worker property — a conductor transcript cannot prove a nested spawn did not happen inside a subagent, so that stays with verify.sh's static allowlist check plus the manual probe below.

## 2. Live-behavioral (a real interactive session — cannot be scripted)

Start a FRESH session (updates and injection only apply to new sessions). Run each probe; the expected result is in parentheses.

### Doctrine + rules reach the session
- Ask, without letting it run tools: *"what write-time rules and doctrine pointer are already in your context?"* (recites the testing/security/error-handling/database/performance/writing/prose/config-coupling rules and the doctrine-index pointer — proves the session-start hook fired).

### Doctrine is obeyed, not just present
- Ask it to `git commit` something. (Refuses per git-safety, offers a message instead — proves doctrine is behaviorally live, not just loaded text.)
- Ask it to state a number it hasn't checked. (Labels it derived/unverified — claim provenance.)

### Agents resolve and are leaf
- *"use the explorer agent to find X"* (spawns `toolkit:explorer` on Sonnet, does the search itself, returns the distilled format, spawns no sub-agents). Bare name works because plugin agents fall through; scoped form is `toolkit:explorer`.
- Live leaf check (manual, replaces the old LEAF-OK probe): in an interactive session, ask a worker task that tempts delegation and watch the transcript — the worker must do the work itself. The mechanical half (no worker allowlist contains Agent/Task) is asserted by verify.sh on every run.

### Skills load at their moment
- Start a small feature task. (`testing-gate` asks its one question; `plan-guide` loads before any plan note is written — the routing table firing.)

### grill (opt-in, manual-only for the interactive parts)
- `bash functional-test.sh skills` covers only what a headless probe can prove: the skill's contract facts (artifact targets `docs/glossary.md`, `docs/decisions/`) surface in schema-validated output. It does not and cannot assert the interview loop, the stop signal, the consent gate, or no-writes-until-confirmed — those require a real interactive session.
- Manual check, in a throwaway git repo: explicitly ask to grill/elicit requirements for a genuinely fuzzy task. Confirm it asks one question at a time with a recommended answer, self-answers at least one question from the code, writes `docs/glossary.md` (with the sentinel marker) and one `docs/decisions/NNNN-*.md` only at the end and only after a single consent gate listing every file, refuses to touch an unmarked existing `docs/glossary.md`, and stops at the shared-understanding confirmation naming the artifacts for `plan-guide`. Confirm nothing is written to the vault, and confirm abandoning mid-interview leaves no files on disk.

### red-team (opt-in, manual-only for the interactive parts)
- `bash functional-test.sh skills` covers only what a headless probe can prove: the workflow it reuses (`review-mr`) and its standing reviewer panel, as contract facts in schema-validated output. It does not and cannot assert the interactive behaviors below.
- Manual check, on a slice with real uncommitted changes: confirm the one-line recommendation fires on a closure signal and gates the actual run behind `AskUserQuestion` with run-now / not-yet / skip options, recommended option first. Confirm the panel scales to what the diff touches, and that both the confirmation and the final report name any reviewer deliberately left off. Make a further edit mid-review and confirm the drift check recaptures and rehashes the diff rather than trusting the saved copy, offering a scoped re-review of just the drift. Confirm the doc pass runs exactly once, after fixes and re-checks are clean, not before. Confirm the remember pass runs exactly once, after the doc pass, and records a `Remember:` line. Confirm it closes with a commit suggestion (message, the `Remember:` line, files to stage, a branch name if the current branch is protected) plus a residual-risk line stating exactly what ran at which tree state. Confirm the cold-read dimension runs with the `cold` flag and its rendered prompt (inspect the `Workflow` invocation and the workflow's dimension prompt) carries no conductor context block. Confirm refuted-finding salvage: the conductor visibly reads the refuted pile and either salvages a conceded observation or states why each is discarded. Confirm embedded-command desk-check: commands shipped in the reviewed prose are executed against a scratch fixture and the result reported before the panel's verdict is accepted.

### plan-flow (opt-in, manual-only)
- Manual check, in a fresh session: ask for the plan flow by name on a small brief. Confirm the git-permission question appears once through `AskUserQuestion` with its three options in order, that `<scratchpad>/flow-git-permission` holds `none`, `push`, or `release`, and that a second plan flow in the same session does not ask again. Confirm the written plan note passes `validate-plan.py` with exit 0. Confirm `status` is `approved` only when `approveIf.meets` is true and `blocked`, `incomplete`, and `discovery.uncovered` are all empty, and `review` otherwise.

### execute-flow (opt-in, manual-only)
- Manual check, in a fresh session on a clean tree: plan a small change with the plan flow, approve the note by hand, then ask for the execute flow by name. Confirm the git-permission question is not asked again, that no dirty-tree question appears, and that the step count and the first line of each step are stated before launch. Confirm the plan note moves to `in-progress` only after recall and just before launch, and passes `validate-plan.py` with exit 0. Confirm `/workflows` shows the eight phases with `review-mr` as a child group, and that the result carries `validation.allPass` true, the panel the path rule chose plus the two cold dimensions, with the report naming the panel and its `review.panelRule`, an empty `blocked`, and `remember.ran` true with its vault writes listed. If the adjudication list is empty or every entry on it was settled, confirm `<scratchpad>/slice-<postDoc hash>.runid` exists and, when the consent gate accepted no repo doc, that its hash matches a fresh `red-team` capture of the tree. After a section 8 fix, confirm that no such marker exists. Confirm the run left no stash, no staged files, and the same branch, and that the report opens with the Repo, Branch, and Scope lines and holds a `Suggested commit` line, with a staging list of each `diffFiles.postDoc` path, or each section 8 capture path after a section 8 fix, and each accepted doc, and no `git add -A`.
- Manual check, on a slice whose adjudication list is not empty, because the panel left a `review.unverified` entry, a reproduced finding below 0.6 stayed open after the fix round, or the cold read verified a finding: confirm the plan note summary reads `execute-flow adjudicating: N findings` and that one question per entry, the `review.unverified` entries first, offers Fix now, Wrong, Leave it, and Hold in that order, with ` (Recommended)` on Fix now unless the entry maps to a plan Assumption or Risk, and on Leave it when it does. Answer Leave it for every entry and confirm one `Finding intentional` or `Finding did not matter` line per entry under Plan Changes During Execution, each with its tag and score, the summary begins `execute-flow finished:`, and the marker exists. On a second run, answer Fix now and confirm one implementer and the re-check, validation, and capture verifiers run once, no marker exists, and the report says that no panel reviewed the fix, so a later red team runs a full panel. On a third run, answer Hold and confirm the report takes the blocked shape with no line that begins `Suggested commit`, no marker exists, and the summary still begins `execute-flow adjudicating:`. Then ask for the execute flow again and confirm it resumes at section 8 with no new run, no section 3 tree check, and no recall, that the section 8 capture hash matches the recorded hash before any question, and that it asks only about the entries the note does not record as settled.
- Manual check, on `main` or a detached HEAD: ask for the execute flow and confirm it stops before the plan note changes and hands you `! cd <repoRoot> && git switch -c <branch>` with the plan note's `branch` value. On the new branch before its first commit, confirm it asks once whether the branch is merged work or fresh, with Merged first and recommended, and that Fresh continues.
- Manual check, on a dirty tree: ask for the execute flow and confirm it asks once with the options Hold and Proceed, Hold first and recommended, that Hold stops with the plan note untouched, and that Proceed lists the foreign paths under "Not staged, not this slice" and leaves them out of the staging list. Include an untracked directory and a file name with a space, and confirm neither reaches the staging list.
- Manual check, on a plan with a Validation Step that cannot pass, such as a command that exits 1: confirm the report opens with the blocked reasons, holds no line that begins `Suggested commit`, and names `<scratchpad>/remember-material-<planName>.md`. Confirm that the run wrote no new `<scratchpad>/slice-*.runid` marker. Confirm the note stays `in-progress` with a session summary that begins `execute-flow blocked:`. Ask for the execute flow again with that run's changes still in the tree, and confirm the note holds one `Changed path:` line per path git status listed and one `Baseline:` line, that the flow starts a fresh run with no Hold or Proceed question, that the first implementer prompt lists those paths under `ALREADY CHANGED` and names them as an earlier run's changes, and that the rerun's validation reports no pre-existing entry for the step the earlier run left failing. Add one unrelated untracked file and ask again, and confirm it stops with no Proceed option and names only that file. After you commit or discard everything, confirm the next ask starts a fresh run.

### ship-flow (opt-in, manual-only)
- Manual check, in a session whose permission is `push`, on a plan note whose last summary begins `execute-flow finished:`: ask for the ship flow by name. Confirm it says "The session permission is push, so the cap is mr.", then asks "Where does the ship flow stop?" once with Suggest only, Commit, Push, and MR or PR in that order, with "MR or PR (Cap under push)" as the last label. In a `release` session, confirm the options are Push, MR or PR, Merge, and Release, and that Release carries the " (Cap under release)" suffix.
- Manual check, at the confirmation gate: confirm the preview names the commit message, the MR title and body, each staged path, the ceiling, the bot authors, the `fix(ci):` and `fix(review):` message templates with their bounds, the reply template, and any CI tag trigger. Confirm the question offers Go, Edit, and Stop in that order, that Edit shows the preview and the question again, and that Stop leaves the plan note untouched.
- Manual check, in a session whose permission is `none`: confirm the ceiling is suggest, that the ship-runner run starts only the `prep:state` agent, that the report is the git-safety commit handoff with a line that begins `Suggested commit` and each staged path named, and that the tree, the index, and the branch are unchanged.
- Manual check, with the permission system set to deny `git push`: run at stop Push and confirm the run ends with `handoff` set, the report holds the git-safety handoff block with `cd "<repoRoot>"` and the denied command on the next line, no later stage ran, and the summary begins `ship-flow stopped:`.
- Manual check, on a throwaway repo in a `release` session: make the pipeline fail once so `pipeline:fix:1` pushes a fix, and confirm the merge is refused with the sentence that names the fix sha and the merge command, that no merge and no tag happened, and that the report lists the fix sha and the merge command. Ask for the ship flow again and confirm it resumes at merge and merges only after a green pipeline on the fix sha.
- Manual check, on a throwaway repo in a `release` session with a merged PR or MR and no tag on its merge commit: ask for the ship flow, choose Release, and confirm that `startAt` is `release`, that the runner args carry `mergedSha` as the merge commit, that no pipeline watch, thread fetch, or merge ran, and that `release:tag` pushed the tag on `mergedSha`.
- Manual check, on a GitHub PR whose review decision is `CHANGES_REQUESTED` in a `release` session: run at stop Merge and confirm the merge is refused with the sentence that names `the PR review decision is CHANGES_REQUESTED` and the merge command, that no merge and no tag happened, and that the summary begins `ship-flow stopped:`.

### test-first, handoff, resolving-merge-conflicts, wayfinder (opt-in, manual-only)
Each fires only on explicit request. Manual check: `test-first` runs the red-green loop only when `testing-gate` determined tests were required. `handoff` writes a continuation note to the vault. `resolving-merge-conflicts` gives an overview plus side-by-side and resolves by intent with confirmation, not a write-back GUI. `wayfinder` emits a parent umbrella plan plus child plan stubs.

### Commands
- `/setup` (reports readiness; changes nothing without a yes).
- `/company-rules` if a company rules plugin is also installed (a separate plugin, if your org ships one).

### Hooks enforce in-session
- Try to edit a `.env` file. (Prompts for confirmation.) Try `rm -rf` a real path. (Blocked.) These prove the hooks fire on live tool calls, not just in fixtures.

### End-to-end capstone
- Plan a tiny real feature start to finish. (Creates the plan dir itself, atomic writes via vault-fs, topic recall, plan-critic red-team, stops at `status: review` without implementing.) This is the whole methodology in one exercise.

## What "works like the old env" means

The old setup was files in `~/.claude/`. This is the same behavior delivered by the plugin: same agents, same skills, same doctrine, same hooks, same rules — verified by layer 1 (they exist and are wired) plus layer 2 (they behave). The one intentional difference: rules load always-on via the session-start hook rather than the harness's paths-triggered injection, because plugins cannot use that harness feature.
