# Workflows

Workflows are multi-agent orchestrations the toolkit ships as scripts under `plugins/toolkit/workflows/`, run through the Workflow tool rather than a single agent turn. There are four: `review-mr`, driven by the `gitlab-mr-review` skill against fetched MR diffs and the `red-team` skill against local uncommitted slice diffs (passing `repoState`), `plan-builder`, driven by the `plan-flow` skill to turn a brief into the body of a plan note, `execute-runner`, driven by the `execute-flow` skill to execute an approved plan note end to end, and `ship-runner`, driven by the `ship-flow` skill to commit, push, open the MR or PR, watch the pipeline, work the bot review threads, merge, and tag a reviewed slice. A workflow and a skill register in the same `toolkit:` namespace, so the script cannot share the skill's name.

Child workflows: a script runs another workflow as a child with `workflow(nameOrRef, args)`. The runtime runs the child inline and returns the child's return value. The call throws on an unknown name or a child failure, and returns null when the child is stopped. `agent()` likewise returns null for a stopped agent. `execute-runner` calls `review-mr` as a child, by the name `toolkit:review-mr` or by the ref its `reviewMr` arg names. `review-mr`, `plan-builder`, and `ship-runner` call no child.

## review-mr.js

Multi-dimension MR review. It runs two phases:

- **Review**: fans out the toolkit reviewer agents (`toolkit:code-reviewer`, `toolkit:security-reviewer`, `toolkit:silent-failure-hunter`, `toolkit:performance-reviewer`, `toolkit:pr-test-analyzer`, `toolkit:coupling-reviewer`) plus any MR-specific custom dimensions, each reading the saved diff and reporting findings against a shared schema (title, file, line, tag, impact, likelihood, confidence, citation, detail, failure scenario). The tag is `important`, `nit`, or `pre-existing`, and impact, likelihood, and confidence each run from 0 to 1. The citation is a file:line the reviewer read. The script scores each finding as 0.5 impact + 0.3 likelihood + 0.2 confidence, rounded to two decimals, and moves a finding with no citation to `dropped` with the reason `no citation` before any verifier sees it. A dimension that can't answer something from the diff or repo returns it as an `open_questions` entry instead of guessing.
- **Verify**: one `toolkit:verifier` on sonnet per dimension checks that dimension's cited findings in chunks of eight, labelled `verify:<key>` for the first chunk and `verify:<key>:<n>` after it. The prompt lists each finding by its index in the chunk with its tag, score, file:line, and title, and the verifier returns one verdict per index. The verifier reproduces each finding scored 0.6 or above before it confirms or refutes it, only by tracing the code or by running commands in a fresh fixture under the system temp directory outside `repoRoot`, which it never modifies, and a finding is real only if the code path executes, the failure scenario is reachable, the citation holds, and nothing else already handles it. It reads each finding below 0.6 with its citation, may raise its score, and reproduces it first when it raises the score to 0.6 or above. For a code finding at 0.6 or above, the reproduction is the trace of the code path or the fixture run and its output. For a real code finding below 0.6, the reproduction is the cited line as the verifier read it and what it shows. A doc finding is one whose file is under a `docs/` directory or ends in `.md`. The verifier reproduces a doc finding at every score by quoting, with its file:line, the code line, rule line, or doc line that makes the doc wrong, and refutes it only by quoting the line in the tree that makes the doc right. A plan note line, an Assumption, a Risk, an approval, or an owner's acceptance is never that line. An accepted Assumption or Risk settles scope and coverage, never a breach of a written rule or a doc line the tree contradicts, so "the plan decided it", "settled at approval", "the owner accepted this", and a subjective preference are not refutations. The verifier lowers the `finalScore` of a finding that cites a file under `rules/`, `doctrine/`, `CLAUDE.md`, `AGENTS.md`, or `.claude/rules` only when the cited rule does not say what the finding claims, never on plan or design grounds. The verifier owns `finalTag`, `finalScore`, and `reproduction`. For a code finding at 0.6 or above, `reproduction` holds the command or trace the verifier ran and the output it saw, and is empty when it ran nothing. The script sets `reproduced` true only when `reproduction` is not empty. A finding the verifier omits goes to `unverified` with the reason `no verdict`. A chunk whose verifier returns nothing puts the dimension's name in `verifierDead` and every finding of that chunk in `unverified` with the reason `verifier died`.

The workflow then routes each finding by the verifier's fields. A real finding with `finalTag` `pre-existing` goes to `preExisting`. Any other real finding goes to `confirmed` when `reproduced` is true, at any `finalScore`. An unreproduced real code finding at `finalScore` 0.6 or above and an unreproduced real doc finding at any score go to `unverified` with the reason `not reproduced`. An unreproduced real code finding below 0.6 is a nit: the five with the highest `finalScore` go to `nits`, and the rest go to `dropped` with the reason `nit cap`. A doc finding is never a nit. A refuted code finding and a refuted doc finding with a reproduction go to `refuted` with the verifier's reasoning as the reason. A refuted doc finding with an empty reproduction goes to `unverified` with the reason `not reproduced` and keeps the verifier's verdict and reasoning. The reviewer's own tag decides nothing. The calling skill settles every `unverified` and `openQuestions` entry and writes the report.

It returns `{confirmed, nits, preExisting, refuted, unverified, dropped, openQuestions, dead, verifierDead, panel, dimensions}`. `confirmed`, `nits`, `preExisting`, and `unverified` hold whole findings with `dimension` and `score`, plus `verdict`, `finalTag`, `finalScore`, `reproduction`, `reproduced`, and `reasoning` when the verifier returned a verdict, and `reason` for an `unverified` entry. `refuted` and `dropped` hold `{title, file, line, dimension, tag, finalTag, citation, reproduction, score, finalScore, reason}`, so a refuted entry carries the line the verifier rested on. A `dropped` entry with the reason `no citation` never reached a verifier and has no `reproduction`. `dead` names the reviewers and dimensions whose agent returned nothing, a registry reviewer by its agent type, such as `toolkit:code-reviewer`, and a custom dimension by its key. `verifierDead` names the dimensions that lost a verifier chunk, by the same names as `dead`. `panel` is the registry reviewer list the run used, and `dimensions` holds the custom dimension keys.

Reviews are run against the diff plus a local checkout at `repoRoot`, whose state the `repoState` argument declares — a target-branch checkout for `gitlab-mr-review`, the post-change working tree for `red-team` — so any claim about existing code, callers, or framework behavior is verified against that declared state.

Invoked by the `gitlab-mr-review` or `red-team` skill, as a child of `execute-runner`, or directly, with:

```
args: {diffPath, repoRoot, contextBlock, dimensions?, registryReviewers?, repoState?}
```

- `diffPath` (required) — absolute path to the saved unified diff.
- `repoRoot` (required) — absolute path to the local repo the review verifies claims against, whose state `repoState` declares: a target-branch checkout for `gitlab-mr-review`, the post-change working tree for `red-team`.
- `contextBlock` (required) — env facts, a summary of the change under review, and verification instructions, built by the conductor (the skill) before the workflow runs. The callers append the default branch's `REVIEW.md` to it under `REVIEW RULES (REVIEW.md on the default branch):`, so the registry reviewers, the non-cold custom dimensions, and every verifier read the repo's review rules. The workflow takes no separate argument for them.
- `dimensions` (optional) — `[{key, prompt, cold?}]`, extra MR-specific review angles (contract impact, framework wiring, conventions, data/upgrade safety) the registry reviewers won't cover; `cold: true` omits the conductor's `contextBlock` from that dimension's prompt so it reads the diff without the author's framing.
- `registryReviewers` (optional) — override the default set of six reviewer agent types. Names must be fully qualified as the harness registers them (plugin agents are namespaced, e.g. `toolkit:code-reviewer`).
- `repoState` (optional) — sentence describing the state of the tree at `repoRoot`, substituted into the reviewer and verifier prompts; defaults to the current MR target-branch sentence.

Tests: `bash plugins/toolkit/workflows/tests/review-mr/run-tests.sh` runs 60 control-flow cases that drive the script with a label-keyed agent stub and a `pipeline()` stub that passes each item to the second stage, as the runtime does: arg validation, the score and the citation drop, the verifier prompt and its chunks of eight, each routing path, the doc-finding routes, the nit cap, a dead reviewer, a dead verifier, and the return keys. The suite needs `node`, and `verify.sh` also runs it.

## plan-builder.js

Plan flow. It turns a brief into every section of a plan note and runs five phases:

- **Discover**: a `toolkit:explorer` agent splits the brief into 2 to 5 investigation areas, each with one question and the paths to start from. One `toolkit:explorer` per area then answers its question with file:line facts, gaps, risks, and a reuse ladder result. If the scoping agent dies, the flow uses one whole-brief area.
- **Draft**: a `toolkit:planner` agent writes every plan section from the findings, plus a branch name and related topics.
- **Invert**: a `toolkit:plan-critic` agent runs a pre-mortem and returns a verdict of `proceed`, `revise`, or `stop`, with objections, tripwires, and walk-away checks. On `revise`, the planner resolves the material objections and the critic runs again, for at most `maxRounds` revisions.
- **Red team**: a second `toolkit:plan-critic` reads the plan cold, without the brief, the recall hits, or the evidence. If it raises material objections, the planner revises the plan once more.
- **Judge**: if `approveIf` is set, a `toolkit:verifier` agent judges whether every clause of the goal maps to an implementation step and a validation step that proves it. The judge defaults to false.

The script writes no files and runs no git. The `plan-flow` skill writes the returned sections to the plan note, validates the note, and sets `status` to `approved` only when `approveIf.meets` is true and `blocked`, `incomplete`, and `discovery.uncovered` are all empty.

Invoked by the `plan-flow` skill (or directly) with:

```
args: {brief, repoRoot, repoName, planName, recallHits, knownEvidence?, approveIf?, maxRounds?}
```

- `brief` (required): the task description the plan answers.
- `repoRoot` (required): absolute path to the repo the explorers, planner, and critics read as ground truth.
- `repoName` (required): the repo name every prompt carries.
- `planName` (required): the plan note name.
- `recallHits` (required): the text output of `topic-recall.py` for the brief's key terms.
- `knownEvidence` (optional): facts the conductor already holds. The scoping agent skips areas these settle.
- `approveIf` (optional): a goal sentence. The Judge phase runs only when it is set.
- `maxRounds` (optional): a non-negative integer that caps the revise rounds in the Invert phase. Default 2 when absent or null. Any other value that is not a non-negative integer, such as the string "0", -1, or 1.5, makes the script throw an Error that names the value.

The script throws if any required arg is missing or is not a non-empty string.

It returns `{plan, branch, relatedTopics, discovery, rounds, tripwires, walkAway, coldObjections, coldVerdict, finalVerdict, openObjections, critiqueStale, blocked, approveIf, incomplete}`:

- `plan`: the 11 section bodies without heading lines, keyed `objective`, `plainLanguageSummary`, `currentContext`, `assumptions`, `affectedFiles`, `implementationSteps`, `validationSteps`, `risks`, `rollbackNotes`, `openQuestions`, `relatedTopics`.
- `branch` and `relatedTopics`: the planner's branch name and topic names for the note frontmatter.
- `discovery`: `{areas, uncovered}`, the area names and the areas whose explorer died.
- `rounds`: one `{verdict, materialCount}` per Invert critique, with `verdict: incomplete` for a critique that died.
- `tripwires` and `walkAway`: from the last Invert critique that returned, or empty arrays when none returned.
- `coldObjections`: the cold critic's objections, or `null` if it died.
- `coldVerdict`: the cold critic's verdict, or `null` if it died.
- `finalVerdict`: `proceed`, `revise`, or `stop` from the last Invert critique that returned, or `incomplete` when none returned.
- `openObjections`: the material objections, each `{section, claim, evidence, fix, material}`, that no revise applied. These are the last Invert critique's material objections when no successful revise came after it, whatever its verdict, plus the cold critic's material objections when `revise:cold` died or returned the plan unchanged.
- `critiqueStale`: `true` when the returned plan differs from the draft the last returned Invert critique saw. A successful revise followed by a dead critique, or a successful cold revise, sets it. In that case `tripwires` and `walkAway` describe an earlier draft.
- `blocked`: one plain sentence per reason the plan must not be auto-approved, or an empty array.
- `approveIf`: `{meets, reasons, unmetGoals}`, or `null` when no goal was set.
- `incomplete`: the labels of the stages that died.

`blocked` gets a sentence for each of these: a `stop` final verdict, a `proceed` final verdict that still carries material objections, a `revise` final verdict left open after `maxRounds` revisions, a `revise` final verdict with `maxRounds` 0, a dead `invert:0`, a dead `red-team:cold`, a `stop` cold verdict, a cold revise that returned the plan unchanged, each dead `revise:N` or `revise:cold`, and `critiqueStale` true. The judge prompt carries `finalVerdict` and `openObjections`, and the judge must return `meets: false` while a material objection stays open or the final verdict is `stop`.

A dead stage never fails the run. Its label (`discover:scope`, `invert:N`, `revise:N`, `red-team:cold`, `revise:cold`, `judge`) lands in `incomplete`, and a dead judge also yields `meets: false`. A dead area explorer lands in `discovery.uncovered`. The one exception is the draft: if the planner returns nothing, the script throws, because no plan exists to return.

Tests: `bash plugins/toolkit/workflows/tests/plan-builder/run-tests.sh` runs 25 control-flow cases that drive the script with a scripted agent stub: dead stages, each verdict path, the cold revise paths, the stale-critique cases, and the judge prompt. The suite needs `node`, and `verify.sh` also runs it.

## execute-runner.js

Execute flow. It executes an approved plan note and runs eight phases in order. The script calls one agent at a time, except in the Red team phase, where the `review-mr` child fans out its panel, its cold dimensions, and their verifiers in parallel:

- **Prep**: a `toolkit:verifier` (`prep:baseline`) records the branch, the `git status --porcelain` lines, and a baseline run of the repo's verify or test command with the names of the checks that fail. It runs `verifyCommand` when that arg is set, and otherwise finds the command in AGENTS.md, CLAUDE.md, VERIFY.md, or the package manifest. It runs any verify or test suite, such as `bash verify.sh`, with stdin from `/dev/null`, because a suite that reads stdin hangs when stdin is a pipe. The validation verifiers carry the same stdin rule. If it finds no verify command, it runs none and returns `command` as `none`, `exitCode` as -1, and `failing` as the one sentence `No verify command was found`.
- **Implement**: one `toolkit:implementer` per Implementation Step, labelled `implement:<n>`, in plan order. No agent prompt carries the plan note whole: each worker gets the sections its job acts on. An implementer prompt carries the plan's Objective, Current Context, Assumptions, Affected Files, Validation Steps, Risks, and Plan Changes During Execution, each as a labelled block or `none`, then a `STEPS` block that lists every Implementation Step by its heading line with ` (your step)` on the worker's own, the worker's own step in full under `YOUR STEP`, and the paths that earlier steps changed under `ALREADY CHANGED`. The heading line is the marker line that starts the step under the splitting rule below, with `###` and the whitespace after it stripped, so text before the first marker never supplies step 1's heading. A section with no step marker is one step, and its heading line is its first line without a trailing period. The prompt says the other steps are not the worker's work. Each worker returns `changedPaths`, `deviations`, `checksRun`, `result`, `blockers`, and `topicMaterial`. `blockers` holds only work the worker could not do, and a caveat goes in `deviations`.
- **Verify**: the script splits the Validation Steps with the Implementation Steps rule below and hands them to the verifier as numbered `STEP <n>:` blocks, asking for exactly that many results in order. A `toolkit:verifier` (`verify:validation`) runs each STEP it can run here and reports it as `pass` or `fail` with evidence, `manual` with the reason for a step that needs a human or another session, or `pre-existing` for a step that fails only on a check the baseline already lists as failing. If a step fails, one `toolkit:implementer` (`fix:validation`) fixes only what makes the failing steps pass, and `verify:revalidation` runs the steps again. The fix prompt carries the plan's Objective, Assumptions, and Plan Changes During Execution, the paths changed so far under `CHANGED PATHS`, and the failing steps with their evidence. Manual and pre-existing steps never trigger the fix and never block. A run whose steps are all manual does not block, and `validation.allPass` is false. After every validation run, including `verify:final`, the script compares the number of results with the number of Validation Steps. On a mismatch it blocks. After `verify:validation`, a mismatch also adds one sentence per `fail` result and stops the run the way a step still failing after revalidation does: no fix round, no child, and no later phase.
- **Red team**: a `toolkit:verifier` (`diff:red-team`) runs exactly the capture commands from `repoRoot` and nothing else, writes the slice diff into `scratchDir`, and returns `diffPath`, `hash12`, `empty`, and `paths`. `paths` holds the repo-relative paths the capture covers: the output of `git -c core.quotePath=false diff HEAD --name-only` plus `git -c core.quotePath=false ls-files --others --exclude-standard`. The `core.quotePath=false` setting keeps a non-ASCII filename as written, because git otherwise prints it in quoted octal form. Each untracked file is diffed with `git diff --no-index -- /dev/null "$f"`, where `--` stops a filename that starts with a dash from reading as a git option. The script then picks the panel from `paths` plus the implementers' changed paths and calls the `review-mr` child, by the `reviewMr` ref or by `toolkit:review-mr` when that arg is absent, with that diff, a context block, the `red-team` repoState sentence, the panel, and the two cold dimensions `cold-read` and `external-reviewer`. The panel rule takes the first match. A path that equals or starts with a high-risk prefix picks all six reviewers, rule `high-risk path`. A non-empty path list where every path is under `docs/` or is a top-level `.md` file, such as `README.md`, picks `toolkit:code-reviewer` alone, rule `docs only`. Any other `.md` path, such as a skill or agent file, gets no docs-only treatment. Anything else picks the standing three, `toolkit:code-reviewer`, `toolkit:silent-failure-hunter`, and `toolkit:pr-test-analyzer`, rule `standing`. The built-in high-risk prefixes are `plugins/toolkit/hooks/`, `plugins/toolkit/scripts/`, `plugins/toolkit/workflows/`, and `.github/`. Each bullet under the `## High-risk paths` heading of `reviewRules` adds its first token, with backticks, quotes, and trailing punctuation stripped. The context block carries the plan Objective, the paths changed so far, a `SETTLED DECISIONS` block with the plan's Assumptions and Risks, the repo rules note, the `red-team` instruction to run embedded commands against a scratch fixture, and, when `reviewRules` is set, its text under `REVIEW RULES (REVIEW.md on the default branch):`. The `SETTLED DECISIONS` block tells the panel that the user accepted those sections at approval, so a finding that only restates one of them, or asks for scope or coverage the Assumptions exclude, is not a finding, unless the tree contradicts the decision, in which case the panel reports it as a normal finding. The block also says that a breach of a written rule in `rules/`, `doctrine/`, `CLAUDE.md`, `AGENTS.md`, or `.claude/rules`, or a doc line the tree contradicts, is never settled by an Assumption or Risk, so the panel reports it as a normal finding and never lowers its score on plan grounds. The `review-mr` verifier brief carries the same rule, because a verifier reads both. The cold dimensions' own prompts never see the context block, but `review-mr` passes it to the batched verifier of every dimension, so the verifiers of cold-dimension findings do see the `SETTLED DECISIONS` block. If the child's `dead` list is not empty, the script blocks and still runs the fix loop on the confirmed findings. If the child returns no `dead` array, as a `review-mr` that predates the field does, the script also blocks. If the child's `verifierDead` list is not empty, the script blocks with its own sentence beside any `dead` sentence. A child that returns no `verifierDead` array does not block on it. An `unverified` entry never blocks and passes through for the `execute-flow` skill to settle.
- **Fix**: `confirmed` holds every finding the verifier reproduced, whatever its `finalScore`. When the child returned confirmed findings, the open list is those findings plus the child's `nits`. When `confirmed` is empty, no round runs and the nits pass through in `review.nits`. For each round up to `maxFixRounds` while a confirmed finding stays open, a `toolkit:implementer` (`fix:<round>`) gets the plan's Objective and Assumptions, the paths changed so far under `CHANGED PATHS`, the open confirmed findings under `CONFIRMED FINDINGS:`, and the open nits under `NITS:`, each finding with its tag, final score, reproduced state, citation, detail, and failure scenario. It fixes each confirmed finding with the smallest change. For a confirmed finding tagged `important` at `finalScore` 0.6 or above, it fixes every instance of that class of defect in the slice. It fixes a confirmed finding tagged `nit`, or any confirmed finding below 0.6, only at its cited line, and fixes a nit only at its cited line and only when the tree confirms it. A `toolkit:verifier` (`recheck:<round>`) returns one result per open entry. A finding is resolved when a recheck result with the same file and title reports `resolved: true`. Two findings with the same file and title resolve together, because `review-mr` returns no finding id. A nit left open after every confirmed finding resolves starts no further round. A `fix:<round>` that returns blockers ends the fix loop, so no recheck and no later round runs. After the last round, the step-back sentence counts only the open confirmed findings at `finalScore` 0.6 or above. An open confirmed finding below 0.6 never blocks and passes through in `review.open` for the `execute-flow` skill to adjudicate.
- **Cold read**: a `toolkit:verifier` (`diff:final`) captures the diff again. If that capture is empty, the script blocks and skips the cold read. Otherwise one `toolkit:code-reviewer` (`cold:read`) reads it with the repoState sentence, the `external-reviewer` prompt, an `ALREADY REPORTED BY THE PANEL:` list, and no context block. The list holds the `<file>: <title>` key of each `confirmed`, `nits`, and `preExisting` entry. The prompt tells the reader not to report a listed finding again, and to report a finding the panel refuted, dropped, or left unverified, because such a claim is not settled. The reader treats comments and doc sentences as claims and marks a finding verified only when the tree confirms it. It returns each finding with file, title, issue, fix, tag, impact, likelihood, confidence, an optional citation, and verified, and the script adds the panel's `score`. A verified finding with a citation is returned in `coldResidual` for the `execute-flow` skill to adjudicate with the user and does not block. Any other finding is returned in `coldUnverified` and does not block. The script runs no cold fix.
- **Doc pass**: only when `blocked` is still empty, a `toolkit:implementer` (`doc:pass`) applies the Doc Update Pass from `skills/execution-guide/SKILL.md` under `pluginRoot` to the slice. Its prompt carries the plan's Objective, Affected Files, and Related Topics, and the paths changed so far under `CHANGED PATHS`. If a fix round ran or the doc pass changed files, `verify:final` runs the Validation Steps once more with no fix round. `diff:post-doc` then captures the tree the user commits. If that capture is empty, the script blocks and sets the `postDoc` hash, path, and paths to null. A blocked slice skips `doc:pass`, `verify:final`, and `diff:post-doc`, adds no new `blocked` sentence, and defers the doc pass to the conductor, the same as the remember pass.
- **Remember**: only when `blocked` is still empty, a `toolkit:implementer` (`remember:pass`) runs the remember brief from the obsidian-topic command with its values filled in and returns `proposals` (each with `path`, `action`, `scratch`, and `factsFrom`), `topicsUpdated`, `rememberLine`, and `blockers`. The prompt carries the plan's Related Topics section under `RELATED TOPICS`, so the worker can stub a topic the plan names. A remember worker that returns blockers blocks the run and sets `remember.ran` to false.

Every agent prompt except the remember pass carries the git rule: in `repoRoot`, git is read-only, limited to `git status`, `git diff`, `git log`, `git ls-files`, `git branch --show-current`, `git remote get-url`, `git symbolic-ref` with one ref argument, and `git merge-base --is-ancestor`, and mutating git is allowed only inside a fresh fixture under `scratchDir`. A `-c core.quotePath=false` prefix on one of these commands keeps it read-only. The remember prompt says to run no git command. The scratch-only rule, that embedded commands run only against scratch fixtures under `scratchDir` and never against `repoRoot`, goes only to the review panel context block, both cold dimension prompts, and `cold:read`. The implementers and the validation verifiers run the plan's own commands in `repoRoot`, so they get the git rule alone. The implement, fix, doc pass, and remember prompts carry the blocker rule: a worker that meets a denied or impossible step, command, or tool call records it as one `blockers` sentence and stops instead of working around it, and that `blockers` holds only such work and is empty when the work is done. The implement, fix, and doc pass prompts and the `verify:validation`, `verify:revalidation`, and `verify:final` prompts also carry the hook rule (`HOOK_RULE`): the dangerous-commands hook refuses any command text, including inside a heredoc, that holds a recursive force-delete of a shell variable, a bare dot or double dot, a bare glob, a path with a `/../` segment, the root, the home dir, or a listed system dir, so a worker removes a scratch fixture by its literal absolute path under `scratchDir`. The implement, fix, and doc pass prompts also carry `HOOK_WRITE_RULE`, which tells the worker to create a file that must hold a command the hook refuses, such as a script's recursive delete of a variable, with the Write tool, never through a heredoc. The `verify:validation`, `verify:revalidation`, and `verify:final` prompts get only the refusal and literal-path sentences, because `toolkit:verifier` has no Write tool and those prompts say to change no file.

The script reads each section of `planContent` from its section heading to the next section heading outside a fenced code block, so a fenced line that starts with `## ` stays inside the section. A section heading is a line outside a fence that starts with `##` followed by a space or tab, and it names a section when the text after `##`, trimmed, equals the section name. A `###` line is not a section heading. A fence opens on a line of 3 or more backticks or tildes with an optional info string, and it closes only on a line of the same character at least as long with nothing else on it. These are the rules `scripts/validate-plan.py` applies. A numbered line is a line outside a fence that opens with a number followed by `.` or `)` and a space. A subheading is a line outside a fence that starts with `###` followed by a space or tab. The numbered lines form a single list when their numbers, in order, run 1, 2, 3 with no restart and no gap. Inside Implementation Steps, the first of three rules that applies splits the steps. First, if at least one subheading starts with a number followed by `.` or `)` after `###`, those numbered subheadings split the steps and every other line stays inside its step. Second, every subheading starts a step, and its heading is the text after `###`, when all of these hold: the section has at least two subheadings and none of them is numbered, no numbered line comes before the first subheading, and the numbered lines do not form a single list that runs across a subheading. A single list that sits entirely under one subheading, a section with no numbered lines, and numbered lines that restart or skip a number all meet the last condition. Third, otherwise a numbered line starts a step when its number is greater than every number before it, so a list that restarts at 1, such as a Tripwires list under its own subheading, stays inside the step before it. Text before the first step joins step 1. A section with no step marker is one step. The script splits the Validation Steps with the same rule. With numbered Validation Steps above the first subheading, a trailing paragraph or subheading such as a Tripwires block joins the last numbered STEP, and so does a list under it that is bulleted or restarts at 1. With numbered checks under their own subheading followed by a Tripwires subheading, the section gives one STEP per subheading. With bullets or prose under two or more subheadings, each subheading starts a STEP. With bullets or prose under fewer than two subheadings, the whole section is one STEP and gets one result.

The script writes no file itself, and no worker runs mutating git in `repoRoot`. Its verifiers write the diff captures under `scratchDir`, and on a clean run the remember worker writes vault notes and `remember-*.md` scratch files. The `execute-flow` skill records the result on the plan note, runs the consent gate, adjudicates each `review.unverified` entry and each `coldResidual` finding with the user, writes the slice marker, and suggests the commit.

Invoked by the `execute-flow` skill (or directly) with:

```
args: {planName, repoRoot, repoName, planContent, recallHits, scratchDir, pluginRoot, vaultRoot, knownEvidence?, verifyCommand?, baselineFailing?, priorChangedPaths?, maxFixRounds?, reviewRules?, reviewMr?}
```

- `planName` (required): the plan note name.
- `repoRoot` (required): absolute path to the checkout the workers change.
- `repoName` (required): the repo name every prompt carries.
- `planContent` (required): the full text of the approved plan note.
- `recallHits` (required): the text output of `topic-recall.py` for the plan's key terms.
- `scratchDir` (required): absolute path to the session scratchpad, where the captures and fixtures go.
- `pluginRoot` (required): absolute path to the installed plugin root, which the doc pass and the remember pass read from.
- `vaultRoot` (required): the vault root folder, `<vault_path>/<root_folder>` from `~/.claude/obsidian-sync.json`.
- `knownEvidence` (optional): facts the conductor already holds.
- `verifyCommand` (optional): the command the baseline verifier runs.
- `baselineFailing` (optional): a list of check names that replaces the baseline verifier's failing list, for a rerun over a tree that already holds the slice. An empty list makes every failing check block. A value that is not an array of strings makes the script throw.
- `priorChangedPaths` (optional): repo-relative paths an earlier blocked run left in the tree. The script seeds its changed list with them, so they appear under `ALREADY CHANGED` in every implementer prompt, under `CHANGED PATHS` in the doc pass, and in `changedPaths`. A value that is not an array of strings makes the script throw.
- `maxFixRounds` (optional): a non-negative integer that caps the fix rounds after the panel. Default 1 when absent or null. Any other value that is not a non-negative integer makes the script throw an Error that names the value.
- `reviewRules` (optional): the text of `REVIEW.md` on the default branch. The script appends it to the panel context block and reads its `## High-risk paths` bullets into the panel rule. A value that is not a string makes the script throw.
- `reviewMr` (optional): the `review-mr` child ref, a non-empty workflow name or `{scriptPath}` with a non-empty path. Default `toolkit:review-mr`. Any other value makes the script throw.

The script throws if any required arg is missing or is not a non-empty string, and throws `execute-runner: the plan has no Implementation Steps` when that section is empty.

It returns `{baseline, steps, validation, review, coldResidual, coldUnverified, docPass, remember, changedPaths, planChanges, diffHashes, diffPaths, diffFiles, blocked, incomplete}`:

- `baseline`: `{branch, status, verify: {command, exitCode, failing}}` from the Prep phase.
- `steps`: one entry per Implementation Step worker that returned, in plan order. The fix, doc pass, and remember workers are not in it.
- `validation`: `{results, runs, allPass, manualChecks, preExisting}`, where `results` holds one `{step, status, evidence}` per result the verifier returned and `runs` counts the validation runs. `allPass` is true only when there is at least one result and every result is `pass`. `manualChecks` and `preExisting` hold one `<step>: <evidence>` line per `manual` or `pre-existing` result, where `<step>` is the first line of the result's `step` field without a trailing period. Null when the build stopped before `verify:validation` returned, including when that verifier died. When the run stopped after it returned, it holds the latest results. For a plan with no Validation Steps, it is `{results: [], runs: 0, allPass: false, manualChecks: [], preExisting: []}`, and `blocked` carries the no-Validation-Steps sentence.
- `review`: `{panel, panelRule, dimensions, confirmed, nits, preExisting, fixed, open, refuted, unverified, dropped, openQuestions, dead, verifierDead, rounds}`, or null when the child did not run or did not return. `panel` names the reviewers the panel rule picked, and `panelRule` names the rule: `high-risk path`, `docs only`, or `standing`. `nits`, `preExisting`, `unverified`, and `dropped` pass through from the child, and each is an empty array when the child returned none. `open` holds the entries still open after the fix rounds, each with `bucket` `confirmed` or `nit`. `dead` is the child's `dead` list: the reviewers and dimensions whose agent returned nothing. It is an empty array when the child returned no `dead` array. `verifierDead` is the child's `verifierDead` list, or an empty array when the child returned none.
- `coldResidual`: the cold read's findings with `verified: true` and a citation, each with its `score`, or null when the cold read did not run or returned nothing.
- `coldUnverified`: the rest of the cold read's findings, each with its `score`, or null when the cold read did not run or returned nothing.
- `docPass`: `{docsUpdated, deferred, distributed, changedPaths, blockers, topicMaterial}`, or null when the doc pass did not run, including when the slice was already blocked, or returned nothing.
- `remember`: `{ran, material, proposals, topicsUpdated, rememberLine}`. When anything blocked or the pass died, `ran` is false, `proposals` and `topicsUpdated` are empty, `rememberLine` is empty, and `material` still carries the topic material. When the remember worker returns blockers, `ran` is false, `proposals` and `rememberLine` are empty, and `topicsUpdated` keeps the notes the worker reports it touched.
- `changedPaths`: the union of the step, fix, and doc pass paths.
- `planChanges`: lines in the forms `Step N: <deviation>`, `Validation fix: <result>`, `Validation fix deviation: <deviation>`, `Fix round R: <deviation>`, `Fix round R resolved: <keys>`, and `Doc debt: <deferred>`.
- `diffHashes`, `diffPaths`, and `diffFiles`: `{redTeam, final, postDoc}` from the three captures, holding the `hash12`, the `diffPath`, and the `paths` list of each capture, with null for a capture that failed or did not run. `postDoc` is also null when the post-doc capture is empty.
- `blocked`: one plain sentence per reason the slice is not done, or an empty array.
- `incomplete`: the labels of the stages that died.

`blocked` gets these sentences:

- `The plan has no Validation Steps, so nothing proves the slice.`
- `The <who> <label> returned nothing.` for each dead stage, which also lands in `incomplete`.
- `The <who> <label> reported blockers: <sentences>` for each worker that returned blockers, including the step, fix, doc pass, and remember workers.
- `Validation returned N results for M steps.` for each validation run whose result count differs from the number of Validation Steps.
- `Validation step failed: <first line>.` for each `fail` result of a `verify:validation` run whose result count differs from the number of Validation Steps.
- `Validation step failed after one fix: <first line>.` for each step still failing after `verify:revalidation`.
- `The diff after implementation is empty.`
- `The review-mr child workflow returned nothing.` when the child returns null.
- `The review-mr child workflow failed: <message>.` when the child throws.
- `The review panel did not report which reviewers ran.` when the child returns no `dead` array.
- `The review panel lost N reviewers: <names>.` when the child's `dead` list is not empty, with the names joined by a comma and a space.
- `The review panel lost the verifier for N dimensions: <names>.` when the child's `verifierDead` list is not empty, with the names joined by a comma and a space.
- `Fix rounds are exhausted at maxFixRounds M with N confirmed findings open, so step back and reconsider the approach rather than run another round.` when confirmed findings at `finalScore` 0.6 or above stay open after the last round. An open nit or an open confirmed finding below 0.6 never adds it.
- `The diff hash changed from <a> to <b> with no fix round.` when the `diff:red-team` and `diff:final` hashes differ and no fix round was launched. A launched `fix:<round>` counts even when it returned nothing.
- `The diff before the cold read is empty.`
- `The diff after the doc pass is empty.`
- `Validation step failed after the doc pass: <first line>.` for each step that fails in `verify:final`.

In the validation sentences, `<first line>` is the first line of the result's `step` field, such as `STEP 1: Run the unit tests`, without a trailing period.

A dead stage never throws. A dead `prep:baseline` lets the run continue. A dead implementer or a step with blockers stops the build: every later phase is skipped, `review`, `validation`, `coldResidual`, `coldUnverified`, and `docPass` are null, and `remember.ran` is false with the material kept. A dead `verify:validation`, `fix:validation`, or `verify:revalidation`, a `verify:validation` result count mismatch, or a step still failing after revalidation, stops the run the same way, except that `validation` keeps the latest results when `verify:validation` returned. A null or empty `diff:red-team` capture skips the child and the fix loop. A dead `fix:<round>` or `recheck:<round>`, or a `fix:<round>` with blockers, ends the fix loop without the step-back sentence. With `maxFixRounds` 0, no fix round runs and any confirmed finding at 0.6 or above blocks with the step-back sentence. A null or empty `diff:final` capture blocks and skips the cold read, so the doc pass does not run either. A null capture leaves its `diffHashes` entry null. A dead `doc:pass` or a `doc:pass` with blockers blocks, so the remember pass does not run, while `verify:final` and `diff:post-doc` still run under their own conditions. A null or empty `diff:post-doc` capture blocks, leaves `diffHashes.postDoc` null, and skips the remember pass, so the skill writes no slice marker.

Tests: `bash plugins/toolkit/workflows/tests/execute-runner/run-tests.sh` runs 164 control-flow cases that drive the script with a scripted agent stub, which records each call's agentType, phase, and schema, and a `workflow()` stub that records the child call's ref and args: the panel rule, `reviewRules` and `reviewMr`, the `verifierDead` gate, the fix round's two headings, the nits rule and the class-rule split, the step-back sentence and its 0.6 count, and the cold read's no-repeats list. The suite needs `node`, and `verify.sh` also runs it.

## ship-runner.js

Ship flow. It carries a reviewed slice up the stage ladder suggest, commit, push, mr, merge, release, and stops at the ceiling: the lower of `stopAt` and the cap the session git permission allows. `none` caps the run at suggest, `push` at mr, and `release` at release. The script calls one agent at a time and runs eight phases:

- **Prep**: a `toolkit:verifier` (`prep:state`) runs `git -c core.quotePath=false status --porcelain -uall`, `git branch --show-current`, `git rev-parse HEAD`, `git ls-remote origin refs/heads/<branch>`, `git -c core.quotePath=false diff --cached --name-only`, the auth probe (`gh auth status` or `glab api user`), and the PR or MR lookup (`gh pr view <branch> --json number,url,state,reviewDecision` or `glab mr list --source-branch <branch> -F json`). It returns the open PR or MR with its `reviewDecision`, an empty string on GitLab. On a run that starts at merge with a `recordedSha`, it also runs `git log --format=%H <recordedSha>..HEAD` and returns the printed shas as `logShas`. The script checks the branch, checks the auth probe and the staged paths when the ceiling is above suggest, and checks the listed paths against the tree when the run commits. A suggest-only run therefore never blocks on a failed auth probe. When no listed path is dirty and HEAD starts with `recordedSha`, the commit counts as made and `commit:paths` does not run. At ceiling suggest, Prep is the only stage that runs.
- **Commit**: a `toolkit:implementer` (`commit:paths`) runs `git add --` with each listed path, `git commit -F -` with the message, and `git rev-parse HEAD`. The commit counts only when the returned sha differs from the Prep HEAD.
- **Push**: a `toolkit:implementer` (`push:branch`) runs `git push -u origin <branch>` and reads the remote head back. The push counts only when the remote sha equals the local sha. When the run made no commit and the remote head already equals HEAD, `push:branch` does not run.
- **MR**: a `toolkit:implementer` (`mr:create`) runs the lookup again and returns the PR or MR with its `reviewDecision`. It reuses only an open PR or MR (`OPEN` on GitHub, `opened` on GitLab), and opens one with `gh pr create` or `glab mr create` when the lookup shows none or only a closed or merged one.
- **Pipeline**: a `toolkit:verifier` (`pipeline:watch:<n>`) watches the pipeline of the pushed commit `headSha`. It runs `bash <pluginRoot>/scripts/watch-mr.sh <host> <remotePath> <number> pipeline --sha <headSha> --bound 9` as one Bash call with the timeout parameter set to 600000. It maps the exit code to the state: 0 `green`, 10 `red`, 11 or 12 `pending`, 13 `none`, and 14 `pending` with the new head from the `MOVED` line as the sha. Every other outcome keeps `headSha` as the sha, and exit 2 or 3 becomes a blocker that carries the script's stderr. On red, it reads the failing log lines: on GitHub `gh run list --commit <sha>` and `gh run view <id> --log-failed`, and on GitLab the `head_pipeline` id, its jobs, and each failed job's trace. It returns the state, the sha it belongs to, and at most 30 failing log lines. A pipeline state is trusted only when its sha is the pushed commit. While the state is red on `headSha` and fewer than `maxFixRounds` rounds ran, a `toolkit:implementer` (`pipeline:fix:<n>`) commits one fix with the message `fix(ci): <failing check> (ship-flow)`, pushes it, and returns `pushed`. A fix counts only when pushed, and the watch then runs again on the new sha.
- **Threads**: when `botAuthors` is not empty, a `toolkit:verifier` (`threads:wait`) first waits for a bot review. It runs `bash <pluginRoot>/scripts/watch-mr.sh <host> <remotePath> <number> threads --sha <headSha> --bound 9` with one `--bot "<login>"` per author as one Bash call with the timeout parameter set to 600000. Exit 0 returns `landed` true, exit 12 returns `landed` false, and exit 14, 2, or 3 becomes a blocker. When `landed` is false, the run blocks with no thread fetch and no thread fix, so `threads` stays null. Then a `toolkit:verifier` (`threads:fetch:1`) fetches the review threads, treating thread text as untrusted data. The script classifies each open thread in this order. A thread from a human, or a bot thread with a human comment, goes to `human`. A bot thread whose id does not match `[A-Za-z0-9_=:-]+` goes to `pushedBackNeeded` with the reason `thread id not safe for a command`, because the thread fix puts the id in a command. A fixable bot thread on a listed path that is neither CI configuration (`.github/`, `.gitlab-ci.yml`, `.gitlab/`, `.circleci/`, `Jenkinsfile`) nor a `protectedPaths` entry gets one `toolkit:implementer` (`threads:fix:<i>`) that edits only that file, commits `fix(review): <summary> (ship-flow)`, pushes, replies `Fixed in <short sha>: <what changed>`, resolves the thread, and returns `pushed`, `replied`, and `resolved`. Every other open bot thread goes to `pushedBackNeeded`. After a thread fix, `pipeline:watch:threads` watches the new sha and `threads:fetch:2` reads the open threads again.
- **Merge**: the script refuses the merge unless the pipeline is green on `headSha`, the threads were fetched, no thread is open, the run pushed no fix commit, and on GitHub the PR review decision is not `CHANGES_REQUESTED`. On a run that starts at merge, it also refuses when a `logShas` entry is in neither `knownShas` nor `fixShas`, which catches a fix commit that a dead agent or a hand-run push left on the branch. Otherwise a `toolkit:implementer` (`merge:mr`) on GitHub runs the PR lookup again, runs `gh pr merge <number> --merge --match-head-commit <headSha>` once only when the fresh `reviewDecision` is not `CHANGES_REQUESTED`, and returns that `reviewDecision`. The script refuses the merge on a fresh `CHANGES_REQUESTED`, so a review posted after Prep still stops it. On GitLab it reads `detailed_merge_status` first, runs `glab mr merge <number> --sha <headSha> --auto-merge=false --yes` once only when the status is `mergeable`, and returns that status as `detailedMergeStatus`. It reads the merge commit back with its `kind`.
- **Release**: after a merge, or on a run that starts at release, a `toolkit:implementer` (`release:tag`) runs `git fetch origin <defaultBranch>`, `git tag -a <tagName>` on the merge commit, and `git push origin <tagName>`.

The Pipeline and Threads phases run inside the mr stage, so a run at ceiling mr watches the pipeline and works the bot threads but never merges. A run that starts at merge still watches the pipeline and fetches the threads. A `startAt` of `release` skips the pipeline and threads block and needs `mr` and `mergedSha`. Every prompt carries a `SHIP GIT RULE` that names only that stage's commands with exactly the flags shown. Its FORBIDDEN sentence names `git stash`, `reset`, `rebase`, `checkout`, `switch`, `clean`, `merge`, `commit --amend`, `add -A`, `add .`, `--force`, `--force-with-lease`, `--no-verify`, `--admin`, and the bare `--auto` flag, and a named command's own flags, such as `--auto-merge=false` on `glab mr merge` or `-f` on `gh api`, are allowed. Every prompt also carries the blocker rule and the denial rule: a worker the permission system denies runs no substitute and returns the exact command in `deniedCommand`, and the script turns it into `handoff`. The commit stage commits `commitMessage` as given, and the commit prompt and the two fix prompts tell the worker that the message carries no Co-Authored-By trailer. The script writes no file itself.

Invoked by the `ship-flow` skill (or directly) with:

```
args: {planName, repoRoot, repoName, host, remotePath, defaultBranch, branch, commitMessage, mrTitle, mrBody, stopAt, permission, scratchDir, pluginRoot, paths, botAuthors?, tagName?, tagMessage?, maxFixRounds?, startAt?, recordedSha?, mergedSha?, mr?, knownShas?, protectedPaths?}
```

- `planName`, `repoRoot`, `repoName` (required): the plan note name, the absolute path to the checkout, and the repo name every prompt carries.
- `host` (required): `github` or `gitlab`.
- `remotePath` (required): the remote path without its host segment, such as `owner/repo` or `group/sub/repo`. The script builds the API paths from it.
- `defaultBranch` and `branch` (required): the default branch and the slice branch. The script blocks when `branch` is the default branch, `main`, or `master`.
- `commitMessage`, `mrTitle`, `mrBody` (required): the commit message and the PR or MR title and body.
- `stopAt` (required): `suggest`, `commit`, `push`, `mr`, `merge`, or `release`.
- `permission` (required): `none`, `push`, or `release`, the recorded session git permission.
- `scratchDir` and `pluginRoot` (required): the absolute scratchpad path and the installed plugin root.
- `paths` (required): a non-empty array of the repo-relative paths to stage.
- `botAuthors` (optional): logins to count as bots beside GitHub app authors and GitLab bot users. Each entry must be a host login: a letter or digit, then letters, digits, `.`, `_`, or `-`, with an optional `[bot]` suffix. When it is not empty, the Threads phase waits for a review from these authors before the fetch. Default `[]`.
- `tagName` and `tagMessage` (optional): required when `stopAt` is `release`.
- `maxFixRounds` (optional): a non-negative integer that caps the pipeline fix commits. Default 1.
- `startAt` (optional): `commit`, `push`, `mr`, `merge`, or `release`, the stage the run resumes from. Default `commit`. Stages below it do not run.
- `recordedSha` (optional): the commit sha an earlier run recorded, 7 to 64 lowercase hex characters. Default an empty string.
- `mergedSha` (optional): the merge commit of a merged PR or MR, 7 to 64 lowercase hex characters. Required when `startAt` is `release`, where it becomes `merged.sha` and the commit the tag lands on.
- `mr` (optional): `{url, number}` of the open PR or MR, with the iid as `number` on GitLab. Required when `startAt` is `merge` or `release`.
- `knownShas` (optional): the commit shas the shipping record holds, the recorded commit sha plus every recorded fix sha, each 7 to 64 lowercase hex characters. A `logShas` entry matches when it starts with a listed sha. Default `[]`.
- `protectedPaths` (optional): repo-relative paths whose threads the run never fixes, added to the CI configuration list. An entry ending in `/` covers a directory, and any other entry covers one exact path. Default `[]`.

The script throws if any required string arg is missing or empty, if `paths` is not a non-empty string array, if `host`, `stopAt`, `permission`, or `startAt` is not one of its values, if `botAuthors` is not a string array or holds an entry that is not a host login, if `stopAt` is `release` without `tagName` and `tagMessage`, if `maxFixRounds` is not a non-negative integer, if `recordedSha` is not a string or is a non-empty string that is not 7 to 64 lowercase hex characters, if `knownShas` is not an array of such shas, if `protectedPaths` is not a string array, if `mr` is not a non-empty `url` with a positive integer `number`, or if `startAt` is `merge` or `release` without `mr`. It throws `ship-runner mergedSha must be a hex commit sha` when `mergedSha` is not 7 to 64 lowercase hex characters, and `ship-runner requires mergedSha when startAt is release` when a release start has no `mergedSha`.

It returns `{stoppedAt, ceiling, commitSha, headSha, pushed, mr, pipeline, threads, fixShas, merged, tag, handoff, blocked, incomplete}`:

- `stoppedAt`: the highest stage the run completed. A run that stops early reports where it stands.
- `ceiling`: the lower of `stopAt` and the permission cap.
- `commitSha`, `headSha`, `pushed`: the slice commit, the pushed head after the last pushed fix, and whether the remote head equals it.
- `mr`: `{url, number}` or null.
- `pipeline`: `{state, sha, rounds, failingLines}` or null, where `state` is `green`, `red`, `pending`, or `none`.
- `threads`: `{fixed, pushedBackNeeded, human, open}` or null. A `pushedBackNeeded` entry may carry `reason`.
- `fixShas`: every fix commit the run pushed, from the pipeline and the thread stages.
- `merged`: `{sha, kind}` or null, where `kind` is `merge` or `unknown` on GitHub, `merge`, `squash`, or `fast-forward` on GitLab, and `unknown` on a release start. `tag`: the pushed tag name or null.
- `handoff`: `{stage, command}` when the permission system denied a command, else null.
- `blocked`: one plain sentence per reason the run stopped, or an empty array.
- `incomplete`: the labels of the stages that died.

`blocked` gets these sentences:

- `The <who> <label> returned nothing.` for each dead stage, which also lands in `incomplete`.
- `The <who> <label> reported blockers: <sentences>` for each worker that returned blockers.
- `The <who> <label> was denied the command: <command>.` for each denied command, which also sets `handoff`.
- `Prep found a detached HEAD.` and `Prep found the branch <found>, not <branch>.`
- `The branch <branch> is the default or a protected branch, so the ship flow does not run on it.`
- `The auth probe <command> failed.`, checked only when the ceiling is above suggest.
- `Paths outside the staging list are already staged: <paths>.`, checked whenever the ceiling is above suggest, and `Listed paths have no change in the tree: <paths>.`, checked only when the run commits.
- `origin/<branch> is at <sha>, not HEAD <sha>, so the run cannot watch the pushed commit.` when the run resumes above push but below release, the ceiling reaches mr, and the remote head differs from HEAD.
- `The commit stage made no new commit.` when `commit:paths` returns no sha or the Prep HEAD.
- `The push left origin/<branch> at <sha>, not HEAD <sha>.`
- `The implementer mr:create returned no PR or MR url and number.`
- `The pipeline state belongs to <sha>, not the pushed commit <headSha>.` when a watch returns the state of another commit.
- `No pipeline was found for <sha>.` when the watch returns `none`.
- `The pipeline for <sha> was still pending at the watch bound.`
- `No review from <botAuthors> has landed on <url> for <headSha> at the watch bound.` when `threads:wait` returns `landed` false.
- `Pipeline fix rounds are exhausted at maxFixRounds <n>.` and `The pipeline for <sha> is red after the thread fixes.`
- `The fix <label> committed <sha> but the push did not happen.` for a fix that returns a new sha without `pushed` true.
- `The implementer <label> pushed no new commit.` for a fix that returns no new sha.
- `The implementer <label> changed <paths>, not only <file>.` for a thread fix that touched another file.
- `The thread fix <label> pushed <sha> but did not reply or resolve thread <id>.`
- `HEAD holds commits the shipping record never saw: <shas>.` on a run that starts at merge.
- `The merge was refused because <reasons>, and the merge command is <command>.`, where the reasons are joined with `and` and each is one of `the pipeline is <state>`, `the green pipeline ran on <sha>, not the pushed head <sha>`, `the review threads were not fetched`, `<n> review threads are open`, `the PR review decision is CHANGES_REQUESTED`, and `this run pushed the fix commits <shas>, which nobody has reviewed`. A refusal on the review decision alone reads `The merge was refused because the PR review decision is CHANGES_REQUESTED, and the merge command is <command>.`, and `merge:mr` returns the same sentence when its fresh lookup reads `CHANGES_REQUESTED`.
- `The merge was refused because the detailed_merge_status of <url> is <status>, not mergeable.` on GitLab.
- `The merge of <url> did not land, and its state is <state>.`
- `The implementer release:tag did not push the tag <tag>.`

A dead stage, a denied command, or a blocked sentence stops the ladder, so no later stage runs. A fix that pushed and then hit a blocker still lands in `fixShas`, and a fix that committed without a push does not. A refused merge skips the release.

Tests: `bash plugins/toolkit/workflows/tests/ship-runner/run-tests.sh` runs 156 control-flow cases that drive the script with a label-keyed agent stub: arg validation, the ceiling for each permission and `stopAt`, the stage order and resume points, each stage's `SHIP GIT RULE`, a denied command and a dead agent at each stage's first label, the pipeline fix loop, the watch-mr.sh calls and their states, the bot review wait, the thread classification, every merge refusal, and the release. The suite needs `node`, and `verify.sh` also runs it.

## post_mr_comments.py

Lives at `plugins/toolkit/skills/gitlab-mr-review/scripts/` — skill-local, not a general toolkit script. Posts review findings as positioned discussions on the GitLab MR: reads a `comments.json` (host, project, MR IID, the head sha the diff was reviewed at, the diff path, and a list of `{path, anchor, body}` comments plus an optional summary note), resolves each comment's `anchor` against the added lines in the diff (exact match first, then substring) to find a line number, then posts a positioned discussion per comment — falling back to an unpositioned discussion, prefixed with file:line, if GitLab rejects the position. It aborts up front if the MR's head sha has moved since the diff was fetched, since anchors may be stale. `--dry-run` prints what would be posted without posting.

This is a separate, explicit step — never automatic. The skill only runs it when the user asks, in that same session, to post the review to the MR; producing the review itself never triggers it.

Tests: `bash plugins/toolkit/scripts/tests/post-mr-comments/run-tests.sh` (5 behavior cases over the `GITLAB_TOKEN` guard: unset, empty, whitespace-padded, embedded-newline, and a well-formed fake that must pass through; also run by `verify.sh`).
