# Execute flow adjudication

The `execute-flow` skill launches the `execute-runner` workflow and settles, with no question, what the run cannot settle alone. What the script takes and returns is in [workflows.md](../workflows.md). This page lists the constraints a change to the skill's stop, resume, and fix paths must keep.

## Why the flow adjudicates

- A fail-closed gate that no person can open stalls the run instead of making it safer, and so does a question in an unattended run. The execute flow therefore tells every worker the dangerous-commands hook rule, shows the review panel the plan's Assumptions and Risks as settled decisions, and returns each unreproduced panel finding in `review.unverified` and each verified cold-read finding in `coldResidual` for section 8 to settle instead of blocking the run. The user contests an outcome on the branch before the merge. [0004-execute-flow-asks-nothing-after-approval.md](../decisions/0004-execute-flow-asks-nothing-after-approval.md) records the decision.

## Stop and resume prefixes

- Section 1 of the skill starts a fresh run on an in-progress plan note only when the last `sessions` summary begins `execute-flow blocked:`, and resumes at section 8 only when it begins `execute-flow adjudicating:`. A new stop path must leave a summary that begins with one of those prefixes, or section 1 refuses the next request to run the flow.
- The ship-flow skill writes summaries that begin `ship-flow stopped:` or `ship-flow finished:`. Section 1 of the ship-flow skill accepts an in-progress plan note only when the last summary begins `execute-flow finished:`, `seat-run finished:`, `ship-flow stopped:`, or `ship-flow finished:`. Section 1 of the execute-flow skill routes a note to the section 11 seat run only when it holds a `Validation deferred:` line and its last summary begins `execute-flow finished:`, `ship-flow stopped:`, `ship-flow finished:`, `seat-run finished:`, or `seat-run blocked:`, or reads `seat-run started`, so a blocked or adjudicating execute run still re-enters its worktree. A change to the `execute-flow finished:` prefix must change that list too, or the ship flow refuses every slice the execute flow finished.
- Section 6 writes one `Changed path:` line per path a blocked run left in the tree, taken from `git status` read with the own-worktree pathspec, every listed path included, and one `Baseline:` line. Section 3 continues a rerun only when every dirty path equals a recorded path. The record comes from the tree and not from the workers' `changedPaths`, because a dead implementer's edits are never collected and a worker can report a foreign path. A blocked stop path that skips the section 6 record forces the user to commit or discard the slice before the rerun, and a WIP commit removes the slice from the `git diff HEAD` capture the panel reviews.
- A run that died with its session is continued, not rerun, when its record holds: the plan note's last `Launch:` line names its session, no `Run ended: <runId>` line names it, and the newest run block in `evidence - <planName>.md` reads `at pending` with a `Run:` line under that session. The run block is written after launch because any plan note write after launch stops the run, and the evidence note is the one vault note beside the plan that no runner worker sha-checks. Section 3 then counts the checkpoint's `changedPaths` and `capture` paths as recorded, the one case where the record comes from workers, because the continued run wrote no `Changed path:` line. `run-checkpoint.py` refuses a run that died inside `implement:<n>`, `fix:<round>`, `fix:validation` or `doc:pass`, whose partial edits have no record, and exits 3 for a run with no run summary or one that says `running`, which section 1 stops on.
- A continued rerun passes the recorded paths as `priorChangedPaths` and the recorded failing names as `baselineFailing`, an empty list when no clean baseline exists. `prep:baseline` runs over the half-built slice and the validation verifier reads pre-existing status from the baseline failing list it is shown, so dropping `baselineFailing` makes a check the blocked run broke look pre-existing. The doc pass reads `CHANGED PATHS` from the runner's changed list, so dropping `priorChangedPaths` leaves the earlier run's files out of the doc pass.
- `blockersOf` in `execute-runner.js` and `ship-runner.js` stops on any `blockers` entry. The implementer and verifier agent definitions and the runner prompts say `blockers` holds only work the worker could not do. The `execute-runner.js` step prompts route a caveat to `deviations`, and the `ship-runner.js` stage schemas have no `deviations` field, so a ship stage prompt carries no caveat routing. A text filter on `blockers` is not used, because a false pass continues over a denied step and nothing reports it.
- The four leaf agents, `implementer`, `verifier`, `explorer`, and `browser-driver`, name the `Blockers` return heading in their opening sentence and in their return list, and `doctrine/orchestration.md` lists the same heading in the worker return contract. A rename of that heading must change all five files, or a worker reads two names for one field.
- A runner prompt routes a caveat only to a field its schema has. `RETURN_STEP` in `execute-runner.js` sends caveats and follow-ups to `deviations`. The doc pass and remember pass schemas have no `deviations` field, so their blockers sentence says only "one sentence per step you could not do". The verifier definition says a caveat goes in a schema field that holds it or is left out. A new prompt must not name `deviations` unless its schema declares it.
- The runner seeds its changed list from `priorChangedPaths` before any worker runs, and each later path is added only when the list does not already hold it. The recorded paths therefore stay first in `changedPaths` and never repeat. The `baselineFailing` override replaces the failing list only when `prep:baseline` returned a result, so a dead baseline verifier still blocks the run. [workflows.md](../workflows.md) gives the arg contracts.

## Adjudicated findings

- The adjudication list is every `review.unverified` entry, then every `review.open` entry with bucket `confirmed`, then every `coldResidual` entry, then every `review.keptForSteps` entry. Section 6 records each `review.open` entry with its bucket, because a resume at section 8 rebuilds the list from the note. An entry is settled when the plan note records it as fixed, intentional, did not matter, or unreproduced. Every gate that holds the finished summary, the slice marker, and the commit suggestion reads settled over the whole list, so a gate that reads only `coldResidual`, or a fifth outcome word, leaves the `execute-flow finished:` summary unreachable and the ship flow refusing the slice.
- Section 8 asks nothing and settles each entry in list order. A `review.unverified` entry takes no fix, because an unreproduced finding does not count under the validation-honesty doctrine. It records `Finding unreproduced:`, which settles it, appears under To settle in the report, and goes into the commit message body under `Unreproduced review findings:`, so the ship flow's MR body carries it. A `coldResidual` entry takes no fix either, because only the cold reader marked it verified and no verifier reproduced it: it records intentional when it maps to one of the plan's Assumptions or Risks, and `Finding unreproduced:` with the reason `cold read, no verifier` otherwise. A `review.open` entry with bucket `confirmed` takes Fix now when it maps to none of the plan's Assumptions or Risks, and Leave it when it maps to one. Fix now records fixed once the fix round's re-check resolves it, and a Validation Step that fails after the fix becomes a separate held entry. Leave it records intentional, with the decision it restates. A finding gets one fix round: one the re-check left unresolved stays held on every resume until the user records `Finding did not matter:` or `Finding intentional:` for it on the plan note, so a resume never runs a second round. A held Validation Step that still fails after the fix takes Hold, and settles when it passes on a resume or when the user records `Validation step accepted:` for it. No recorded line starts with `Remember:`, because `remember-guard.sh` keys on that word.
- The cold read gets the keys of the panel's `confirmed`, `nits`, and `preExisting` entries as a no-repeats list, and never the refuted, dropped, or unverified ones, because the cold read is the recovery path for a real defect one verifier refused. Unreproduced nits ride fix round 1 under `nits: fix`, and on a seat run only a round that a confirmed finding starts. Under `nits: skip`, and when no round ran, they stay under To settle. A reproduced finding never waits there: it is confirmed at any score, and an open confirmed finding below 0.6 is settled in section 8 rather than blocking. A refuted doc finding is listed under To settle with the verifier's reason and quoted line, because the cold read is its only automated re-raise. [context-review-scoring.md](context-review-scoring.md) holds the scoring and routing rules.
- The `red-team` skill's post-fix cold read, its section 6, sends a verified residual of fifteen lines or fewer to one scoped implementer fix round. The execute flow fixes no cold-read entry, because no verifier reproduced it, and its section 8 records each one as intentional or unreproduced instead. The two policies differ on purpose, and the `red-team` skill stays interactive.
- The section 8 fix round runs after the doc pass and never reruns it. The skill's report must say whether the fix touched a public surface that the doc pass did not see, because this is the one path in an execute-flow run where the doc pass can miss a change.
- Three files state the adjudication list and its order: this page, [context-review-scoring.md](context-review-scoring.md) under Settled outcomes, and section 8 of the `execute-flow` skill. Section 8 settles the entries in the same order. A change to the list or its order must edit all three.
- The `red-team` skill still settles its unverified panel entries with the user and recommends Fix now for them. Only section 8 of the `execute-flow` skill settles an unverified entry with no question. A change that moves one policy toward the other must say so in both skills.

## Shipping record

- Section 7 of the skill writes the shipping record (the staging list, the commit message, and a hash) after the accepted docs are written, a section 8 fix replaces it, and the ship flow compares a fresh capture against its hash before a commit. The slice marker still keys on `diffHashes.postDoc`, which is taken before any doc lands, so the shipping record hash and the marker hash differ whenever the consent gate accepted a doc.
- `execute-runner.js` marks a failed `diff:post-doc` capture dead and turns an empty one into a `blocked` sentence, so a result with an empty `blocked` and an empty `incomplete` always carries `diffHashes.postDoc`. Section 7 therefore takes no capture of its own.
- Section 7 declines every repo doc proposal with no question and copies each proposal's scratch file, `remember-<kebab-path>.md`, into the plan note's vault folder as `remember-<kebab-path> - <planName>.md`, linked under Linked Artifacts. Step 4 of the obsidian-topic gate folds the declined proposals' facts into the vault topics. The report lists each copy's repo path and vault path under "Repo doc proposals", never the scratch path.
