# Workflow script authoring

The scripts under `plugins/toolkit/workflows/` run through the Workflow tool. What each script does and returns is in [workflows.md](../workflows.md). This page covers how a script must be written so that it parses and tests cleanly, and the `verify.sh` conventions a new script or check must follow.

## Naming a script

- A skill and a workflow script cannot share a name, because both register in the same `toolkit:` namespace and the workflow shadows the skill. The `plan-flow` skill therefore launches the `plan-builder` script, the `execute-flow` skill launches the `execute-runner` script, and the `ship-flow` skill launches the `ship-runner` script.

## Parsing a script

- The exit code of `node --check` says nothing about a workflow script either way. The script bodies use top-level `await` and `return`, which no plain parse mode accepts.
- The real check strips `export ` from `export const meta` and compiles the body with the AsyncFunction constructor, `Object.getPrototypeOf(async function () {}).constructor`. `verify.sh` does this in its `WF_PARSE` one-liner for every `workflows/*.js` file.
- `node --check` also rejects a valid workflow script with `SyntaxError: Illegal return statement`, because of the top-level `return`. Its exit code therefore says nothing about a workflow script. The syntax check is `WF_PARSE` in `verify.sh` and the script's harness suite.

## Writing prompts

- A prompt is a template literal, so text inside it cannot contain an unescaped backtick. An unescaped backtick ends the string. Shared prompt text such as `RULES` in `plan-builder.js` leaves out code-style markup for that reason.
- If a prompt key names two things, the prompt must name each one separately. In `plan-builder.js`, `relatedTopics` is both a plan section and a top-level list. `RULES` says the section holds one wiki link per line and the list holds plain names. A rule that says only "relatedTopics are a few plain names" leads the planner to return the section as a comma list.
- `review-mr.js` drops `contextBlock` from the prompt of a cold dimension and gives every custom dimension no `agentType`. A rule that a cold reviewer must obey, such as read-only git in `repoRoot`, must be written inside the dimension prompt itself.
- `REVIEW.md` reaches the panel only inside `contextBlock`. `execute-runner.js` appends its `reviewRules` arg there, so the registry reviewers, the non-cold custom dimensions, and every verifier read it, and a cold dimension never does. `review-mr.js` takes no argument of its own for it.
- `review-mr.js` adds `contextBlock` to every batched verifier prompt, whatever the dimension. `cold: true` hides the context from the cold reviewer only, so text placed in `contextBlock`, such as the `SETTLED DECISIONS` block, still reaches the verifiers of a cold dimension's findings. The verifier reads the `SETTLED DECISIONS` sentence and the verifier brief in one prompt, so the sentence must not contradict the brief: both say an Assumption or Risk settles scope and coverage and never a rule breach or a doc line the tree contradicts.
- `GIT_RULE`, `HOOK_RULE`, and `DOCTRINE` in `execute-runner.js` interpolate `repoRoot`, `scratchDir`, and `pluginRoot`. A copy of their text outside the runner, such as a briefing the `execute-flow` skill sends, must substitute those values.
- `runValidation` in `execute-runner.js` builds one prompt for `verify:validation`, `verify:revalidation`, and `verify:final`. That prompt carries `HOOK_RULE` and "Change no file" but not `HOOK_WRITE_RULE`, which only the prompts built on `SHARED` carry. A prompt sent to `toolkit:verifier` must not tell it to use the Write tool, because the verifier has no Write.
- `execute-runner.js` declares a top-level `strList` as a JSON schema fragment for the result schemas. An arg check that tests for an array of strings must use another name, as `isStrList` does. A new optional arg changes three places: the args list in the error text the script throws, the args signature in the `execute-runner` section of [workflows.md](../workflows.md), and a bullet in the arg list under that signature.
- Every runner takes an optional `models` arg, the `agents` object `resolve-models.sh` prints, keyed by short agent name. The runner throws unless each entry is an object whose only keys are `model` and `effort`, each a string. Each `agent()` call applies it through a `...modelOpts(who)` spread with its agent's short name, which omits a blank `model` or `effort` so the session value applies. The resolver has already turned `inherit` into blank. `execute-runner.js` forwards the map to its `review-mr` child only when it was given. `review-mr.js` gives a custom dimension, which has no agent type, the `code-reviewer` entry. A new `agent()` call must carry the spread for its agent's short name.
- The `models` check, `isModelEntry` and the `throw` that uses it, is copied in each runner: `execute-runner.js`, `plan-builder.js`, `ship-runner.js`, and `review-mr.js`. Each runner is a standalone Workflow script with no shared module, so a change to the allowed entry keys must be made in all four. Because the check accepts only `model` and `effort` with string values, passing the resolver's whole `{agents: ...}` output or a bare string entry throws `<runner> models must map agent names to {model, effort} objects when given`.
- No `execute-runner.js` worker prompt carries the plan note whole. Each prompt carries only the plan sections its job acts on, each as its line range, which the worker reads itself after the sha check, as the execute-runner section of [workflows.md](../workflows.md) lists. A prompt that carries the whole plan grows with the body of every step, and with one implementer per step the run's usage grows with the square of the plan size. A prompt that needs another section adds that section, never the whole plan. [context-economics.md](../context-economics.md) covers why prompt size drives cost.

## Runtime behavior a script relies on

- `pipeline()` returns one entry per input item, in input order. A stage that throws turns that item's entry into `null` and keeps its position. `plan-builder.js` relies on `findings[i]` matching `areas[i]`.
- `plan-builder.js` sets `critiqueStale` by comparing the rendered plan text with the text the last returned Invert critique saw, not by object identity. A cold revise that returns identical text therefore leaves `critiqueStale` false.
- `plan-builder.js` checks that case separately. If the cold revise returns text identical to the draft, the script counts it as unapplied, keeps the cold material objections open, and adds a `blocked` reason.
- The exhausted-rounds check in `plan-builder.js` must ignore `revise:cold` when it reads the dead-revise list, because the cold revise is not an Invert round.
- `workflow(nameOrRef, args)` throws on an unknown name or a child failure and returns null when the child is stopped. `execute-runner.js` wraps its `review-mr` call in try/catch and turns both outcomes into a `blocked` sentence, so a failed child never ends the parent run.
- `review-mr` drops a dead reviewer or dimension silently unless the caller reads the `dead` list it returns, so `execute-runner.js` blocks when that list is not empty. It also blocks when the `verifierDead` list is not empty, because `review-mr` routes the findings of a chunk whose verifier returned nothing to `unverified` without failing, and the slice would otherwise finish with that dimension unchecked. The scratch-only rule in `execute-runner.js`, `SCRATCH_ONLY`, reaches only the panel context block, the two cold dimensions, and `cold:read`, because a worker whose job is to run commands in the repo cannot also obey a rule to run commands only against scratch fixtures.
- `execute-runner.js` captures the diff three times: `diff:red-team` for the panel, `diff:final` for the cold read, and `diff:post-doc` after the doc pass for the remember brief and the slice marker. Only the post-doc hash matches a later `red-team` capture of the tree the user commits, and only when the `execute-flow` skill ran no section 8 fix, because its consent gate declines every repo doc. If the red-team and final hashes differ while no fix round ran, something other than a fix worker changed the tree, and the script blocks. That check reads `fixAttempts`, the count of launched fix rounds, not the recorded `rounds`, because a fix worker that died or reported blockers may still have edited the tree. A fix round enters `rounds` as soon as its `fix:<n>` agent returns a result, before its recheck, so a round whose recheck died still counts. `toolkit:verifier` has Read, Grep, Glob, Bash, WebFetch, and WebSearch, and no Write or Edit, so the capture prompt writes the diff through a shell redirect into `scratchDir`. The captures run read-only git only, because the git-safety `## Flows` section lets the execute flow's agents run read-only git and lists no capture among the commands the flow may mutate git with.
- A workflow script has no shell primitive. Its calls are `agent`, `workflow`, `pipeline`, `parallel`, `phase`, and `log`, so a wait on external state inside a script is one blocking Bash call in a verifier, under the harness cap of 600000 ms on a foreground call. At the bound the script ends the run with a named `blocked` sentence, and the conductor skill waits on it in the background. `ship-runner.js` passes `--bound 9` to `scripts/watch-mr.sh`, so the watcher exits before the harness kills the call. `threads:wait` runs only when `botAuthors` is not empty, because an empty list cannot say whether a bot review is expected.
- `execute-runner.js` also blocks when the child returns no `dead` array. Without a `reviewMr` arg it resolves the child by the registered name `toolkit:review-mr`, so a runner that is newer than the installed `review-mr` blocks every run until the plugin updates. The `execute-flow` skill passes `reviewMr` as `{scriptPath}` when `repoRoot` holds `plugins/toolkit/workflows/review-mr.js`, which is how the toolkit repo runs its working-tree child. A refused ref lands in `blocked` as `The review-mr child workflow failed: <message>.` Open item: the `red-team` skill does not read `dead` yet, so a dead reviewer in its runs goes unreported.
- `E2E_OUTCOME` in `execute-runner.js` sets the `deferred` status only when `inWorktree` is true, and the `VALIDATION` schema adds `deferred` to its status enum only under `inWorktree`. The two must keep the same condition, or the runner settles an end-to-end step to a status the schema rejects.
- With `planPath`, `plan:index` is the only read of the whole note, and it relays the sha256, heading names and lines, and step headings and start lines that `plan-index.py` prints, never section text. The script derives every end line from the next start and gives each range two anchors, so a relayed line number that slipped fails the script's order check, fails a worker's anchor check before that worker acts, or touches no range a worker reads. A heading entry the relay dropped leaves an unfenced `##` line inside the range before it, which the read rule stops on. A renamed entry fails the `after` anchor of the range before it, but the first heading has no range before it, so a slipped first name only blanks its own block. A relayed `e2e` flag that differs from `E2E_MARK` on its relayed heading blocks the run as an inconsistent index, because `settleE2E` overwrites the verifier's result on a flagged step. A relayed sha256 that slipped makes the first reading worker report a mid-run change. A resume replays the cached `plan:index` return, and each new worker's checks still compare it with the file. The index and the sha check go through `vault-fs.sh`, the one script setup's allow rule clears for vault access. The `execute-flow` skill passes its `<runner-plugin-root>` as `pluginRoot`, the repo's own `plugins/toolkit` whenever it launches a repo runner that takes `planPath`, so such a runner never calls a `vault-fs.sh` from another tree. A repo runner that predates `planPath` gets the installed plugin root, because its own `vault-fs.sh` has no `index` subcommand.
- `execute-runner.js` holds the line `const REPLAY = null`, which `run-checkpoint.py` replaces in a scratchpad copy, so the line keeps that exact text. The execute-runner harness's `replayFlow` replaces it the same way.
- `settleE2E` finds the end-to-end steps by result index, not by the step text the verifier returns. It relies on the verifier returning one result per STEP in step order, which the `runValidation` prompt requires. A verifier that returns results out of order settles the wrong step.

## Reading plan content

- `scripts/plan-index.py` reads a section from its `## <name>` heading to the next line outside a fenced block that starts with `##` and a space or tab. A fence opens on a line of 3 or more backticks or tildes with an optional info string, and it closes only on a line of the same character at least as long with nothing else on it, the rule `scripts/validate-plan.py` applies. A split that ignores fences ends a step early at a fenced `## ` line.
- Inside Implementation Steps, `scripts/plan-index.py` splits on numbered `###` headings, else on unnumbered `###` headings, else on numbered lines, under the conditions the execute-runner section of `docs/workflows.md` states. The `execute-flow` skill counts the `implementationSteps` that `vault-fs.sh index` prints before launch, so the stated count matches the implementers the script spawns.
- `scripts/plan-index.py` splits Validation Steps by the same step rule, and `execute-runner.js` sends them to the verifier as numbered `STEP <n>:` blocks, with an instruction to return exactly that many results. The count check and the verifier therefore agree whatever list style the plan uses. A bulleted list under fewer than two `###` headings has no step marker, so it becomes one `STEP 1:` block and gets one result.
- `items()` in `scripts/plan-index.py` sets each step's heading when it splits the section: the marker line that started the step, with `###` and the whitespace after it stripped, or the first line of the section when the section has no marker. A later scan of a step's text for its heading picks the wrong line, because step 1's text starts with any text before the first marker, and a step split on a `###` heading can hold numbered sub-steps.
- `scripts/plan-index.py` ends a section at an unfenced line that starts with `##` and a whitespace character, and names the section by the rest of the line, trimmed. `scripts/validate-plan.py` matches `^##\s` in multiline mode, where `\s` also matches a newline, so a bare `##` line ends a section in the validator and not in the indexer.
- The `[e2e]` marker has one definition for plans: the Validation Steps subsection of `skills/plan-guide/SKILL.md`. `E2E_MARK` in `plan-index.py` tests the parsed step heading against it, and plan-guide's `## Run options` defines `e2e: required` and `e2e: skip` to match what the runner does with marked steps. The `plan-flow` skill appends the marker instruction to the `plan-builder` brief when the run options carry `e2e: required`. `execute-runner.js` holds a copy of `E2E_MARK` to check the relayed `e2e` flag. A change to the marker's form must change plan-guide, both `E2E_MARK` copies, and the plan-flow line together. The `[shots]` marker directly after `[e2e]` has the same single definition. `SHOTS_MARK` in `plan-index.py` reads it, and `execute-runner.js` holds a copy that checks a relayed `shots: true`.
- `plan-index.py` matches JavaScript's `\s` and `trim()` whitespace set (`WS`), not Python's, because the execute-runner harness cases pin splits on that set, such as a tab after `##`. It lists every unfenced `##` heading, including ones the runner never reads, because the runner ends each section at the next listed heading.

## Gating on a script result

- A gate that reads one signal while the script produces several approves results it must reject. A gate on `approveIf.meets` alone can approve a plan that has a `stop` verdict, exhausted rounds, a dead critic, or a stale critique.
- A script whose result feeds an approval gate returns an explicit `blocked` list with one sentence per reason, and the gate requires that list to be empty. The `plan-flow` skill reads `blocked` this way.
- A non-null worker result is not a success. Each `execute-runner.js` worker prompt tells the worker to record a denied or impossible step as one `blockers` sentence and stop instead of working around it, and the script treats non-empty `blockers` as a failure: it adds a `blocked` sentence. An implement or `fix:validation` worker with blockers stops the build, a `fix:<round>` with blockers ends the fix loop, blockers from `doc:pass` skip the remember pass, and blockers from `remember:pass` set `remember.ran` to false.
- A validation failure the slice did not cause must not send a fix worker. `execute-runner.js` records the checks that fail before any change in `prep:baseline`, and the validation verifier reports a step that fails only on one of those as `pre-existing`, which never triggers the fix and never blocks.
- A stage that writes to the repo or the vault runs only after every check it depends on passed. If `blocked` holds a sentence when the doc pass starts, `execute-runner.js` skips the doc pass, the final validation, and the post-doc capture. If `blocked` holds a sentence when the remember pass starts, the script skips that pass too and returns the topic material with `remember.ran` false for the conductor. An empty post-doc capture adds a `blocked` sentence and is set to null, so no slice marker keys to the hash of an empty diff. A verified cold-read finding and an unverified panel finding add no `blocked` sentence. The script returns them in `coldResidual` and `review.unverified`, so the doc pass and the remember pass still run, and the `execute-flow` skill holds the slice marker and the commit suggestion until its section 8 settles each one with no question.
- If the first validation returns a result count that differs from the step count, the script adds the count sentence and one sentence per failing result, and returns before the red-team capture.
- One cause yields one `blocked` sentence. When a fix or recheck stage dies, or a fix worker reports blockers, the script skips the exhausted-rounds sentence, because the dead-stage or blockers sentence already names the cause.
- The `verifierDead` check in `execute-runner.js` is its own `if` after the `dead` checks, not another branch of them. A run that lost both a reviewer and a verifier reports both sentences, because they are two causes.
- A seat run, `seatRun: true`, skips every `implement:*` stage, `doc:pass`, and `remember:pass`, and still runs `diff:final`, `cold:read`, and `diff:post-doc`. The final validation keeps its existing condition, a fix round or a doc pass that changed files. `docPass` stays null on a seat run, so `verify:final` runs only after a review fix round.
- On a seat run, the stray filter compares the `diff:red-team` paths with `changed`, the list seeded from `priorChangedPaths` plus the paths `fix:validation` reports. A path outside both and outside `OWN_WORKTREES` blocks the run before the panel. A seat run whose red-team capture is empty returns right after the capture with no review and no `blocked` sentence.
- An `e2e: required` run with Validation Steps and no `[e2e]` step blocks after `plan:index` and before `prep:baseline`.

## Testing a script

- `workflows/tests/plan-builder/harness.mjs` compiles the script with the same AsyncFunction method and passes in stub `args`, `agent`, `pipeline`, `phase`, and `log`. `workflows/tests/execute-runner/harness.mjs` passes no `pipeline` stub. Its parameters are `args`, `agent`, `workflow`, `phase`, and `log`, in that order, and the `workflow` stub records each child call's ref and args, and returns or throws the value scripted under the `workflow:review-mr` label. Its `run()` takes the plan text from a `plan` key that it removes from the args, scripts `plan:index` with the output of `scripts/plan-index.py` on that text, and returns `reads`, each prompt with its range pointers replaced by the fixture lines they name. A case on what a prompt carries asserts the raw pointer through `pointerTo`, and a step-splitting case asserts `reads`. `workflows/tests/review-mr/harness.mjs` passes `args`, `agent`, `pipeline`, `phase`, and `log`, and its `pipeline` stub calls the second stage with the first stage's result and the item, as the runtime does, because `review-mr.js` reads the dimension from that second argument. The plan-builder stub calls each stage with one argument, so it cannot drive `review-mr.js`.
- The stub `agent` returns the scripted result for the call's `label`, or `null`, so a case kills a stage by leaving its label out. The plan-builder stub `pipeline` follows the runtime rule above: a stage that throws leaves `null` in that item's position.
- A fence tracker that only toggles on each fence line passes a nested-fence case whenever the fence lines come in even pairs. The nested case must put the `## ` heading inside the inner block, as the execute-runner suite's four-backtick case does.
- The execute-runner harness's `run()` returns the child workflow calls in `calls`, so a case reads the panel context block at `calls[0].args.contextBlock`. The default `run()` reaches only `implement:1`, `implement:2`, `implement:3`, `doc:pass`, and `remember:pass` among the implementer labels. The `FULL_RUN` fixture in `harness.mjs` also reaches `fix:validation` and `fix:1`, so a case that claims to cover every implementer prompt must run `FULL_RUN`. The default `implement:3` returns `src/c.js`, so a default run's `changedPaths` is `src/a.js`, `src/b.js`, and `src/c.js`.
- `execute-runner.js` picks the panel from the `diff:red-team` paths joined with every implementer's `changedPaths`. The execute-runner harness's `onPaths(paths)` helper therefore scripts every implementer with no changed paths, so a panel-rule case sees only the capture paths it names. `rulesOf(bullet)` builds a minimal `REVIEW.md` with one High-risk paths bullet for the `reviewRules` cases, and `STEP_BACK(n, rounds)` builds the exact step-back sentence.
- The review-mr harness's `finding`, `verdict`, and `verdictsOf` helpers build a cited finding and its verdict. The default finding scores 0.68 and cites `src/a.js:4`. The case `a second-chunk verdict at index 0 routes to the ninth finding` pins the chunk-local verdict index, so a change that numbers verdicts across chunks fails it.
- A change to the step splitter must pass two plan shapes besides its own cases. The first is numbered Validation Steps followed by a `### Tripwires` subheading with its own list that starts at 1, the block the plan-critic step in `skills/plan-guide/SKILL.md` copies into Validation Steps. The second is the execute-runner suite's `REFERENCE_PLAN`, one numbered list that runs across unnumbered subheadings. A rule that lets every `###` heading split whenever the numbered lines are not one list folds the numbered steps before a lone `### Tripwires` heading into one STEP.
- The execute-runner harness reads the script path from its first argument, as `run-tests.sh` passes it, so `node harness.mjs <copy>` runs the real suite against a mutated scratch copy of `execute-runner.js`. `PLAN_INDEX=<copy> node harness.mjs <runner>` runs the suite against a mutated copy of the indexer. Each condition of the second split rule, the unnumbered `###` rule, must keep one case that fails without it. The `REFERENCE_PLAN` case is the only guard for the condition that a single numbered list must not run across a subheading.
- A case that asserts a section's text in a worker prompt must use `SECTIONED_PLAN`, which fills Current Context, Affected Files, and Plan Changes During Execution. The default `PLAN` leaves those sections out, so they render as `none` and a prompt that reads the wrong section still passes. An assertion on the `STEPS` block must anchor on `\n\nSTEPS:\n` or on ` (your step)`, because `STEPS:\n` also matches inside `VALIDATION STEPS:`.
- The review-mr harness's `route()` stubs only the first verifier chunk, `verify:code-reviewer`. A case with more than eight findings in one dimension must also stub `verify:code-reviewer:2`, with verdict indexes restarting at 0, or the findings after the eighth land in `unverified` with the reason `verifier died`.
- The review-mr harness's default `verdict` carries a non-empty `reproduction`, so its finding routes to `confirmed` at any score. A case that expects a nit or a `not reproduced` entry must pass `reproduction: ''` on each verdict.
- The review-mr harness's `flat()` collapses whitespace, so a pin on a prompt substring must compare through `flat()` to survive a line wrap inside the prompt template.
- The execute-runner harness's `L1` fixture is a reproduced confirmed finding with `finalTag` `nit` at `finalScore` 0.4, the fixture for a confirmed finding below the threshold. The fix brief renders `finalTag` before `tag`, so `L1` shows as nit.
- The execute-runner and ship-runner harnesses each declare `AGENT_TYPES`, a table from label to agent type. The execute-runner case `the models map lands on every label by its agent type` runs `FULL_RUN` and checks every label in that table, so a new `agent()` label is covered only once it is added to `AGENT_TYPES`. The review-mr harness's `agent` stub records `model` and `effort` for each label.
- `execute-runner.js` spreads `models` into the `review-mr` child args only when it was given, so the cases that compare the child's whole args without a `models` arg still hold.
- The ship-runner harness checks arg validation through `throwsWith`. The plan-builder harness checks `error.message` from `run()` inline.
- The execute-runner harness's default `diff:red-team` capture returns the path `src/a.js`. A `seatRun` case with no `priorChangedPaths` and no `fix:validation` paths therefore blocks as stray before the panel. A seat-run case that must reach the panel passes the capture paths in `priorChangedPaths` or scripts a fix that reports them.
- Because `settleE2E` keys on result index, a stub that labels step 2 with another step's text is still settled as the end-to-end step at index 2. A case that pins the e2e outcome must place the result at the marked step's index.

## verify.sh conventions

- The run passes only when `pass + skip` reaches the floor on the last line of `verify.sh`. A check gated on `node` must emit exactly one `skip` for each `ok` it replaces, or a run without `node` falls below the floor.
- `verify.sh` runs the hook fixture suite as one check, so a fixture failure costs one pass, not one per fixture.
- The agent and skill counts are hardcoded in two places: the Structure checks in `verify.sh` and the expected welcome line in `hooks/tests/fixtures/session-start/06-startup-welcome.json`. [agents.md](../agents.md) states the agent count too. Adding or removing an agent or a skill means updating all of them.
- Three files state the case count of each behavior suite. `verify.sh` passes it to `suite_ok` as the minimum passed count, section 1 of `VERIFY.md` gives it after the suite name, and the suite's Tests line in [scripts.md](../scripts.md) or [workflows.md](../workflows.md) gives it too. Adding or removing a case means updating all three.
- A check that two files carry the same sentence must extract the sentence from both files and compare them, not hardcode it.
- The run-options checks in `verify.sh` are not sentence comparisons. They grep `^## Run options$` from `skills/plan-guide/SKILL.md`, require the literal `Run options` in each of `skills/crawl`, `plan-flow`, `execute-flow`, `ship-flow`, and `testing-gate` and the absence of `Do I have permission` in each, and extract the ceiling set from the one-line `"ceiling": {...}` entry in `scripts/validate-plan.py`, the one-line `const CEILING = {...}` in `workflows/ship-runner.js`, and the one-line `case "$I_CEIL" in ...)` in `hooks/session-start.sh`, sorted, and require all three to be equal. Each of those lines stays on one line for that reason. One more check extracts every quoted question sentence from plan-guide's `### Question set` subsection and requires that no other skill under `skills/` carries it.
- Every doctrine index line in `plugins/toolkit/CLAUDE.md` opens with a bold file name followed by an em dash. Any edit to such a line puts that existing em dash on an added line of the diff. A check for "no em dash on added lines" must compare each added line with the line it replaced.
- To exercise a run without `node` on a machine that has it, build a scratch directory of symlinks to every PATH tool except `node`, and run `verify.sh` with that directory as PATH. Build the directory under `/bin/bash -c`, because zsh does not word-split an unquoted `$PATH` expansion, so a loop written for bash sees one word.
- The `REVIEW.md` check strips backticks and quotes with `tr -d '\140\042\047'`, octal escapes, because a literal backtick inside the `$(...)` substitution breaks it.
- A check greps `review-mr.js` for the literal `toolkit:coupling-reviewer`, so the `REVIEWERS` array must keep that full string. A refactor that builds the agent names from short keys fails the check.
- The orchestration invariants check runs a Python heredoc over `agents/*.md` that prints `BAD <list> NONE <list> PIN <list>`, and the shell compares that output with `BAD  NONE  PIN ` exactly. A glob match passes even when `PIN` lists a file, so the comparison must stay exact. A separate check fails when `scripts/toolkit-models.json.template` routes any agent to Haiku.
- No check compares the `verify.sh` suite floors with the counts in `VERIFY.md`, so the two drift apart silently. The hook suite count in `VERIFY.md` is the JSON fixtures plus the non-fixture checks, and its floor is the `suite_pass` call after the hook suite run, not a `suite_ok` line.
- A group of contract checks pairs the files that must name the same token: `[e2e]` in plan-guide with `E2E_MARK` in `plan-index.py` and `E2E_MARK.test` in `execute-runner.js`, `Seat run passed:` in the `execute-flow` and `ship-flow` skills, the `(exclude,top)` pathspec in `seat-check.sh`, `execute-runner.js`, the `red-team` skill, and the `execute-flow` skill, `occupant: ` in `seat-check.sh` with `occupant:` in the `execute-flow` skill, `[shots]` in plan-guide, plan-builder and plan-critic with `SHOTS_MARK` in `plan-index.py`, and the `const REPLAY = null` line in `execute-runner.js` with `REPLAY_LINE` in `run-checkpoint.py`. One more check fails when the `execute-flow` skill names `AskUserQuestion`. A rename of any of these tokens must change every file its check reads.
