# Worktree seat

The seat is a repo's main checkout, the directory whose `.git` is a directory. `seat-check.sh` decides which live sessions hold it, and the `session-start.sh` hook, `seat-queue.sh`, section 2a of the `execute-flow` skill, and its section 11 seat run act on its output. The holder rule, the output lines, and the exit codes are in [scripts.md](../scripts.md#seat-checksh). This page lists the constraints a change to the script or its callers must keep.

## seat-check.sh

- The script parses the session list with `jq -rn 'input | ...'`. Plain `jq` exits 0 on empty stdin, so a missing or failing `claude` binary would read as an empty list and report the seat free. `input` errors on empty stdin, and the script turns that error into exit 2.
- The script joins each row on the 0x1f unit separator and reads it with `IFS=$'\x1f'`. It replaces any tab, newline, carriage return, or 0x1f inside a field with a space. A whitespace `IFS` such as a tab collapses consecutive separators, so a null `status` or `kind` would shift every later column.
- The dirty count runs `git --no-optional-locks status`, so a check from one session never writes the main checkout's `.git/index` while the holder works there. It also sets `core.fsmonitor=false` and a null `core.hooksPath`, because `seat-queue.sh` runs the check unattended on every verdict, and a repo config that names an fsmonitor command would otherwise run that command each time.
- The script resolves the main checkout as the parent of the git common dir when that dir is named `.git`. Otherwise it falls back to `git rev-parse --show-toplevel` of the path it was given.
- Every caller must pass its own session id as `--self`. Without it, a caller whose `cwd` is the main checkout lists itself as a holder and the script exits 10. `seat-queue.sh` is the one caller that omits `--self`, so its own `holder:` line tells it that the session sits in the main checkout.
- The script resolves the `--worktree` path with `cd` and `pwd -P` after it resolves the main checkout, and a path that does not resolve exits 2 with `not a directory`.
- The session loop collects the `live:` lines after the `kill -0` liveness test and before the `--self` skip, so `--live` lists the caller too. It collects occupants after that skip and before the holder test. `inside()` tests only the resolved worktree directory, so a session whose `cwd` is the main checkout is a holder and never an occupant, unless `--worktree` names the main checkout itself.
- The `occupant:` lines print after the `holder:` lines, and the `live:` lines after them, with the same tab-separated fields. The exit code still reflects holders only: 0 free, 10 held, 2 error. An occupant never changes it, so a caller must read the `occupant:` lines, not the exit code.

## The main: line

- The hook and the execute flow both read the `main:` line. A change to its label or its form must change both callers.
- The hook prints the seat line only when the script exits 10 and its `main:` line equals `cd $ROOT && pwd -P`. A linked worktree session's root is the worktree directory, so that equality is the only test that keeps such a session silent. The worktree-silent case in `hooks/tests/session-start-seat-check.sh` pins it.
- Section 1 of the `execute-flow` skill takes `repoName` from the `main:` line. It falls back to the section 3 verifier's `git rev-parse --path-format=absolute --git-common-dir` output only when the seat check exited 2, so a run from a linked worktree recalls and reports under the main checkout's name.

## The worktree

- Section 2a of the `execute-flow` skill names the worktree after the plan name, which `plan-guide` keeps lowercase kebab-case and unique across the vault, so no two plans share a directory under `.claude/worktrees/`. Under `none`, EnterWorktree `name` creates the branch `worktree-<planName>` for a plan branch that exists nowhere, and under `mr` or `merge` section 2a cuts the note's `branch` instead. A plan name holds no `/`, which EnterWorktree would turn into a `+` that section 3's ref-name check refuses. A worktree the note does not record is the plan's only by the section 2a ownership rule: it is on the plan's branch, or it sits in `.claude/worktrees/<planName>` on `worktree-<planName>` and the vault holds exactly one plan note of that name. When `test -d` finds the directory and the rule fails, section 2a stops with the plan note untouched and names the directory and the branch it holds.
- Section 2a opens a worktree with no question on a held seat, on a free seat whose `dirty:` count is above 0 on a run from approved or start-work, and, by the section 2a default branch rule, on a free, clean seat on a run from approved or start-work when the main checkout sits on `main`, `master`, the origin default branch, or a detached HEAD, because section 3 would stop that run at the branch check. It also opens one on a free, clean seat on a run from approved or start-work when the note's `branch` is not blank and the main checkout sits on any other branch, so the run never builds on a branch other than the note's. A run that stays in the main checkout, because no section 1 or section 2a step entered, re-entered, or adopted a worktree, stops at section 3 when its branch differs from a non-blank `branch`. A worktree run keeps the section 5 rewrite of the `branch` key instead, so a `test -d` re-entry after a failed install or an adopted `claude --worktree` session never stops there. The seat check's `branch:` line names `main`, `master`, and a detached HEAD with no probe, and one verifier reads `git symbolic-ref --short refs/remotes/origin/HEAD` only when the branch is none of those three and not the plan's branch. A held seat with a dirty main checkout stops a rerun and names the holders. Asking for the execute flow is the explicit request that EnterWorktree requires.
- When the main checkout is dirty and the table gives a worktree or a stop, a verifier lists its status with the own-worktree pathspec. Each untracked path gets the paste-ready line `printf '%s\n' '/<path>' >> "<common dir>/info/exclude"`, and each tracked path gets the sentence to commit or discard it. A path that holds a single quote, a backslash, `*`, `?`, or `[`, or that starts with `!` or `#`, gets no line. A worktree run lists these under `Main checkout not clean` in its report, because the seat run needs an empty status there. The flow never writes the exclude file, because it is the user's local git config.
- When `test -d <main>/.claude/worktrees/<name>` succeeds and the ownership rule passes, section 2a calls EnterWorktree with `path` and runs the install step whatever the seat state, so a rerun enters the worktree that an earlier run opened.
- When EnterWorktree is absent, a permission rule refuses it, or the call fails, section 2a stops with the plan note untouched. The report names the cause and the setting that removes it, such as a deny rule for EnterWorktree or `permissions.blockWritesOutsideWorkingDirectories`. Section 2a never asks and never falls back to the main checkout.
- EnterWorktree with `name` always creates a new branch from the `worktree.baseRef` setting and never checks out an existing branch. When the plan's branch exists locally or on origin, section 2a obtains the worktree with `git worktree add` under the note's ceiling, as a paste-ready command for the user under `none` and through an implementer under `mr` or `merge`, then calls EnterWorktree with `path`. Git refuses that add while another worktree has the branch checked out, so section 2a stops with the plan note untouched when `git worktree list --porcelain` shows the branch under another worktree, and a failed worktree command also stops. A failed `git ls-remote` reads as no remote branch only when `git remote get-url origin` also fails, because the repo then has no origin remote. Any other failed section 2a lookup stops the flow with the plan note untouched, because a failed lookup against a configured origin cannot tell a missing branch from an unreachable remote, and reading it as absent would fork the plan onto a new branch. A `claude --worktree` session, a worker session's included, starts on `worktree-<name>` cut from the same setting, so execute-flow section 3 stops a fresh run in such a worktree whose branch carries commits that are not on `origin/<default>`.
- When the plan's branch exists nowhere under `mr` or `merge`, an implementer runs `git fetch origin '<default>'` and `git worktree add --no-track -b '<branch>' '<main>/.claude/worktrees/<name>' 'origin/<default>'`, where `--no-track` keeps the default branch from becoming the new branch's upstream, or the add alone with no start point in a repo with no origin remote, which starts at the main checkout's HEAD and so runs only when the main checkout sits on `main` or `master`, and section 2a enters the directory with EnterWorktree `path`. A missing `origin/HEAD` stops the run with the section 3 set-head handoff. Section 2a calls EnterWorktree with `name` only under `none` when the plan's branch does not exist. After either route section 3 skips its merged check, because the new branch has no commits of its own. After any worktree entry, section 5 writes the worktree's branch from section 3 into the plan note's `branch` frontmatter when the two differ, so the commit handoff and the ship flow name the branch the worktree carries.
- After the switch, `repoRoot` is the worktree path in every later section. `repoName` does not change, because section 1 resolves it from the main checkout.
- The switch lasts only for the live session. Section 5 records `Seat: worktree <path>` under Plan Changes During Execution, and section 1 re-enters that path with EnterWorktree `path` before anything else in a later session. A session that already runs in that path counts as entered, so section 2a opens no other worktree. When the directory is gone or EnterWorktree fails, section 1 stops with the plan note untouched and names the recorded path. Before section 1 re-enters a recorded path, before the unrecorded worktree rule adopts a worktree, and before section 2a enters a directory that `test -d` found, the occupant check runs the seat check with `--worktree` on that path. It stops with the plan note untouched when another live session runs there. The check covers only a directory that exists and a session that the agents list reports. When it exits 2, the run continues and the report says so. A second session asked for the same plan before the first one's EnterWorktree created the directory finds nothing to check. The seat route to section 11 is the one run that section 1 starts from the main checkout on a note with a `Seat: worktree` line.
- The section 1 unrecorded worktree rule covers a session that already runs inside a worktree the note does not record, such as one started with `claude --worktree`, or one a failed install left in the same session. A verifier reads the worktree's branch and common dir from inside it, because the harness refuses a worktree session's git commands in the main checkout. Section 1 adopts the worktree when the ownership rule holds, section 2a runs the install step there, and section 5 records its `Seat: worktree` line. Otherwise section 1 stops and names the directory and its branch.
- A fresh worktree holds only tracked files, so section 2a runs the repo's install step after the switch. A line in the main checkout's `CLAUDE.md` that begins `Worktree install: ` overrides the default for a repo the default does not fit, and a `<worktree>` token in it expands to `.claude/worktrees/<name>`, the worktree path relative to the main checkout. `<name>` is the plan name, or the directory name of a worktree that section 1 adopted.
- Without that line, the default needs nothing declared. When the main checkout's `.env` has a line that begins `WARDEN_ENV_NAME=` and `composer.lock` exists, the composer part is `warden env exec -T php-fpm composer install -d /var/www/html/.claude/worktrees/<name> --no-interaction --no-scripts`, because Composer runs in the `php-fpm` container, which mounts the main checkout at `/var/www/html`. `--no-scripts` keeps a Composer script in the container from reaching the running stack, which serves the main checkout. Without Warden, the composer part is `composer install --no-interaction`. When `package-lock.json` exists, the npm part is `npm ci` on the host. The install is the composer part, the npm part, or both joined with `&&`, composer first. With neither lockfile, no install runs.
- The Warden command runs with the worktree as its working directory like any other install, and `warden` finds the environment by walking up from there.
- The install runs after every section 2a entry and never after a section 1 re-entry, because the earlier run installed there. An implementer runs it with the worktree as its working directory, because the harness blocks a worktree session's commands whose working directory is the main checkout.
- A failed install stops the flow with the plan note untouched, so the note carries no `Seat: worktree` line and section 1 does not re-enter the worktree. The worktree stays, and the next ask enters it through the `test -d` check and runs the install again, whether the seat is held or free.
- No worker or conductor builds a worktree's environment by hand: no symlink or copy from the main checkout into the worktree, no partial install, and no ignore-file edit to hide one. A worktree whose tests cannot run after the install step is a stop, not a repair.
- A run in a worktree, entered by section 1 or section 2a, passes `inWorktree: true` to the runner. The running local stack serves the main checkout, so the validation verifier does not run a Validation Step that needs it, such as the site's URL, a browser check, or a request to the local stack. It returns that step as deferred with `needs the seat` as evidence and runs every other step. The runner also defers every step that carries `[e2e]` after its number, whatever the verifier judged. A deferred step does not block.
- The plan note records each deferred step under Plan Changes During Execution as `Validation deferred: <step> (needs the seat)`, and the report lists them first under a line that reads "Deferred to the seat". Nothing is created outside the worktree for such a step: no container, no database clone, no media mount, and no hostname.
- The `deferred` status exists in the validation schema only under `inWorktree`, and a runner result without the `deferred` list reads as an empty list.
- `seat-check.sh` names `.claude/worktrees` once, in `OWN_WT`, for the holder rule and for the dirty-count pathspec `':(exclude,top).claude/worktrees/'`. `slice-capture.py`, which the `execute-runner.js` capture runs, the `red-team` capture, and the execute flow's status reads carry the same pathspec, so they list the paths that the dirty count counts. A worktree session holds no seat, and its directory is neither a dirty path nor a captured path, with or without an ignore entry. If Claude Code moves its worktree directory, the constant, `OWN_WORKTREES` in `slice-capture.py`, `execute-runner.js` and `ship-runner.js`, and every pathspec must move with it.
- In the [lead and worker session shape](../../plugins/toolkit/doctrine/orchestration.md#lead-and-worker-sessions), an execute worker session starts with `-w <planName>`, so Claude Code creates `.claude/worktrees/<planName>` on `worktree-<planName>`, or opens it when it exists, and section 1 adopts or re-enters it. After a lead report whose `Next:` line tells the lead to stop the worker session, the worker session leaves the worktree with ExitWorktree keep and the lead stops it with `claude stop`, never `claude rm`, because step 4's occupant check stops on a live session in the worktree and the lead's seat run waits in the seat queue while a live session sits in the main checkout. After any other report it stays in the worktree and waits for the lead's continue message, because the ship flow and a rerun both run from the recorded worktree.

## Seat run

Section 11 of the `execute-flow` skill runs the Validation Steps that a worktree run deferred, against the running local stack, by checking the plan branch out in the main checkout. Section 1 routes a note there when it holds a `Validation deferred:` line and its last summary is one of six that the section lists.

- Join and location. Step 1 runs the seat check and then `seat-queue.sh join` with the session id from the scratchpad path and `--lead <lead id>` when the worker session's first prompt carries a valid lead session id. A resume runs no queue command. `TURN` and `DIRTY` mark the entry seated, so the session holds the seat for every waiter whatever `cwd` the agents list reports. `DEADLOCK`, `LEAD`, exit 2, and any exit code the step does not list run the release and stop before any ExitWorktree call. A session under `<main>/.claude/worktrees/` leaves only on its turn: it writes the worktree path to the return file, then calls ExitWorktree keep, because the harness refuses a worktree session's commands whose working directory is the main checkout. On `WAIT` it stays in the worktree and goes to the queue wait. Asking for the execute flow is the request to leave the worktree, ExitWorktree asks no permission, and keep leaves the directory and the branch in place. When ExitWorktree is absent, refused, or fails, or the session still sits under `.claude/worktrees/`, step 1 runs the release and stops with the plan note untouched and names a session started in `<main>`. The flow never calls ExitWorktree with remove, which deletes the worktree and its branch.
- Free, clean, and the wait. Step 2 goes on to step 3 only after the join printed `TURN` or `DIRTY` and the main checkout's status, read with the own-worktree pathspec, prints no path. After `DIRTY` with a path, it runs the release and stops, and the stop names each dirty path, with the section 2a exclude line for each untracked path and the commit-or-discard sentence for each tracked one. A dirty main checkout would otherwise ride the switch onto the plan branch. In every other case the run waits: it starts `seat-queue.sh wait` in the background, runs `seat-queue.sh list`, and names in chat each seated entry, each waiter ahead, and each unqueued holder, which holds the wait until it ends or moves into a linked worktree. When section 1 kept a `<lead>`, the wait start sends the lead the same names by SendMessage. The run then ends its turn with the plan note and the evidence note untouched. On `TURN` or `DIRTY` from the watcher it goes back to step 1. On any other exit, or a `WAIT` after the third watcher, it runs `list` and the release and stops, naming each session that still holds the wait. After `LEAD`, from the join or from a watcher round, the run starts no watcher, and the stop and the lead report tell the lead to run the seat run itself once the worker session is stopped with `claude stop`, or to move into a linked worktree and dispatch the seat run again.
- Ref names. Every ref name the flow puts in a command, the remote's default branch included, must match `^[A-Za-z0-9._/-]+$` before any command names it, and the note's `branch` value and a restore point must also pass `git check-ref-format --branch`. A sha must match `^[0-9a-f]{7,40}$`, and every command single-quotes a ref name. The seat run also single-quotes `<main>`, `<worktree>`, and each staged path, because an agent runs those commands unattended, and a staged path that holds a single quote fails the fix commit instead of reaching the shell. Git accepts `;`, `$`, a backtick, `|`, and `&` in a branch name, so `git check-ref-format` alone does not keep a name out of the shell.
- Restore point. Step 5 writes `Seat run restore:` before the first switch, and step 10 writes `Seat run restored:` after the seat check that follows the restore shows `dirty: 0` and the restore point's branch. The open restore point is the last `Seat run restore:` line with no `Seat run restored:` line after it. A seat run reuses it only when the main checkout sits on the plan branch, because an earlier seat run switched in and stopped. When the main checkout sits anywhere else, step 3 records `Seat run restored: <branch> (by hand)` and picks a new restore point, so a stale one is never reused. With no open restore point, a main checkout already on the plan branch stops the run, because nothing records where it came from.
- Resume. Step 5 records `Seat run tip:` and `Seat run worktree:` with the plan branch tip and the worktree HEAD that step 4 read. A resume skips steps 3 to 6, so it reads both from the note, and step 2 rereads the open base diff and `git log` against the recorded tip. The worktree HEAD must come from the note, because a commit that lands on the detached worktree during the run would otherwise pass the step 10 check as unmoved. A failed restore records `seat-run blocked: the restore failed`, so the next ask starts again at step 2 rather than resuming the runner.
- Open base. When no open base exists, step 5 records `Seat run base: <sha>` with the plan branch tip. The open base is the last such line with no `Seat run passed:` line after it, so only a pass closes it. Every seat run passes the open base as the runner's `diffBase` and the paths that `git diff --name-only <base> <branch>` prints as `priorChangedPaths`, so its capture, panel, and cold read cover every commit since the base, a fix that a blocked seat run committed included. A passing run records `Seat run reviewed:` with every sha that `git log --format=%H <base>..<tip>` prints and its own commit sha. A run passes only when every step a `Validation deferred:` line names came back `pass`, so a deferred step reported as manual or pre-existing keeps the ship flow's cap in place.
- Worktree checks. Step 4 first runs `test -d` on the recorded `Seat: worktree` path and stops naming that path when it is gone, because a remove answer at Claude Code's worktree exit prompt deletes the directory. The worktree status must be empty. On a run that picks a new restore point, the worktree HEAD must equal `git rev-parse '<branch>'`. On a run that reuses one, the worktree is already detached, and the HEAD must pass `git merge-base --is-ancestor` against `<branch>`, because a blocked seat run may have committed on `<branch>` after the detach.
- Occupants. The last step 4 read reruns the seat check with `--worktree <worktree>`, before the status write and the detach. Any `occupant:` line stops the run and names each session, because the detach would move the HEAD under a live session. A session whose reported `cwd` is the main checkout is a holder instead, which the step 1 join and the step 2 wait hold the run for.
- Detach before switch. Git refuses to check a branch out in the main checkout while another worktree has it checked out, so step 6 runs `git switch --detach` in the worktree first. When the main checkout's switch then fails or is denied, the implementer reattaches the worktree. Step 10 restores the main checkout first, then reattaches the worktree only when its HEAD still equals the step 4 sha. On a mismatch, the worktree stays detached on that commit, so nothing is orphaned, and the outcome is blocked with the sha named.
- Staged and stray paths. The runner blocks a seat run before the panel when the red-team capture holds a path that no fix wrote, that no commit since the base holds, and that sits outside `.claude/worktrees/`. Step 9 reads a fresh status. It stages only the paths that the runner's `changedPaths` or the section 8 implementer's `changedPaths` hold, and any other dirty path is stray. A stray path keeps the open restore point and skips the restore, because a switch carries untracked files to the branch it switches to.
- Commit before the restore. Step 9 commits the fixes on a blocked run too, so the restore never carries them onto the restore point. When `git add` or `git commit` fails or is denied, the run records `Seat run blocked: the fix commit failed:`, keeps the open restore point, and runs no restore. The report hands the commit block and then the restore commands.
- Worktree baseline. Section 6 records a `Baseline:` line on every execute run, taken in the worktree before the slice. The seat run passes its failing names as `baselineFailing`, and the runner refuses `seatRun` without `baselineFailing` and `diffBase`. A baseline taken in the main checkout after the switch would already hold the slice, so a check the slice broke would read as pre-existing. On a seat run the runner turns an `[e2e]` step reported as pre-existing into a fail, because the worktree baseline could not run a step that needs the stack.
- Lockfiles and guards. Step 4 stops before the switch on any path in the restore diff, `git diff --name-only '<restore point>' '<branch>'`, whose file name is a listed lockfile of composer, npm, yarn, pnpm, bun, bundler, poetry, pipenv, or uv, because the installed dependencies match the restore point. The stop names the plan branch as the side that changed it when the branch diff `'<restore point>...<branch>'` holds the path, and the restore point side when only the restore side diff `'<branch>...<restore point>'` holds it. For the restore point side, the stop names the remedy: update the plan branch from the default branch, then rerun the seat run. Each `Seat run guard: <path prefix>` line in `<main>/CLAUDE.md` stops the run on a branch diff path with that prefix. A guard reads only the branch diff, because a migration that only the restore point carries does not run when the plan branch is served. The toolkit ships no default guard.
- Local stack. The restore returns the code but not the local database or caches, so every seat run report states that the stack keeps any change it applied.
- Under `none`, every switch, the commit, and the restore are paste-ready handoffs, and the run stops after each.
- Ship. The ship flow takes `repoRoot` from the path on the last `Seat: worktree` line when that directory exists, because the plan branch is checked out there, and from the note's `repo` frontmatter when it does not. It caps a `merge`-ceiling run at `mr` while a `Validation deferred:` line has no later `Seat run passed:` line that names the HEAD it would merge, so a ship fix commit after a pass brings the cap back.
- Cleanup. Under `ceiling: merge`, the ship-runner cleanup reads the seat with `seat-check.sh --self` at cleanup time, after the merge. It switches the main checkout off the plan branch only when the exit code, the seat line, and the holder lines agree on `seat: free`, as the seat run does. It fast-forwards a clean main checkout already on the default branch under live holders, because the pull moves no holder off its branch, and the report names the holders. It removes the plan's worktree only when its own `--worktree` read at cleanup time ran and names no occupant. [context-ship-flow-constraints.md](context-ship-flow-constraints.md#cleanup) lists the rest of its guards.
- Run id. The seat run writes its run id to `<scratchpad>/seat-run-<planName>.runid`, a file separate from the execute flow's `execute-flow-<planName>.runid`, and then opens a `seat run` block in the evidence note, which step 8 completes. Step 2 treats the ask as a resume only when the last summary is `seat-run started` under this session's id and that file exists, and then relaunches with `resumeFromRunId`.
- Return. Step 1 writes the path of the worktree it leaves to `<scratchpad>/seat-run-<planName>.return`. The release at step 12, after the restore, calls EnterWorktree `path` on that path when the plan note has no open restore point, the directory exists, and its `--worktree` read names no occupant, then deletes the file and runs `seat-queue.sh leave`. A session that started in the main checkout has no return file, so it runs the leave and stays a holder by its `cwd`.
- Summary ownership. Step 8 records the section 6 lines, `Fix rounds used:` included, apart from `Changed path:`, `Baseline:`, `Blocked at:`, `No blocked tree:`, `Seat:`, and the holder lines, and leaves the `seat-run started` summary for step 11 to rewrite. On a seat run, section 8 writes no summary and closes no report, so a section 8 Hold still continues to the step 9 commit and the step 10 restore.

## Seat queue

`seat-queue.sh` keeps the order of the sessions that wait for the main checkout. Its subcommands, status lines, and exit codes are in [scripts.md](../scripts.md#seat-queuesh).

- Storage. The queue is `<git common dir>/toolkit-seat-queue/`, which every linked worktree resolves to the same path and git never lists. Each joined session has one entry named `<join epoch seconds>-<sessionId>`. The entry is empty while its session waits and holds `seated` once the session has its turn. The seated mark is file content, not a rename, so a listing never misses an entry while its state changes.
- Grant lock. A `mkdir` of `.grant` in the queue directory serializes every grant step and every leave, because macOS ships no `flock`. Each verdict reads the seat before it takes the lock, because the agents read can take 3 seconds, and reads each entry's state once under it. A contender removes a lock older than 10 seconds, which belongs to a killed process. A join creates its own empty entry without the lock, because a file that lands after a verdict's listing is decided by its own later verdict, which takes the lock and sees every mark written before it.
- Miss rule. A registry rewrite can hide a live row from one agents read, and such a row looks the same as a dead session. So an entry goes only on a second miss 5 seconds to 10 minutes after the first, which `.miss-<sessionId>` records, and a marker older than 10 minutes counts as a first miss again. A missed seated entry keeps holding the seat until the removal. A wait round, or a join that already had an entry, whose own row is missing waits a round instead of taking the turn, so the step 1 join after a watcher `TURN` never drops the entry. A join that creates its entry and misses its own row reads again 5 seconds later, and exits 2 only when that read misses it too. A verdict removes only entries from the listing it took before its seat check, so it never removes a join that lands during the read.
- Seated holder. A seated entry counts as a holder for every other session, beside the `holder:` lines, so the queue does not depend on the agents-list `cwd` after ExitWorktree. Other seat readers, such as the session-start seat line and another run's section 2a, still read `cwd` alone.
- Turn rule. A session outside the main checkout gets its turn when no waiting entry is ahead of it, no other session holds the main checkout or a seated entry, and its own row read live. A session in the main checkout ignores order, because it already holds the seat for everyone else by its `cwd`, and waits only for the other holders. `DEADLOCK` covers only a waiting entry beside such a session, because the two would wait for each other. A seated entry there is a run at work, so it is waited for. `DIRTY` is a turn on a dirty main checkout, which waiting does not clear, so step 2 stops and names the paths.
- Unqueued holders. A session in the main checkout with no entry holds every waiter until it ends or moves into a linked worktree. The wait start names each one to the user and, by message, to `<lead>`. When `<lead>` is an unqueued holder, the queue prints `LEAD`, and the run starts no watcher and stops at once, so the lead runs the seat run itself once the worker session is stopped, or moves into a linked worktree and dispatches it again. The run passes the lead's session id from its first prompt, because names can repeat, and without a valid id it waits for the lead as for any other holder.
- Worker sessions. A worker session that waits for its lead's continue message stays in its worktree, so it never holds the queue. A worker session whose report tells the lead to stop it leaves its worktree with keep, and the lead stops it with `claude stop`, never `claude rm`, because rm removes the worktree and its branch.
- Liveness needs a pid. A live background session lists a pid. A stopped session, or one whose process Claude Code's supervisor ended after about an hour finished or waiting for its next message, lists `pid: null`. Such a session has no `live:` line on either join read, so its join exits 2 and keeps no entry, and its seat run stops. A join with no entry would let a run that no seat reader sees switch the main checkout under a queued waiter.
- Release. The release removes the entry after the return to the worktree, or at once for a session that started in the main checkout. It keeps the session in the main checkout with its entry seated while the plan note has an open restore point or the return fails. Every stop in steps 1 and 2 after the join runs it. A stop after step 2 runs no release, so the session keeps the seat until it ends or a later ask reaches step 12. A background `seat-queue.sh wait` writes `seated` into the entry as it prints `TURN`, before the conductor acts on the notification, and nothing expires a seated mark while its session stays live, so the other waiters stay held until that session acts on the turn or ends. This window is accepted.
- Watchers. A run starts one watcher at a time and at most three per ask, as ship-flow section 7b caps `watch-mr.sh`, each with the wait bound that [scripts.md](../scripts.md#seat-queuesh) states, which the execute flow passes.
- Sessions outside the queue. A session that never joins can take a free seat first. The woken run's next verdict reads `WAIT`, which empties its mark, so it stops holding the seat while it waits again.

## Several repos

Section 2b of the `execute-flow` skill runs a note whose repo set, as `plan-guide` § Repos and modules defines it, holds two or more repos. [0010-plans-span-several-repos.md](../decisions/0010-plans-span-several-repos.md) records why.

- Projects root. The session must start in the projects root, the directory that holds each top-level repo as `<projects root>/<repo>`, and a `git rev-parse --path-format=absolute --git-common-dir` read that exits 0 there stops the run with the relaunch command. The harness guard refuses git against another repo only in a session isolated in a worktree, so section 2b never calls EnterWorktree or ExitWorktree. It opens each top-level repo's worktree at `<main>/.claude/worktrees/<planName>` with the section 2a branch lookup and `git worktree add` commands through one implementer per repo, runs the section 2a seat check and occupant check per repo, and runs each repo's install after it creates that worktree.
- Rules and hooks. A session in the projects root loads no repo's `.claude/settings.json` hooks, `.claude/settings.local.json` permissions or `.claude/rules/`. Before any worktree exists, one verifier per home lists `CLAUDE.md`, `AGENTS.md` and `.claude/rules/*.md` with `find`, never a shell glob, because zsh aborts a command whose glob matches nothing, and reads each settings file's hooks with `jq`. Rule files come from the main checkout, because some exist only there, untracked. A home with hooks stops the run until its `CLAUDE.md` holds a `Several-repos hooks: <how its checks are covered>` line, whose text, cut to 300 characters, reaches every worker through the runner's `repos` arg.
- External module checkouts. A project whose `CLAUDE.md` holds `Module checkout path: <template>`, a relative path with a `<repo>` token, keeps each module's working checkout at `<projects root>/<template>`, with `<repo>` taken from the last segment of the module's `composer.lock` source url less `.git`. That checkout must exist with that origin, because the flow never clones a module. Section 2b opens its worktree like a top-level repo's and records `Module checkout: <package> at <mw> on <branch> (worktree of <c>)`.
- Nested module checkouts. Without that line, each module is a nested checkout at `<project worktree>/<path>`. When it holds no `.git` after the project install, one implementer runs the module install: a `Module install:` line in the project's `CLAUDE.md`, with `<worktree>` and `<package>` replaced, else `composer reinstall --prefer-source --no-scripts --no-interaction` for the package, in the Warden `php-fpm` container when `.env` names a Warden environment with the default web root, and on the host otherwise. A Warden environment with another `WARDEN_WEB_ROOT` stops the run, because its container cannot see the worktree. The flow reads `.git` again rather than the exit code, because Composer installs the dist archive when the clone fails, and then switches the module to its branch. Section 2b records `Module checkout: <package> at <m> on <branch>`.
- Edit probe. When the project has `Several-repos hooks:` text, section 2b runs each PreToolUse hook whose matcher covers `Edit` once, from the project worktree with a 30-second timeout, on a payload that edits `<m>/composer.json`. Exit 2 means the project refuses edits under that module path, as a vendor guard does, so the run stops and names the `Module checkout path:` line. The probe reads only `tool_input.file_path`, so a hook that reads more of the payload can answer differently than in a session.
- Runner edit check. The runner's first multi-mode stage, `edit:check`, has one implementer per top-level root write and remove `<root>/toolkit-edit-check-<planName>.tmp` through the Workflow agent path the real edits use. Claude Code treats `.claude` as a protected directory with its own worktrees as the exception, and a `permissions.allow` rule does not pre-approve a protected-path write, so a refusal blocks the run before any work. The check proves only the first write, because in auto mode the classifier judges each later write again. A nested module root sits inside its project's root, so it gets no check of its own.
- Re-entry. Section 5 writes one `Seat: worktree` line per top-level repo and one `Module checkout:` line per module, and section 1 re-enters each with the seat path rule, `test -d` and the occupant check, with no install and no module step.
- No seat run. Section 11 does not run on such a note, because the seat run switches one main checkout. The user runs each deferred step against the running local stack and records `Validation step accepted:` for it, which lifts the ship flow's seat cap.

## Seat line size

- The hook re-sends the seat line on every request, so its size is a budget. The fixed text is 241 bytes, and a change to the wording must recount it.
- The hook keeps at most three holders. It cuts each holder name to 24 and each status to 8 with awk `substr`, and the branch to 40 with `cut -c`. That keeps a line with three ASCII holders and an ASCII branch under 400 bytes, and the line-cap and three-holders cases in the hook test pin it.
- The macOS system awk counts bytes in `substr`, and `cut -c` counts characters under a UTF-8 locale. A branch name with multibyte characters can therefore push the line past 400 bytes.

## Tests

- The seat-check suite creates its linked worktree at `<main>/.claude/worktrees/wt` and adds no exclude entry for it, so its dirty cases prove the pathspec. Its occupant cases prove the `--worktree` listing: a live session in that path is an occupant, and a session in the main checkout is a holder and not an occupant.
- The hook test makes a holder live by writing the test shell's own `$$` as its `pid`, so `kill -0` succeeds without starting a process. It supplies the session list through `TOOLKIT_AGENTS_FILE`, which the hook passes to the script through its environment.
- The seat-queue suite builds its own repo with two linked worktrees under `.claude/worktrees/`, apart from the seat-check fixture. It sets join order and turn state with fixed epochs and file content, ages a lock with `touch -t` and a miss marker with perl `utime`, holds a fresh lock to check that a join waits for it, holds one join between its listing and its seated write with a stub `ls` and gives both joins one epoch with a stub `date` to check that the other join gets no turn, and passes `--lead` to check the lead stop and its fallback to the wait, and `--parent` to check that the earlier option name still works. Its round-change cases run against a stub `claude` with `TOOLKIT_AGENTS_FILE` unset, because that variable fixes one answer for every round.
- `session-start-seat-check.sh` reuses `_sr_make_repo` from `session-start-recall-check.sh`, so `run-all.sh` must source it after that file.
- A suite file that cleans up with a recursive force `rm` on a variable must be written with the Write or Edit tool. [context-watch-mr.md](context-watch-mr.md) gives the hook rule behind this.
